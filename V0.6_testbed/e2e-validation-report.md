# spec-driven-dev Skill V0.6 — 差分実地検証(CR-003)レポート

作成日: 2026-08-04

## これは何か

`spec-driven-dev` Skill(V0.6)が、`V0.5_testbed` の検証で新たに見つかった2件の問題(P904の完了CR記法が二値前提であること、CRによるデータモデル変更時のマイグレーション冪等性についてSkillに指針が無いこと)を意図どおり解消しているかを、`V0.6_testbed/`(`V0.5_testbed/` を土台に `.claude/skills/spec-driven-dev/` だけをV0.6に差し替えたテストヘッド)上で確認した記録。

あわせて、V0.5の検証で「✅合格(ただし確度の割引あり)」と判定され、V0.6のreview-report §2で「V0.6ではSkillの記述は変更せず、代わりに `V0.6_testbed` で実際に動的検証を行う」と明記されていた V0.4 defect 1-6(P302のデプロイトポロジー確認)を、実際にトポロジーを壊した状態から検証してクローズした。

検証は3部構成で行った。

* **Part 1(Tier A・動的検証、中心)**: 新規のCR-003(予約に参加予定人数を追加)をP901→P905のフルフローで実際に処理した。CR-003は**非冪等な `ALTER TABLE ... ADD COLUMN` を必然的に伴うデータモデル変更**であり、V0.6の新しいマイグレーション規定が働くべき条件を確実に踏むよう設計した。CR-002ラウンドと異なり、意図的なバグ注入は行っていない。
* **Part 2(Tier A・動的検証)**: デプロイ資産(`docker-compose.yml`・`nginx.conf`)を意図的に壊した状態から、`SKILL-P302-deliver.md` の実行前チェック項目7・項目8を適用して検出できるかを検証した。検証後、資産は破壊前と同一に復旧した。
* **Part 3(Tier B・静的検証)**: Part 1・2で踏まないV0.6の変更、特に `TEMPLATE-CR.md` ↔ `SKILL-P904-cr-verify.md` の矛盾解消を、両ファイルの現物で確認した。

**結果サマリ**: V0.6が対応した2件(1-1・1-2)はいずれも**実際に実行担当の振る舞いを変えた**。特に1-2は、CR-002が「実装後にクラッシュして気づいた」問題を、CR-003では「スコープ決定の段階で論点として上げ、設計方針を文書化し、実測で確認する」という流れに変えており、机上の記述の追加にとどまっていない。V0.4 defect 1-6も動的検証で検出可能であることを確認し、V0.5の確度の割引を解消した。一方で、V0.6にも**新たに3件の問題**(うち1件は「重大度: 中」相当の設計上の指摘)を発見した。詳細は「3. V0.6で新たに見つかった問題」を参照。

最終状態: **バックエンド159件 + フロントエンド57件、全PASS**。`docs/.inprogress` なし、`docs/CR.md` に未完了CRなし、`docs/cr-records/CR-003.md` にP905の判定結果あり(=ステップ0の完了判定を満たす)。デプロイ資産は正常な単一オリジン構成に復旧済み。

## 1. Part 1: CR-003の詳細(Tier A検証の中心)

### 1.1 CRの内容

`docs/cr-records/CR-003.md` として最終的に記録した。要旨:

> 予約に「参加予定人数(attendee_count)」を追加する。S03(予約作成画面)・S04(予約詳細・編集画面)で任意入力の整数として登録・編集でき、S02(予約カレンダー画面)の予約サマリには表示しない。バックエンドでは `reservations` テーブルに `attendee_count` カラムを追加し、`POST /api/reservations`・`PUT /api/reservations/{reservation_id}` のリクエストと、`GET /api/reservations/{reservation_id}`・`GET /api/reservations/mine` のレスポンスに含める。値が入力された場合、予約先の会議室の収容人数(`rooms.capacity`)を超えていたらバリデーションエラー(400)とする。未入力(null)は許容する。

CR-002(会議室に説明文を追加)と同じく「画面項目追加・変更」「API契約変更」「データモデル変更」の3カテゴリにまたがるが、次の2点を意図的に加えた。

* **非冪等DDLの必然性**: `RESERVATIONS` への `ALTER TABLE ... ADD COLUMN`。V0.6の新しいマイグレーション規定が働くべき条件をピンポイントで踏む。
* **エンティティ横断のバリデーション**: 予約の `attendee_count` と会議室の `capacity` の比較。これまでの予約バリデーションはすべて予約単体で完結しており(純粋関数化できた)、初めて「純粋関数に置けない検証」が発生する。

### 1.2 P901(CR作成)

* 優先度ルーブリック(影響度×緊急度)を適用: 影響度「高」(S03・S04は全利用者が日常的に使う主要機能で、`POST`/`PUT /api/reservations` というシステムの中核APIの契約が変わる)× 緊急度「低」(備考欄に人数を書くという回避策があり、実害の報告なし)→ **優先度「中」**。判断理由を明記のうえ★FIXME★を付記した。
* CR-002は「低×低→低」だったため、本ラウンドで**ルーブリックの別の象限を実際に通した**ことになる。

### 1.3 P902(要件定義更新)

* 更新前の原本を `docs/P001-requirement_20260804_CR-003.md` として保持。既存3ファイルと共存することを確認した。

### 1.4 P903 — 「データモデル変更」カテゴリの必須確認(V0.6の新規定、本ラウンドの主眼)

`SKILL-P903-refactor-execute.md` の新しい必須確認を、**書かれているとおりに順番に**実施した。以下は、その過程で実際に起きたことの正直な記録である。

**(1) 「`docs/P003-backend-spec.md` に記載されているマイグレーション方式を確認する」**

→ **記載が無かった**。V0.5時点のP003 §6.3には、CR-002処理時に書かれた「`ALTER TABLE ADD COLUMN` はSQLiteの構文上『未適用の場合のみ』という条件付き実行ができないため、`init_db()` 側で `duplicate column name` エラーを捕捉して無視する実装とした」という★FIXME★付きの**実装メモ**が1行あるだけで、V0.6のP003が要求する3点(適用のタイミングと方式/その方式が冪等かどうか/冪等でない場合の担保方法)としての記載は無かった。

**(2) 「記載が無い場合は、実際のコード(マイグレーション実行処理)を読んで現在の方式を特定し、P003に追記する」**

→ 指示が具体的だったため、迷わず `server/app/db/connection.py` を読んだ。現行方式は「アプリ起動時に `migrations/*.sql` をファイル名順に **全件** `executescript()` で再実行し、`sqlite3.OperationalError` のメッセージに `duplicate column name` が含まれる場合は当該ファイルの適用を `continue` で打ち切る」というものだった。

**(3) 「非冪等DDLを追加する場合は、既存の適用方式のままでアプリケーションを再起動しても正常に起動するかを必ず確認する」**

→ 実測した。既存方式のまま素朴に `0003_add_reservation_attendee_count.sql`(1文)を置いて `init_db()` を2回連続実行したところ、**2回目も成功した**。

ここが本検証で最も重要な発見である。**V0.6のP903が定める検証条件(「実際に初期化処理を2回連続で実行し、2回目も成功すること」)だけを機械的に満たすなら、この時点で「問題なし」として先に進むことになる。** CR-002の場当たり対処は「1ファイル1文」という慣習の下では実際に冪等に振る舞うためである。

**(4) 既存方式の妥当性の再評価(P003側のルールが効いた部分)**

しかしP003側のルールは、方式を書くだけでなく「**その方式が冪等かどうか**」「**冪等でない場合に、どう冪等性を担保するか**」を明記せよと要求している。この2点を文書に書き下ろそうとすると、「なぜ冪等なのか」を仕組みのレベルで説明する必要が生じる。そこで説明を試みた結果、次の限界が見えた。

* 例外を捕捉した時点で **そのファイルの残りの文が黙って読み飛ばされる**(`continue` はファイル単位のループに対して効く)。
* エラーメッセージの文字列一致で判定しているため、同一ファイル内の別の文が起こした本物のエラーを取り違えて握りつぶす余地がある。
* 「どこまで適用済みか」の情報がどこにも残らない。

これを机上の推測で終わらせず、**実測で確認した**。一時DBに「カラム追加 + 付随するインデックス作成」の2文からなるマイグレーションを適用したのち、インデックスだけを落として(=途中まで適用済みの状態を再現して)`init_db()` を再実行すると、先頭の `ALTER TABLE` が `duplicate column name` になった時点で後続の `CREATE INDEX` に到達せず、**インデックスは復元されないまま `init_db()` が正常終了した**(エラーも警告も出ない)。

* 実測手順と結果: `docs/test-records/20260804-1520-cr003-test-record.md` 末尾「補足: 既存のマイグレーション冪等化(CR-002の場当たり対処)の妥当性検証」。

**(5) 判断: 冪等化そのものをCRのスコープに含めた**

P903の規定「冪等でない場合は、冪等化(バージョン管理テーブルの導入、適用済みエラーの捕捉など)もCRの対応範囲に含め、その判断と実施内容をCRの記録に残す」に従い、**`SCHEMA_MIGRATIONS` テーブルによる差分適用方式への切り替えをCR-003のスコープに含めた**。

* 新方式: `SCHEMA_MIGRATIONS`(`filename` TEXT PK、`applied_at` TEXT)に適用済みファイル名を記録し、未記録のファイルのみを **1文ずつ** 適用して記録する。
* 既存DBからの移行(ブートストラップ): CR-002以前の方式で構築されたDBは `SCHEMA_MIGRATIONS` を持たないため、初回の移行時に限り 0001・0002 が「未適用」と判定されて再実行される。この場合に出る「既に適用済み」を意味するエラー(`duplicate column name` / `... already exists`)のみを読み飛ばすが、**同一ファイル内の後続の文の実行は継続する**(場当たり対処との決定的な違い)。
* 2回目以降の起動では1文も実行されないため、今後さらに非冪等DDLを追加しても再起動で失敗しない。この性質はCRごとに再検証しなくてよい。
* この方針をP003 §6.4「スキーマの適用方式(マイグレーション方式)」として新設し、V0.6が要求する3点をそのまま見出し構成にした。切り替えた理由(上記の実測結果を含む)、ブートストラップ手順、検証観点も記載した。

**(6) 検証: 「実際に初期化処理を2回連続で実行し、2回目も成功すること」**

実ファイルに対して実測した。

```text
=== 1回目(初回起動相当) ===
init_db() 1回目: 成功
  RESERVATIONS: [... 'attendee_count']
  SCHEMA_MIGRATIONS: ['0001_initial.sql','0002_add_room_description.sql','0003_add_reservation_attendee_count.sql']
=== 2回目(停止→再起動相当、同一DBファイル) ===
init_db() 2回目: 成功   (スキーマ・記録とも1回目と同一)
=== 3回目(念のため) ===
init_db() 3回目: 成功
```

さらに、2回のマイグレーションを経たDBファイルに対して実際に `uvicorn` を起動し、`GET /api/me` が `401 AUTH_REQUIRED` を返す(=アプリが正常に起動して応答している)ことを確認した。自動化版として `server/tests/test_db_init.py::DbInitIdempotencyTest`(4件: 2回実行、データ保持、適用記録、CR-003以前DBからの移行)を追加した。

### 1.5 P903 — CRスコープの決定

22フェーズ分の対象/対象外とその理由を `docs/cr-records/CR-003.md` に記録した。CR-002(17フェーズ分)より対象範囲が広い。要点:

* **対象**: P002, P003(§6.4新設を含む), P004(軽微), P005(軽微), P006(運用観点の新設を含む), P007(新規U007), P008(新規T024〜T028), P020, P102相当, P103相当, P104相当, P301, **P302**。
* **対象外**: P009(新規シナリオを伴わないため既存回帰確認で代替)、P010〜P012(矛盾を生じさせないため)、P021(ADRはP905で確認)、**P022**、P101、**P201〜P205(FAILが発生しなかったため)**。

対応表の目安を超える判断が2件あり、いずれも理由を明記して記録した。

* **P302を対象にした**: 「データモデル変更」行の目安フェーズにP302は含まれていないが、マイグレーション適用方式の変更は納品物の起動可否に直接影響するため対象に含めた。CR-002ではP302を対象外にしており、判断が変わった。
* **P022を対象外にした**: マイグレーション方式の変更はアーキテクチャ上の決定に見えるが、レイヤー構成・技術選定・コンポーネント分割のいずれも変えておらず、ArchitectureHandbookの記述粒度には影響しないと判断した。

また、P201〜P205は「対象外(発生せず)」となった。CR-002では事前予測(対象外)が実際のFAIL発生により「対象」へ変わったのに対し、CR-003では予測どおり発生しなかった。スコープ決定の予測が当たる場合・外れる場合の両方を実地で確認できたことになる。

## 2. Part 2: P302の実行前チェックの動的検証(V0.4 defect 1-6のクローズ)

### 2.1 背景

V0.5の検証レポートは、defect 1-6(P302のデプロイトポロジー確認)について次のように留保していた。

> ただし、本当に「トポロジーを壊した状態からP302を再実行して検出できるか」までは今回検証していない(nginxの修正を意図的に外して再実行するのは本ラウンドのスコープ外としたため)。この点は判断の確度をやや割り引いて評価した。

1. `docker-compose.yml`・`nginx.conf` をスクラッチ領域(`/tmp/scratch/deploy-backup/`)に退避し、md5を記録した。
2. **意図的に破壊**: `nginx.conf` を削除し、`docker-compose.yml` から nginx サービスを除去して、server を `ports: 8000:8000`、client を `ports: 8080:8080` で**別オリジン公開**する構成に置き換えた。`client/js/api/*.js` は一切変更していない(同一オリジン相対パスfetchのまま)。

### 2.3 項目7を適用した結果 — **検出できた**

項目7の文言は次のとおり(V0.5から変更なし)。

> 7. フロントエンドとバックエンドを分離して配布する構成(例: `client/` `server/` をそれぞれ別コンテナにする docker-compose 構成)の場合、フロントエンドのAPI接続前提(例: 同一オリジンでの相対パスfetchか、絶対URLでのクロスオリジンfetchか)と、本フェーズで組み立てる実際の配布トポロジーが一致しているか

この文言を機械的に適用すると次のようになる。

* **前提条件の判定**: 「`client/` `server/` をそれぞれ別コンテナにする docker-compose 構成」に該当するか → **該当する**(壊した構成はまさにこれ)。項目7が発火する。
* **フロントエンドのAPI接続前提の確認**: 文言が「同一オリジンでの相対パスfetchか、絶対URLでのクロスオリジンfetchか」と**確認すべき2択を明示している**ため、何を見るべきかが自明である。`client/js/api/*.js` を確認すると、`authApi.js` は `const BASE_URL = ""` を定義して `` fetch(`${BASE_URL}/api/auth/login`) ``、他の3ファイルは `fetch("/api/rooms")` のように直接相対パス。→ **同一オリジンでの相対パスfetch**。
* **実際の配布トポロジーの確認**: server(:8000)と client(:8080)の**2オリジン**。リバースプロキシなし。
* **判定**: 不一致。

**この検出に、項目7の文言以外の知識は必要なかった。** 見るべきファイル(`client/js/api/*.js` 相当のフロントエンドのAPI呼び出し箇所)と判定軸(相対パス vs 絶対URL)が文言の中で名指しされているため、経験的な勘に頼らずに到達できる。V0.5の検証が「同じ発見に至る蓋然性は高い」と推定していた点は、実際にそのとおりだった。

### 2.4 実測による裏付け

壊した構成を実際に起動して確認した。

| 要求 | 想定する主体 | 結果 |
|---|---|---|
| `http://127.0.0.1:8080/api/me`(client オリジンへの相対パス要求 = ブラウザが実際に出す要求) | ブラウザ上のSPA | **404**(静的配信サーバーが返す。APIには到達しない) |
| `http://127.0.0.1:8000/api/me`(server オリジンへの直接要求) | P009受け入れテストのHTTPクライアント | **401 AUTH_REQUIRED**(APIは正常) |

この**非対称性**が、項目7が防ごうとしている問題そのものである。P009受け入れテストはバックエンドに直接接続するため全件PASSしたまま、実際に配布するとフロントエンドからAPIが1本も呼べない。V0.4実行時にP302作業中に偶然発見された不具合と同じ構造であり、それが再現することを実測で確認した。

### 2.5 「判定」の強制力 — **十分に強い**

判定節の文言は次のとおり。

> 7.のフロントエンド/バックエンドの接続前提と実際の配布トポロジーが一致しない場合(…)→ これを不具合として扱い、本フェーズを完了とする前に、フロントエンドの接続設定(例: `BASE_URL` の環境変数化、リバースプロキシの追加など)を修正する。修正せずに本フェーズを完了としない。単に「10. 未整備事項」に記載するだけで済ませ、壊れたトポロジーを黙って納品しない。

評価すると、この文言は**逃げ道を3重に塞いでいる**点が効いている。

1. 「不具合として扱い」— 分類を先に固定する(「制約」「既知の課題」に格下げできない)。
2. 「本フェーズを完了とする前に…修正する」「修正せずに本フェーズを完了としない」— 完了条件に組み込む。
3. 「単に『10. 未整備事項』に記載するだけで済ませ…ない」— **最もありがちな抜け道を名指しで禁止している**。

本testbedの `docs/P302-deliver.md` §10には、既に「Docker Compose資産が未検証」「TLS終端が未整備」といった**未整備事項として許容されている項目**が並んでおり、トポロジー不一致もその横に1行足せば形式上は収まってしまう。3.の一文が無ければ、そちらに流れる誘因は実際に強かった。この一文の効果は本実験で実感できた。

### 2.6 項目8(V0.6新設、再起動/冪等性)の検証

同じ枠組みで項目8も適用した。

* 判定の規定「8.の再起動時の起動可否が確認できていない場合 → 実際に初期化処理を2回連続で実行して確認する(実行環境の制約で確認できない場合は、その旨を「10. 未整備事項」に明記する)。2回目が失敗する場合は、7.と同様に不具合として扱い、冪等化を行ってから本フェーズを完了とする。」に従い、実測を行った(結果は §1.4(6))。
* 項目7と同じ扱い(黙って納品しない)に揃えられていること、および「実行環境の制約で確認できない場合」の逃げ道が**明示的な記載義務付き**で用意されていること(=黙って飛ばすことは許されない)を確認した。本サンドボックスではDockerデーモンが無いためコンテナとしての再起動確認はできないが、`init_db()` レベルでの2回連続実行は実行可能だったため、そちらで確認した。この使い分け自体が判定文から自然に導かれた。

## 3. V0.6で新たに見つかった問題

V0.6が対応した2件とは別に、本検証の過程で以下を新たに発見した。V0.6(`/tmp/work/V0.6/`)のファイル自体は変更していない。

### 3.1 P903の検証条件「2回連続実行して2回目も成功すること」が必要条件にとどまり、既存方式の妥当性判断としては不十分 — 新規指摘、重大度: 中

* **事象**: `SKILL-P903-refactor-execute.md` の「データモデル変更」カテゴリの必須確認は、締めくくりとして次のように書かれている。

  > この確認は単体テスト・結合テストでは代替できない(テストごとに新しい一時DBを作る構成では常に初回実行になるため)。**実際に初期化処理を2回連続で実行し、2回目も成功すること**をもって確認とし、結果をテスト記録に残す。

  「〜をもって確認とし」という書き方は、この条件を**十分条件として提示**している。しかし本検証で実測したとおり、CR-002の場当たり対処(`duplicate column name` を捕捉して当該ファイルの適用を打ち切る)のまま非冪等DDLを1文だけ追加した状態でも、**2回連続実行は成功する**。この条件だけを満たして先に進むと、既存方式が抱える問題(同一ファイル内の後続の文が黙って読み飛ばされる、本物のエラーを取り違える、適用状況が追跡できない)はすべて見逃される。
* **なぜ今回は見逃さなかったか**: P903の検証条件ではなく、**P003側のルールが効いた**。`SKILL-P003-backend-spec.md` は「その方式が**冪等かどうか**」「冪等でない場合に、どう冪等性を担保するか」を文書に明記せよと要求しており、これを書き下ろすには方式の仕組みそのものを説明する必要がある。説明を試みた過程で「例外を捕捉した時点でファイルの残りが読み飛ばされる」という性質に気づき、実測して確認できた。つまりV0.6が「4ファイルに分けて捉える」設計を採ったことが結果的に効いており、**P903の必須確認だけを読んだ実行担当は、2回実行の成功をもって『問題なし』と判断する可能性が高い**。
* **影響**: 「1ファイル1文」という(どこにも明文化されていない)慣習が守られている限り顕在化しない。しかしマイグレーションに「カラム追加 + バックフィルUPDATE」「カラム追加 + インデックス作成」のような複数文を書いた時点で、途中まで適用済みのDB(適用中のプロセス異常終了、リリース後のファイル追記など)に対して**沈黙して壊れる**。しかも `init_db()` は成功扱いで終了するため、ログにも何も残らない。
* **推奨対応(V0.7検討課題)**: P903の検証条件に、2回連続実行に加えて次のいずれかを追加することを推奨する。(a)「既存の適用方式が『適用済みかどうか』をどう判定しているかを説明できること」を確認項目にする、(b)「エラー捕捉によって冪等性を担保している場合は、捕捉のスコープ(文単位かファイル単位か)を確認し、ファイル単位であれば1ファイル1文の制約が守られていることを確認する」を明記する。あるいは、P003側にある「冪等かどうかを説明せよ」という要求への参照をP903の必須確認から明示的に張る(現状のP903は「P003のマイグレーション方式を確認する」としか書いておらず、P003が要求している3点の中身までは参照していない)。

### 3.2 `SKILL-P904-cr-verify.md` の「アウトプット文書」節に、V0.5由来の二値表現が1箇所残存 — 新規指摘、重大度: 低

* **事象**: V0.6は 1-1 への対応として、P904本文の完了CR記法を二値から手順ベースに全面的に書き換えた。しかし同じファイルの「アウトプット文書」節(21行目)は、V0.5から変更されずに次のまま残っている。

  > * `docs/CR.md` (対応が完了したCRを削除、または状態を更新)

## 5. 総評: V0.6の文言は実際に実行担当の振る舞いを変えたか

本検証の主眼は「V0.6の新しい文言が、机上で良く見えるだけなのか、実際に実行担当の振る舞いを変えるのか」である。項目ごとの正直な評価は次のとおり。

**1-1(P904の完了CR記法)— 変えた。** V0.5の文言下では「実際の記法を『残す』『削除する』のどちらに分類するか」という解釈作業が必要で、V0.5の検証レポートも「上位の趣旨を汲んで」という留保付きで記録していた。V0.6は分類作業そのものを廃し、「現物を見て複製する」+「確認すべき3点」という機械的な手順に置き換えている。本ラウンドでは3点をチェックリストとしてそのまま使えたため、解釈の余地が生じる場面が無かった。加えて、根本原因(テンプレートとの矛盾)を潰して記述を一本化したことで、再発の構造も除去されている。

**1-2(マイグレーション冪等性)— 変えた。ただし効いたのは主にP003側である。** CR-002では「実装してテストを流し、アプリを起動してクラッシュしてから対処を発明した」のに対し、CR-003では**スコープ決定の段階で冪等性が論点として上がり、設計方針を先に決めてから実装した**。この差は明確にV0.6のP903の必須確認によるものである。また「P003に記載が無ければコードを読んで特定しP003に追記する」というフォールバックが、Skillのルール変更が既存文書に遡及しないという構造的限界を実質的に回避しており、この設計は良い。

一方で正直に書くと、**P903の必須確認だけを読んでいたら、既存の場当たり対処を「2回実行して成功したから問題なし」と追認していた可能性が高い**。既存方式の欠陥に気づけたのは、P003が「その方式が冪等かどうか」「冪等でない場合にどう担保するか」を**文書に書かせる**ことで、方式の仕組みを言語化させたからである。V0.6が意図した「4点で捉える」設計が結果として保険になった形だが、P903の検証条件そのものは弱い(3.1)。この点は「文言が振る舞いを変えた」というより「文言の組み合わせが偶然カバーした」と評価するのが正確である。

**1-6(P302トポロジー確認)— 変えた(そして今回それを実証できた)。** 項目7は、見るべき対象(フロントエンドのAPI呼び出し箇所)と判定軸(相対パス vs 絶対URL)を文言の中で名指ししているため、経験的な勘に頼らずに不一致へ到達できる。さらに判定節が「未整備事項に書いて済ませる」という最もありがちな抜け道を名指しで禁止しており、この一文が実際に効いた。本testbedの `docs/P302-deliver.md` §10には既に許容済みの未整備事項が複数並んでいて、そこに1行足せば形式上は収まる状況だったため、禁止の一文が無ければ流れていた可能性は十分にある。

**総合**: V0.6の2件の対応は、いずれも「実際にやってみて初めて表面化した問題」への対応として妥当であり、実行担当の振る舞いを実際に変えている。特に1-2は、単一箇所への追記で済ませず4フェーズに分けて配置した判断が有効に働いた。ただし3.1で指摘したとおり、P903の検証条件は「必要条件を十分条件のように書いている」という弱さがあり、V0.7で補強する価値がある。3.2・3.3はいずれも軽微で、1〜2行の追記で解消する。
