### 2.2 API別テスト観点(主要な異常系)

| API | 主要な異常系テストケース |
| --- | --- |
| POST /api/auth/login | 400(必須項目欠落)、401(ID/パスワード不一致、無効化済みユーザー) |
| POST /api/auth/logout | 未ログイン状態での呼び出しでも200(冪等) |
| GET /api/me | 401(未ログイン) |
| GET/POST/PUT/DELETE /api/rooms | 401(未ログイン)、403(一般ユーザー)、404(存在しないroom_id)、400(バリデーション、重複名) |
| GET/POST/PUT/DELETE /api/reservations 系 | 401、403(本人・管理者以外の編集/取消)、404(存在しないID)、400(バリデーション)、409(重複) |
| GET/POST/PUT/DELETE /api/users | 401、403(一般ユーザー)、400(社員ID重複、自己無効化) |

* 上記の異常系は、`docs/P002-frontend-spec.md` §2(共通エラーレスポンス形式)・§4(API外部仕様)に定義されたステータスコード・エラーコードと一致することを結合テスト(P008)で確認する。
* 権限まわり(一般ユーザーが管理者専用画面・APIにアクセスできないこと、予約の編集・取消が本人/管理者のみであること)は、P001の指示どおり必ず結合テストで確認する対象とする。単一スプリント内で完結する権限チェック(例: 会議室APIへの一般ユーザーアクセス)はP008、スプリントをまたぐ・役割をまたぐ確認(例: 管理者が他人の予約を編集できるか)はP009で扱う。

## 3. 非機能観点のテスト

| 観点 | テスト内容 | テストレベル |
| --- | --- | --- |
| 性能 | `GET /api/reservations`(1週間分・全会議室)のレスポンスタイムを計測し、カレンダー画面の描画開始までが3秒以内に収まることを確認する | システムテスト(P009) |
| 負荷・同時実行 | 同一会議室・同一時間帯に対し複数リクエストを同時発行し、成立するのは1件のみであること(`docs/P003-backend-spec.md` §5の排他制御)を確認する | システムテスト(P009) |
| セキュリティ | 一般ユーザーが管理者専用API(rooms/users のPOST/PUT/DELETE、GET /api/users)を直接呼び出した場合に403になること。未ログイン状態で保護APIを呼び出した場合に401になること。パスワードが平文でDB・レスポンスに含まれないこと | システムテスト(P009) |
| 運用(ログ監視) | アプリケーションログが標準出力にJSON Lines形式で出力され、エラー発生時にエラーログが出力されることを確認する(`docs/P003-backend-spec.md` §8) | システムテスト(P009) |
| 運用(再起動耐性) | アプリケーションを停止・再起動しても正常に起動すること(初期化処理・マイグレーションが冪等であること)を確認する。具体的には、**同一のデータベースファイルに対して `app.db.connection.init_db()` を2回連続で実行し、2回目も成功すること**、および2回目の実行後もスキーマ(カラム構成)・既存データが壊れないことを確認する。`docs/P003-backend-spec.md` §6.4 に記載のとおり、本プロジェクトのマイグレーションは `SCHEMA_MIGRATIONS` テーブルによる差分適用方式である。 | 独立した運用観点(下記の注記参照)。実装としては `server/tests/test_db_init.py` の再起動シナリオテストで自動化し、加えて納品前チェック(`docs/P302-deliver.md` 実行前チェック項目8)で実測する |

* **「運用(再起動耐性)」を独立した観点として明示する理由(※CR-003により追加)**: この観点は、テストごとに新しい一時データベースを作る単体テスト・結合テストでは**構造的に検出できない**。それらのテストでは初期化処理が常に「初回実行」になり、2回目以降の実行だけで顕在化する非冪等なDDL(`ALTER TABLE ... ADD COLUMN` など)を踏まないためである。一方、実運用の再起動シナリオでは確実に踏む。したがって機能観点のテストに紛れ込ませず、独立した観点として計画に明記する(`SKILL-P006-test-plan.md`「運用観点(再起動耐性)」の規定にもとづく)。

## 4. テスト遂行上の技術的な決め事

* **外部APIのモック方針**: 本アプリはGoogleカレンダー/Outlookカレンダー等の外部サービス連携を持たない(P001で本バージョン対象外と明記)。したがって外部APIのモックは不要である。
* **テストデータの準備方法**:
  * SQLiteのテスト用DBファイルをテスト実行ごとに初期化するシードスクリプト(`server/tests/seed.py` 等、実装スプリントで作成)を用意し、管理者ユーザー1名・一般ユーザー数名・会議室数室をあらかじめ投入する。
  * 予約データの日付は、テスト実行日を基準とした相対日付(例: 実行日+1日)で生成し、`docs/P002-frontend-spec.md` §3 S03の「過去日付不可」バリデーションと矛盾しないようにする。
  * 結合テスト・受入テストは、原則としてテストごとに独立したデータ(または独立したトランザクション)を用い、他のテストケースの実行順序に依存しないようにする。
