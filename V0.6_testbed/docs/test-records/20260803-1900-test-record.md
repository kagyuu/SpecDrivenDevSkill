## 根本原因の分析(第1回で判明したもの)

* **根本原因1(A001・A002・A003・A004・A005・A006・A007・A010、およびA008手順1に共通)**: `server/app/api/auth.py` の `login()` が発行するセッションCookieに `secure=True` を無条件に設定している(ADR-004の決定どおり)。ADR-004自体は妥当な決定だが、本アプリケーションの配布物には(P302 Closingが未実施の時点で)TLS終端を行うリバースプロキシやHTTPS証明書が一切含まれていない。そのため `server/INDEX.md` に記載の実行方法(`uvicorn app.main:app --reload`、プレーンHTTP)どおりに起動して実際のHTTPクライアント(ブラウザ、`requests`等、RFC 6265準拠のCookieジャーを持つあらゆるクライアント)からアクセスすると、ログイン自体は成功する(Set-Cookieはブラウザに保存される)ものの、`Secure`属性のためそのCookieが平文HTTP接続では二度と送信されず、ログイン直後から実質的に全ユーザーが未認証扱いになる。
  * P008の単体・結合テスト(T001等)がこの不具合を検出できなかった理由: `server/tests/test_api_auth.py` 等がStarletteの `TestClient` を `base_url="https://testserver"` で生成しており、テスト用HTTPクライアントの通信を疑似的に常にHTTPS扱いにしていたため、`Secure`属性のあるCookieでも問題なく送受信できていた。これは実装時(P102)の単体テストの都合による回避策であり、実際のHTTPデプロイ環境の挙動を反映していない。
* **根本原因2(A009)**: `docs/P003-backend-spec.md` §8で要求されている「標準出力への構造化ログ(JSON Lines)」の出力コードが実装されていない(単なる仕様未実装の抜け漏れ)。
* **根本原因3(A008手順2、コードの不具合ではない)**: `docs/P009-acceptance-direction/A008-security-password-and-sql-injection.md` の期待結果は「bcrypt形式(`$2b$...`)」を明記しているが、本サンドボックスの制約により`docs/P101-impl-context.md`で承認済みの代替方式(`hashlib.scrypt`、ADR-004実装詳細)を全システムで一貫して使用している。これはP009文書がP101の代替決定(Executor開始時点、Plan Loop Step完了後)より前に書かれたテスト指示書であるため、実装済みの承認済み代替と表現が食い違っているだけであり、セキュリティ上の欠陥ではない(平文保存されていないことは確認済み)。
