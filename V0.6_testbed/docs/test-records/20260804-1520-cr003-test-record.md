## 補足: 既存のマイグレーション冪等化(CR-002の場当たり対処)の妥当性検証

CR-003のスコープ決定にあたり、`SKILL-P903-refactor-execute.md`「データモデル変更」カテゴリの必須確認に従って、CR-002で入れた対処(`init_db()` が `duplicate column name` を捕捉して当該ファイルの適用を `continue` で打ち切る)のままでも再起動できるかを実測した。

* 単純に `0003`(1ファイル1文)を追加しただけの状態では、**2回連続実行は成功した**(つまり「2回実行して成功するか」という確認だけでは、この対処の問題は表面化しない)。
* しかし、1ファイルが複数文で構成され、かつ途中まで適用済みのDBに対して再実行した場合、先頭の `ALTER TABLE` が `duplicate column name` になった時点で**後続の文が黙って読み飛ばされ、`init_db()` は成功扱いで終了する**ことを実測で確認した(検証コード: 一時DBに対して「カラム追加 + インデックス作成」の2文からなるマイグレーションを適用したのち、インデックスのみを削除して再実行 → インデックスは復元されず、エラーも警告も出ない)。
* この結果を踏まえ、CR-003では冪等化そのものをCRの対応範囲に含め、`SCHEMA_MIGRATIONS` テーブルによる差分適用方式に置き換えた(`docs/P003-backend-spec.md` §6.4)。判断の詳細は `docs/cr-records/CR-003.md` を参照。
