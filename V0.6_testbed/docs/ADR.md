# ADR.md — 会議室予約システム

本プロジェクトで現在有効な設計判断を管理する。
過去に廃止された設計判断は `ADR_master.md` に移動する(現時点では廃止済みADRはなく、`ADR_master.md` は未作成)。

* 1つの決定 = 1つの ADR-NNN とする。
* 「決定内容」「理由」は、後続のAI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。長い経緯や検討の過程そのものは書かず、結論とその根拠だけを残す。
* 状態が「廃止」になったADRは、本文を `ADR_master.md` に移し、この `ADR.md` の一覧・本文からは削除する。`ADR_master.md` 側には、廃止日と廃止理由(何のADRに置き換えられたか)を追記する。
* 本書はP022フェーズ(Overview Step)で、`docs/P001-requirement.md` 〜 `docs/P005-impl-plan.md` から後戻りできない/コストの高い技術的決定を抽出して初回作成したものである。Plan Loop Step(P002〜P012)自体では設計の矛盾は検出されなかった(`docs/P010-design-review.md` 参照)ため、決定を覆す既存ADRの廃止は発生していない。

## ADR-001

### タイトル

フロントエンド技術スタックにReact 18 + TypeScript + Viteを採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-SCREEN-001 〜 REQ-SCREEN-007(全画面)

### 背景

会議室×時間帯のカレンダーグリッドなど、状態変化の多いインタラクティブなUIを画面数7件程度の中規模SPAとして構築する必要がある(`docs/P001-requirement.md`「フロントエンドで使う技術」)。

### 決定内容

フロントエンドはReact 18 + TypeScript + Viteで構築する。状態管理はReact標準機能のみとし、Redux等の外部状態管理ライブラリは導入しない。

### 理由

* SPA・カレンダーUI構築の実績・エコシステムが豊富である。
* コンポーネント分割による画面再利用性が高い。
* 画面数が7件と少なく、Reduxのような外部状態管理を要するほどの状態複雑度がない。

### 検討した代替案

#### Redux等の外部状態管理ライブラリ導入

却下。理由: 画面数・状態の複雑度に対して導入コスト(ボイラープレート、学習コスト)が見合わないため。

### 影響範囲

* Frontend全体(`client/`)

### 関連成果物

* `docs/P001-requirement.md`(フロントエンドで使う技術)
* `docs/P002-frontend-spec.md`
* `docs/P005-impl-plan.md` §5(`client/`ディレクトリ、npmビルド)

### 備考

なし

## ADR-002

バックエンド技術スタックにPython + FastAPI(レイヤードアーキテクチャ)を採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-API-001 〜 REQ-API-017(全API)

### 背景

型ヒントベースの実装と、フロントエンドとのAPI契約(OpenAPI)を明確にしたいという要求があり(`docs/P001-requirement.md`「バックエンドで使う技術」)、かつ予約重複チェック等の業務ロジックを単体テストしやすい構成が求められる。

### 決定内容

バックエンドはPython + FastAPIを採用する。内部構成はController/Handler層(FastAPIルーター)→Service層(業務ロジック)→Repository層(SQLite CRUD)のレイヤードアーキテクチャとする(`docs/P003-backend-spec.md` §1)。

* レイヤー分離により、重複チェック等の業務ロジック(Service層)をHTTP・DBから独立して単体テストしやすい。

### 検討した代替案

#### レイヤー分離なし(Handlerに業務ロジックを直接実装)

却下。理由: 予約重複チェック等の業務ロジックの単体テストが困難になり、`docs/P006-test-plan.md`が要求する単体テストレベルでの検証がしにくくなるため。

### 影響範囲

### 関連成果物

## ADR-003

### タイトル

データストアにSQLiteを採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-NFR-004(スケーラビリティ)
* REQ-NFR-005(想定同時利用者数)

### 背景

想定規模は従業員300名・会議室10室程度、ピーク時同時30接続程度の中規模社内システムである(`docs/P001-requirement.md`「システムの前提」「非機能要件」)。

### 決定内容

データストアにSQLite(ファイルベース、`server/`配下に配置)を採用する。追加のミドルウェア(Redis等のキャッシュ、メッセージキュー)は導入しない。

### 理由

* 想定規模(同時30接続、単一サーバー構成)では、サーバー型RDBを別途運用するコストに見合わない。
* ファイルベースのため運用・バックアップが単純。
* `BEGIN IMMEDIATE`によるファイルロックベースの排他制御で、想定規模の同時実行制御は成立する(ADR-006参照)。

### 検討した代替案

#### PostgreSQL等のサーバー型RDB

却下(本バージョンでは)。理由: 想定規模では単一サーバー構成で要件を満たせると判断し、運用コストの高いサーバー型RDBは過剰である。ただし将来の多拠点展開等でスケールアウトが必要になった場合、SQLiteは複数サーバー間での共有書き込みに向かないため、サーバー型RDB(PostgreSQL等)への移行が必要になる(`docs/P003-backend-spec.md` §8)。この移行要否は将来のCRの起票候補として`docs/ArchitectureHandbook.md` §9(既知の制約・技術的負債)にも記録する。

### 影響範囲

* Backend全体、Repository層、デプロイ構成

### 関連成果物

* `docs/P001-requirement.md`(バックエンドで使う技術)
* `docs/P003-backend-spec.md` §5, §8
* `docs/P005-impl-plan.md` §5

### 備考

将来的なスケールアウト要否は非機能要件REQ-NFR-004の観点で継続的に監視する対象であり、`docs/P003-backend-spec.md` §8で「後続のADR整理で意思決定として記録することを推奨する」とされていた事項に対応するADRである。

## ADR-004

### タイトル

認証方式にCookieベースのサーバーサイドセッション認証を採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-SCREEN-001(S01ログイン画面)
* REQ-API-001 〜 REQ-API-003(login/logout/me)
* REQ-NFR-003(セキュリティ)

### 背景

社内アカウント(ID/パスワード)によるログインが必須要件であり(`docs/P001-requirement.md`「システムの前提」)、将来的な社内SSO(SAML/OIDC)連携の検討余地も残しておく必要がある。

### 決定内容

ログイン成功時にサーバーがセッションCookie(`session_id`、HttpOnly / Secure / SameSite=Lax、有効期限8時間)を発行するCookieベース認証を採用する。レスポンスボディにトークン(JWT等)は含めない(`docs/P002-frontend-spec.md` §1)。

### 理由

* フロントエンドがCookieの中身を意識せず、ブラウザの自動送信に任せられるため実装がシンプルになる。
* HttpOnly Cookieにより、XSS経由でのトークン窃取リスクをJWTのlocalStorage保存等と比べて抑えられる。
* 社内向けWebアプリ(単一オリジン想定)であり、Cookieベース認証のCSRF対策(SameSite=Lax)で要件を満たせる。

### 検討した代替案

#### JWT(レスポンスボディでトークンを返却しフロントエンドが保持)

却下。理由: フロントエンドでのトークン保管(localStorage等)がXSS時の窃取リスクを高めるため、また本アプリはSPA単体でモバイルアプリ等の他クライアントを持たず、JWTのステートレス性の利点(サーバー側にセッション状態を持たない)が活きる場面が乏しいため。

### 影響範囲

* Frontend(Cookie送信を前提としたHTTPクライアント設定)、Backend認証・認可ミドルウェア

### 関連成果物

* `docs/P002-frontend-spec.md` §1
* `docs/P003-backend-spec.md` §2
* `docs/P007-impl-direction/U001-foundation-auth.md`

### 備考

将来の社内SSO(SAML/OIDC)連携(`docs/P001-requirement.md`「連携・参考にする既存システムの有無」)は本バージョンの対象外。SSO導入時はこのADRの見直し(CR起票)が必要になる可能性が高い。

* ★P202-F001修正(2026-08-03)★ 本決定どおりセッションCookieには `Secure` 属性を既定で付与する(`SESSION_COOKIE_SECURE`環境変数、既定値 `true`)。この決定は「本番相当の配布ではTLS終端(リバースプロキシ等)を経由してブラウザとの通信がHTTPSであること」を前提にしている。本アプリの配布物には現状TLS終端コンポーネントが含まれておらず(`docs/P302-deliver.md` 未整備事項参照)、TLSなしでのローカル動作確認・受け入れテスト時に限り `SESSION_COOKIE_SECURE=false` を明示指定してSecure属性を無効化できる(`server/app/api/auth.py`)。本番相当のデプロイでは既定値(`true`)のまま、TLS終端を用意すること。詳細: `docs/test-records/20260803-1900-test-record.md`根本原因1、`docs/P202-fix-plan/fixed/F001-session-cookie-secure-flag.md`。

## ADR-005

### タイトル

セッションの永続化先にSQLiteの`sessions`テーブル(DB保存)を採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-API-001 〜 REQ-API-003(login/logout/me)

### 背景

ADR-004でCookieベースセッション認証を採用したことに伴い、セッション状態(`session_id` → ユーザー・有効期限)をサーバー側のどこに保持するかを決定する必要がある。

### 決定内容

セッションはアプリケーションサーバーのインメモリではなく、SQLiteの`sessions`テーブル(システム全体で共有する永続ストア)に保存する(`docs/P003-backend-spec.md` §2)。

### 理由

* 単一サーバー構成ではあるが、サーバー再起動時にセッションが失われない(再起動のたびに全ユーザーが再ログインを強いられることを避ける)。
* 既にSQLiteを採用しており(ADR-003)、追加のミドルウェア(Redis等のセッションストア)を持ち込む必要がない。

### 検討した代替案

#### アプリケーションサーバーのインメモリ保存

却下。理由: サーバー再起動(デプロイ・障害復旧時)のたびに全セッションが失われ、全ユーザーの再ログインが必要になるため、可用性要件(平日日中99%以上、`docs/P001-requirement.md`非機能要件)の観点で望ましくない。

### 影響範囲

* Backend認証・認可ミドルウェア、Repository層(`sessions`テーブル)

### 関連成果物

* `docs/P003-backend-spec.md` §2, §6.2

### 備考

無効化されたユーザーの既存セッションは即時失効ではなく遅延失効(次回リクエスト時に`users.is_active`を確認して失効させる)方式とする旨が`docs/P003-backend-spec.md` §2に★FIXME★付きで記載されている。リアルタイム性が必要になった場合はこのADRとあわせて即時失効方式への見直しを検討する。

## ADR-006

### タイトル

予約重複チェックの排他制御に`BEGIN IMMEDIATE`トランザクションを採用する

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-API-011(POST /api/reservations)
* REQ-API-012(PUT /api/reservations/{id})
* REQ-NFR-005(想定同時利用者数)

### 背景

同一会議室・同一時間帯への二重予約を防ぐ必要があり、かつSQLiteという単一ファイルDBを採用済み(ADR-003)であるため、チェックと書き込みの間に他のリクエストが割り込む競合状態(TOCTOU)を防ぐ仕組みが必要になる。

### 決定内容

予約の作成・更新時、`BEGIN IMMEDIATE`でトランザクションを開始して書き込みロックを即座に取得し、トランザクション内で重複チェックのSELECTを行った上でINSERT/UPDATEし、重複があれば`ROLLBACK`して`409 RESERVATION_CONFLICT`を返す(`docs/P003-backend-spec.md` §5)。

### 理由

* SQLiteは書き込みが事実上シリアライズされるため、`BEGIN IMMEDIATE`による早期ロック取得だけで追加のミドルウェア(分散ロック等)なしに排他制御が実現できる。
* 想定同時接続数(ピーク時30接続程度)の規模であれば、書き込みロック待ちによる性能影響は許容範囲内と見積もられる(`docs/P003-backend-spec.md` §8)。

### 検討した代替案

#### 楽観的ロック(バージョン番号によるCompare-And-Swap)

却下。理由: 実装が複雑になり、本アプリの規模・SQLiteの特性(書き込みシリアライズ)に対して`BEGIN IMMEDIATE`より複雑さに見合うメリットが薄いため。

#### アプリケーションレベルの分散ロック(Redis等)

却下。理由: 単一サーバー構成でSQLiteのファイルロックのみで排他制御が成立するため、追加のミドルウェア導入は過剰(ADR-003の判断とも整合)。

### 影響範囲

* Backend Service層・Repository層(予約作成・更新API)

### 関連成果物

* `docs/P003-backend-spec.md` §5, §8
* `docs/P007-impl-direction/U003-reservation-core.md`
* `docs/P009-acceptance-direction/A007-concurrent-reservation-requests.md`

### 備考

具体的な負荷試験による検証はP009受け入れテスト(A007)で行い、本ADRの見積もりを検証する方針(`docs/P003-backend-spec.md` §8)。

## ADR-007

### タイトル

予約(RESERVATIONS)は物理削除、会議室・ユーザーは論理削除とする

### 状態

採用

### 日付

2026-08-03

### 関連要求

* REQ-API-013(DELETE /api/reservations/{id})
* REQ-SCREEN-006 / REQ-API-007(会議室の論理削除)
* REQ-SCREEN-007 / REQ-API-017(ユーザーの論理削除)

### 背景

`docs/P001-requirement.md`は会議室・ユーザーの削除操作を明示的に「論理削除」と定めているが、予約の取消操作については削除方式(論理/物理)を明記していない。

### 決定内容

会議室(ROOMS)・ユーザー(USERS)は論理削除(`is_active`フラグ)とする一方、予約(RESERVATIONS)の取消は物理削除とする。`RESERVATION_PARTICIPANTS`は`ON DELETE CASCADE`で連鎖削除する(`docs/P002-frontend-spec.md` §4.13、`docs/P003-backend-spec.md` §9)。

### 理由

* 会議室・ユーザーはマスタデータであり、既存の予約(過去の`created_by`・`room_id`参照)が残るため、参照整合性のために論理削除が必要。
* 予約はマスタデータではなく、取消後は業務上「無かったこと」として扱ってよいトランザクションデータであり、履歴保持の要求がP001に明記されていない。

### 検討した代替案

#### 予約も論理削除とする

却下(暫定)。理由: P001に予約の履歴保持(監査ログ等)要求が明記されておらず、物理削除の方がスキーマ・クエリともに単純になるため。ただし、この判断はP001に明記のない事項をP002が仮定したものであり(★FIXME★)、監査要件が判明した場合は本ADRの見直し(論理削除への変更、CR起票)が必要になる。

### 影響範囲

* Backend Repository層(RESERVATIONS DELETE)、DBスキーマ(FK制約)

### 関連成果物

* `docs/P002-frontend-spec.md` §4.13
* `docs/P003-backend-spec.md` §9

### 備考

本決定はP001に明記のない事項に対する仮定(★FIXME★)を前提にしている。将来的にP001側で予約の履歴保持要件が明確化された場合は、本ADRを見直したうえで状態を「廃止」とし、`docs/ADR_master.md`へ移すこと。

## ADR-008

### タイトル

スキーマの適用方式に`SCHEMA_MIGRATIONS`テーブルによる差分適用を採用する

### 状態

採用

### 日付

2026-08-04

### 関連要求

* CR-003(予約に参加予定人数を追加。非冪等な`ALTER TABLE ... ADD COLUMN`を必要とした)
* REQ-NFR-002(可用性。アプリケーションの再起動で起動不能にならないこと)

### 背景

初期構築時(P102/U001)のマイグレーション実行方式は「アプリ起動のたびに`migrations/*.sql`を全件再実行する」というものだった。初期スキーマ(`0001_initial.sql`)が`CREATE TABLE IF NOT EXISTS`のみで構成されていたため冪等に成功しており、この方式は当時は問題にならなかった。

しかしCR-002(`ALTER TABLE ROOMS ADD COLUMN description`)以降、SQLiteに`ADD COLUMN IF NOT EXISTS`相当の構文が無いことから、全件再実行方式では2回目以降の起動が`duplicate column name`で失敗する。CR-002では`init_db()`側で当該エラーを捕捉して当該ファイルの適用を打ち切る場当たり的な対処を採ったが、CR-003で同種のカラム追加が再び必要になったのを機にこの対処の妥当性を再評価した。

### 決定内容

適用済みのマイグレーションファイル名を`SCHEMA_MIGRATIONS`テーブル(`filename` TEXT PK、`applied_at` TEXT)に記録し、**未適用のファイルのみを1文ずつ適用する差分適用方式**を採用する。外部のマイグレーションツールは導入しない。既存DB(`SCHEMA_MIGRATIONS`を持たない、CR-002以前の方式で構築されたもの)からの移行のため、初回の移行時に限り「既に適用済み」を意味するエラー(`duplicate column name` / `... already exists`)を読み飛ばす。詳細な手順は`docs/P003-backend-spec.md` §6.4。

### 理由

* CR-002の場当たり対処は、例外を捕捉した時点で同一ファイルの残りの文が黙って読み飛ばされる。1ファイルが複数文(カラム追加 + インデックス作成/バックフィル等)で構成される場合、途中まで適用済みのDBに対する再実行で後続の文が適用されないまま正常終了する(実測で確認、`docs/test-records/20260804-1520-cr003-test-record.md`)。
* エラーメッセージの文字列一致だけで「適用済み」を判定していると、同一ファイル内の別の文が起こした本物のエラーを取り違えて握りつぶす余地がある。
* 適用済みかどうかの状態がどこにも残らないため、運用時にどのマイグレーションまで適用されているかを確認できない。
* 差分適用方式では、2回目以降の起動で1文も実行されないため、非冪等なDDLを含むマイグレーションを今後追加しても再起動で失敗しない。この性質は今後のCRごとに再検証しなくてよい(方式そのものが冪等性を保証するため)。

### 検討した代替案

#### 外部マイグレーションツール(Alembic等)の導入

却下。理由: ADR-003(SQLite採用、ORMを使わず標準`sqlite3`モジュールを直接使用)の方針と整合しない。また本サンドボックスはpypi.orgに接続できず、追加パッケージを導入できない(`docs/P101-impl-context.md`)。

#### CR-002の対処(`duplicate column name`の捕捉)を継続する

却下。理由: 上記「理由」節のとおり、「1ファイル1文」という明文化されていない慣習に依存しており、その慣習が破れたときに沈黙して壊れる。

#### マイグレーションを冪等に書くことを規約とする(適用前に`PRAGMA table_info`で存在確認する等)

却下。理由: SQLファイル単体では条件分岐が書けないため、結局アプリケーション側に判定ロジックが必要になる。同じ判定ロジックを書くなら、適用済み状態を明示的に記録する方が運用時の確認可能性が高い。
