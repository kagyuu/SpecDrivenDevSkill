# Spec-Driven Dev Skill Ver0.5 → Ver0.6 改訂レポート

作成日: 2026-08-04

## 経緯

V0.5に対し、`V0.5_testbed`(`V0.4_testbed`を土台に、Skillだけを V0.5 に差し替えたテストヘッド)で差分実地検証を行った(詳細は `V0.5_testbed/e2e-validation-report.md` および `V0.5_testbed/testbed.md` を参照)。この検証では、V0.4で指摘された26件の不備のうち24件が明確に解消(✅合格)、2件が「概ね合格だが留保あり」と判定され、**致命的にV0.5でも未解決の重大な不備は無い**ことが確認された。

一方で、この検証の過程でV0.5に**新たに2件**の問題が見つかった(`V0.5_testbed/e2e-validation-report.md`「3. V0.5で新たに見つかった問題」)。V0.6は、この2件への対応を主眼とする改訂である。V0.5と比べて変更の規模は小さいが、いずれも「実際にCRを1件処理してみて初めて表面化した」種類の問題であり、机上のレビューでは見つからなかったものである。

あわせて、V0.5まで「人間の判断に委ねる」として持ち越されていた3件の設計論点について、**人間の判断により「対処しない」と正式に決定された**。その決定と理由を本レポートに記録する(後述「3. 人間の判断により対処しないと決定した論点」)。

以下、`V0.5_testbed/e2e-validation-report.md` の項番に対応させて記載する。

## 1. 新たに見つかった問題への対応

### 1-1. P904の完了CR記法が「残す/削除する」の二値を前提にしており、実運用で生まれる記法を言い当てられていない — 重大度: 低 への対応

* **事象**: `SKILL-P904-cr-verify.md` は、完了したCRを `docs/CR.md` から「削除するか残すか」の二値で規定し、慣習が無い場合のデフォルトを「残す」としていた。しかし `V0.5_testbed` で実際に確立していた記法は、そのどちらでもない**第三の形式**(CR一覧の表からは除き、表の下に `docs/cr-records/` へのリンクを1行残す)だった。V0.5の文言を字面どおり「残す」「削除する」の二択と読んだ別のAgentが、CRへの参照ごと消してしまう/表に行を残したままにする、という2方向のブレを起こしうる状態だった。

* **本改訂で追加で判明した根本原因**: V0.5の検証レポートは「P904の文言が二値である」ことを指摘していたが、本改訂で該当ファイル群を精査した結果、**より根本的な原因として `TEMPLATE-CR.md` と `SKILL-P904-cr-verify.md` が正面から矛盾していた**ことが判明した。
  * `TEMPLATE-CR.md` 冒頭: 「対応が完了したCRは、本文を `docs/cr-records/CR-{番号}.md` に退避し、この `CR.md` の**一覧・本文からは削除する**」
  * `TEMPLATE-CR.md`「対処内容」欄: 「…本CR全体を退避し、`CR.md` からは**削除する**」
  * `SKILL-P904-cr-verify.md`: 慣習が無い場合のデフォルトは「完了行は一覧表・本文とも**削除せず残す**」
  * つまり、テンプレート側は「削除」、フェーズ指示側は「残す」と指示していた。実行担当が両方を満たそうとして「本文と表の行は削除するが、リンクは残す」という第三の形式に落ち着いたものと考えられる。V0.5_testbedで観測された「第三の形式」は、Agentの逸脱ではなく**矛盾した指示に対する合理的な折衷**だった。

* **V0.6での変更**:
  * `SKILL-P904-cr-verify.md` の当該規定を、二値の選択ではなく**手順ベースの指示**に全面的に書き換えた。
    * 2件目以降のCR処理では、「直近の完了済みCRが実際にどう記載されているかを `docs/CR.md` の現物で確認し、その記載形式をそのまま複製する」ことを指示し、「自分の解釈で『残す/削除する』のどちらかに寄せ直してはならない」と明記した。あわせて、確認すべき3点(表に行が残っているか/表とは別に参照リンクが置かれているか、その書式/本文が残っているか)を列挙した。
    * 初回CR処理時のデフォルトを、実運用で有効に機能した**第三の形式そのもの**に変更した(本文は `docs/cr-records/` に退避して `CR.md` からは削除、一覧表からは完了行を除きプレースホルダ行を残す、表の直後に完了CRへのリンクを1件1行で並べる)。具体的なMarkdownの書式例も併記した。
  * `TEMPLATE-CR.md` の矛盾していた2箇所(冒頭の説明文、「対処内容」欄の指示)を、上記の手順と整合する記述に修正し、詳細な手順は `SKILL-P904-cr-verify.md` を参照する形に一本化した。これにより、テンプレートとフェーズ指示の二重管理による矛盾の再発を防ぐ。

### 1-2. CRによるデータモデル変更時のマイグレーション冪等性について、Skillに指針が無い — 重大度: 中 への対応

* **事象**: `V0.5_testbed` のマイグレーション基盤は、アプリ起動のたびに `migrations/*.sql` を全件再実行する設計であり、初期構築時は `CREATE TABLE IF NOT EXISTS` のみだったため冪等に成功していた。ところがCR-002でカラム追加(`ALTER TABLE ROOMS ADD COLUMN description TEXT`)が必要になった際、SQLiteの `ALTER TABLE ADD COLUMN` には条件付き実行の構文が無いため、素朴に追加すると2回目以降の起動が `duplicate column name` で失敗し、**アプリが起動しなくなる**ことが判明した。V0.5にはこの種の非冪等DDLに対する指針が、`SKILL-P003-backend-spec.md`(データモデル定義)にも `SKILL-P903-refactor-execute.md`(データモデル変更カテゴリ)にも無かった。
* この問題は、テストごとに独立した一時DBを作る単体テスト・結合テストでは**構造的に検出できない**(常に初回実行になるため)一方、実運用の再起動シナリオでは確実に踏む、という検出困難性を持つ点が特に問題である。

* **V0.6での変更**: 単一箇所の追記ではなく、「設計時に方針を決める」「テスト計画に観点として載せる」「CR適用時に確認する」「納品時に確認する」の4点で捉えるよう、4ファイルに追記した。
  * `SKILL-P003-backend-spec.md`(設計時): データモデルを定義する際に**スキーマの適用方式(マイグレーション方式)を必ず明記する**ルールを追加した。記載すべき3点(適用のタイミングと方式/その方式が冪等かどうか/冪等でない場合の担保方法)を列挙し、特に「全件再実行」方式について、「初回構築時は `CREATE TABLE IF NOT EXISTS` だけで構成されるため冪等に見えるが、後からCRでカラム追加が発生した時点で破綻するため、**データモデルを最初に定義するP003の時点で決めておく必要がある**」と、この問題の本質(先送りすると手遅れになる)を明記した。冪等化の具体的手段(バージョン管理テーブルによる差分適用、適用済みエラーの捕捉)も例示した。
  * `SKILL-P006-test-plan.md`(テスト計画時): 非機能観点の並びに「運用観点(再起動耐性)」を追加し、データストアを持つ場合は「アプリケーションを停止・再起動しても正常に起動すること」を確認する観点を必ず含めるよう指示した。あわせて、この観点が単体テスト・結合テストでは検出できない理由を明記し、独立した観点として明示するよう求めた。
  * `SKILL-P903-refactor-execute.md`(CR適用時): CRスコープ決定の手順に、「データモデル変更」カテゴリに該当する場合の**必須確認**を追加した。P003記載のマイグレーション方式の確認(記載が無ければコードを読んで特定しP003に追記)、非冪等DDLを追加する場合の再起動可否の確認、冪等でない場合は冪等化自体もCRの対応範囲に含めること、および「**実際に初期化処理を2回連続で実行し、2回目も成功すること**をもって確認とし、結果をテスト記録に残す」という具体的な検証手順を定めた。
  * `SKILL-P302-deliver.md`(納品時): 「実行前チェック」に項目8として再起動時の起動可否(初期化処理の冪等性)を追加し、判定にも「2回目が失敗する場合は不具合として扱い、冪等化を行ってから本フェーズを完了とする」「実行環境の制約で確認できない場合はその旨を未整備事項に明記する」を追加した。既存の項目7(デプロイトポロジー整合性)と同じ扱い(黙って納品しない)に揃えている。

## 2. V0.5の検証で「留保あり」とされた項目の扱い

`V0.5_testbed/e2e-validation-report.md` は、26件中2件を「⚠️ 概ね合格」と判定していた。その扱いは次のとおり。

* **3-11(P904の完了行表記)**: 上記 1-1 で対応済み。
* **3-8(P007目次の技術スタック名ハードコードが、既存の生成済みドキュメントには遡及しない)**: **V0.6では対応しない**。検証レポート自身が「V0.5の欠陥ではなく、Skillという仕組みの当然の限界」と整理しているとおり、Skillのルール変更が既に生成済みのドキュメントを自動的に書き換えることはない(そのドキュメントを再生成するフェーズを実際に再実行しない限り起こらない)。これをSkill側の仕組みで解決しようとすると「既存の全ドキュメントを毎回スキャンして現行ルールとの差分を検出する」といった重い仕組みが必要になり、費用対効果が見合わない。人間が必要と判断した時点で、該当フェーズを対象に含めたCRを1件起票すれば足りる。
* **1-6(P302のデプロイトポロジー確認)**: V0.5では「✅合格(ただし確度の割引あり)」と判定された。これは記述自体は妥当だが、「トポロジーを実際に壊した状態から検出できるか」までは検証していなかったためである。**V0.6ではSkillの記述は変更せず、代わりに `V0.6_testbed` で実際に動的検証を行う**方針とした(結果は `V0.6_testbed/e2e-validation-report.md` を参照)。

## 3. 人間の判断により対処しないと決定した論点

V0.5まで「部分的な緩和にとどめ、設計そのものの再検討は次バージョンの検討課題として人間に判断を委ねる」としていた次の3件について、**人間の判断により「対処しない(現状の部分的緩和のまま確定させる)」と決定された**。V0.6以降、これらを再び「検討課題」として持ち越すことはしない。

| 論点 | 内容 | 対処しないと判断した理由 |
|---|---|---|
| 1-3 | P008のテストIDとP102の実装命名の対応づけを、構造的に保証する仕組み | **自動検証は複雑化し破綻しやすい**ため |
| 2-5 | 1根本原因・多テスト波及時の、修正指示ファイルの粒度の形式的基準 | **形式化はAIが苦手で誤判定が増える**ため |
| 1-5 | P903のCRスコープ判断を自動分類する仕組み(影響分析エンジン) | **影響分析エンジンは破綻リスクが高い**ため |

この判断は、`V0.5_testbed` のCR-002実地検証の結果とも整合している。同検証では、3件いずれについてもV0.5の「部分的な緩和」が実務上は十分に機能することが確認されていた(1-3: P102のインプットにP008を追加しただけで命名の厳密一致を実際に達成、2-5: 条件付きの例外規定だけで複数テスト1ファイルの運用を実際に達成、1-5: 目安の対応表と「理由を記録する」義務だけで複合カテゴリのCRのスコープ判断を実際に達成)。

これら3件に共通するのは、いずれも「AIの判断を、機械的なルールや自動化された仕組みで置き換えようとする」方向の改善案だという点である。今回の判断は、**この方向には進まず、判断そのものはAIに委ねたうえで、その判断結果を人間が後から検証できるように「記録を残させる」方向を採る**という、本Skillの設計方針の確定を意味する。V0.5までに導入済みの各規定(スコープ決定の対象/対象外+理由の記録義務、複数テスト1ファイルの条件付き許可、命名一致の指示)は、いずれもこの方針に沿ったものである。

## 4. V0.6で変更しなかった点

`V0.5_testbed/e2e-validation-report.md` で✅合格と判定された24件については、V0.5の記述をそのまま維持している。特に、CR-002の実地処理を通じて実際に機能することが確認された次の仕組みは、有効に働いた実績があるため一切変更していない。

* P903のCRスコープ決定表と「対象/対象外+理由」の記録義務(1-5)
* P202の「複数テスト1根本原因」例外規定(2-5)
* P102のインプットへのP008追加と命名厳密一致の指示(1-3)
* P901の影響度×緊急度ルーブリック(3-10)
* ★FIXME★のインライン配置ルール(2-1)
* `TEMPLATE-test-record.md` によるテスト記録形式の統一(2-2)
* P902のバックアップファイル名へのCR番号付与(2-9)
* ステップ0の再開判定におけるP904/P905の考慮(2-8)
* P905の判定結果の記録先定義(2-7)

また、`V0.5_testbed/testbed.md`「件数についての注記」が指摘していた件数の不一致(V0.4のレポートが冒頭で「23件」としながら本文では26件を列挙している、V0.5のreview-reportの重大度内訳がヘッダの合計と一致しない)は、過去バージョンのレポート文書の数え間違いであり、Skillの動作には影響しない。過去の記録を遡って書き換えることはせず、本レポート以降は実際の列挙件数に一致する数を記載する方針とする。

## 5. V0.6_testbedでの検証後に行った修正

`V0.6_testbed` での検証(詳細は `V0.6_testbed/e2e-validation-report.md`)により、上記 1-1 の改訂に**編集漏れが1件**あることが判明したため、検証後に修正した。

* `SKILL-P904-cr-verify.md` の「アウトプット文書」節に、V0.5時点の二値の記述(「対応が完了したCRを削除、または状態を更新」)がそのまま残っており、同じファイルの本文で新たに定めた手順ベースの指示と矛盾していた。同節を、本文の手順を参照する記述に修正した。
* これは1-1で解消したはずの「二値前提」がファイル内に残存していたものであり、V0.6の改訂そのものの欠陥である。検証で実際に機能が確認された本文の手順自体には変更を加えていないため、本修正によって `V0.6_testbed` の検証結果が無効になることはない。

なお、同検証では他に2件の指摘(P903の冪等性確認基準が必要条件にとどまり十分条件として書かれている件、`docs/CR.md` 冒頭の説明文が旧テンプレート由来のまま残り現行の記法と食い違う件)が出ているが、これらは編集漏れではなく設計判断を伴う指摘であるため、V0.6には反映せず、次バージョンの検討事項として `V0.6_testbed/e2e-validation-report.md`「V0.6で新たに見つかった問題」に記録している。

## 6. 今回あえて反映しなかった判断

* **マイグレーション方式そのものの標準化はしない**。V0.6が求めるのは「方式を明記すること」「非冪等な場合に冪等化の手段を決めること」「実際に2回実行して確認すること」であって、「バージョン管理テーブルを必ず導入せよ」といった特定方式の強制はしていない。対象プロジェクトの規模・採用技術によって適切な方式は変わるためであり、これは上記3節で確定した設計方針(判断はAIに委ね、記録と検証を義務づける)とも一致する。
* **`docs/CR.md` の記法をテンプレートで機械的に固定することはしない**。1-1では初回のデフォルト形式を具体化したが、2件目以降は「既存の記法を現物で確認して複製する」という手順を優先させている。プロジェクトごとに記法が育つこと自体は許容し、Skillはその一貫性の維持だけを保証する立場を採る。
