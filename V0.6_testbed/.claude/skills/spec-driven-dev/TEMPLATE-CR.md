# CR.md

本プロジェクトに対して人間から出された、未対応または対応中の変更要求(Change Request)を管理する。
対応が完了したCRは、本文を `docs/cr-records/CR-{番号}.md` に退避し、この `CR.md` からは本文と一覧表の行を除いたうえで、表の下に `docs/cr-records/` へのリンクを1行残す(具体的な手順と書式は `SKILL-P904-cr-verify.md` を参照)。

* 1件の要望 = 1つの CR-NNN とする。複数の要望が混ざっている場合は分割する。
* 「変更内容」は、Refactorステップ(P901〜P905)でAIがP002〜P302を再実行する際にそのまま読み込める程度に、具体的かつ簡潔に書く。
* CRは仕様そのものではない。CRにもとづいて更新されるのは `docs/P001-requirement.md` 以降の各設計書であり、CR自体は「何をなぜ変えてほしいか」の記録として残る。

## CR 一覧

| CR | タイトル | 状態 | 優先度 |
| --- | --- | --- | --- |
| CR-001 | (例) 予約のキャンセル機能を追加してほしい | 未対応 | 中 |

状態は次のいずれかを取る。

```text
未対応     まだ着手していない
対応中     P903 修正実施を実行中
反映確認中  P904 で設計・実装への反映を確認している
完了       反映確認が済み、docs/cr-records/ へ退避済み
却下       対応しないことが決まった(理由をCR本文に残す)
```

優先度は次のいずれかを取る。

```text
高   次のRefactor実行で最優先に対応する
中   通常どおり対応する
低   他の対応に余裕があれば対応する
```

## CR-001

### タイトル

(例) 予約のキャンセル機能を追加してほしい

### 状態

未対応

### 優先度

中

### 起票日

YYYY-MM-DD

### 起票者

(人間の名前、または「利用者からのフィードバック」などの出所。具体的には例えば以下のような特定方法がある。判明している範囲で具体的に書く。)

* 依頼者の氏名・役職(例: 「山田太郎(業務部門責任者)」)
* 起票の元になったチケット・issueへのリンク(例: 「Jira: PROJ-123」「GitHub Issue #45」)
* 打ち合わせ・レビューの議事録への参照(例: 「2026-08-03 定例会議事録 3節」)
* 問い合わせ窓口・サポートチケットの参照番号
* 上記が特定できない場合は「利用者からのフィードバック(詳細不明)」のように、不明である旨を明記する(出所不明のまま書かない)

### 背景・課題

* なぜこの変更が必要か。現状どのような困りごとがあるか。

### 変更要求の内容

* 何をどう変えてほしいか。画面・API・データモデル・非機能要件のうち、どこに関わる変更かを具体的に書く。
* 対応する既存の仕様箇所があれば、`docs/P00N-*.md` の該当箇所を明記する。

### 期待する振る舞い

* 変更後、どのような入力に対してどのような結果になっていればよいか(受け入れ条件)。

### 影響が想定される範囲

* 画面: ...
* API: ...
* データモデル: ...
* 関連ADR: (あれば ADR-NNN を記載)

### 対処内容(P903〜P904で追記)

* 実際にどのフェーズ(P002〜P302)を再実行し、どのドキュメント・コードを変更したか。
* 完了後、この節と状態欄を埋めたうえで `docs/cr-records/CR-001.md` に本CR全体を退避する。`CR.md` 側の反映方法(本文の削除・一覧表からの除去・完了CRへのリンクの残し方)は `SKILL-P904-cr-verify.md` の手順に従う。

### 備考

なし
