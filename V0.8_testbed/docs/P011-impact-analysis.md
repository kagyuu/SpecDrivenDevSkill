# 影響分析(設計書横断レビュー起因) — 会議室予約システム

> 本書は `spec-driven-dev` Skill フェーズP011の成果物です。`docs/P010-design-review.md`(1回目)で列挙された矛盾点4件それぞれの修正方針を整理します。修正そのものはP012で行います。

## 矛盾点 #1

- 概要: フロントエンドのテスト実行コマンド `node --test tests/*.test.tsx` が、TypeScript+JSXのトランスフォーム手段の指定なしに23箇所以上で使われている。Node.js標準テストランナーは `.tsx` を単体で解釈できない。
- 修正すべき文書と箇所: `docs/P006-test-plan.md` 5章(テストフレームワークの決め事)、`docs/P007-impl-direction/U001-foundation-and-auth.md` U001-T1(依存関係追加)、`docs/P007-impl-direction/U001〜U005-*.md` の全「実行コマンド」節、`docs/P008-test-direction/T0NN-*.md` の全「実行コマンド」節。
- どちらの記述を正とすべきか(判断とその理由): 新たに「`tsx`パッケージ(npm、TypeScript+JSXをNode.jsのESMローダーとして解決するツール)を導入し、`node --import tsx --test` の形で実行する」という方針を採用する。理由: `docs/P002-frontend-spec.md` 0章で確定したReact+TS+Viteのスタックを維持したまま(スタック変更は行わず)、`docs/P006-test-plan.md` が既に選定している「フロントエンドは`node --test`」という方針も維持できる、最小の追加で解決できる手段であるため。Vitest等の専用テストランナーへの乗り換えも代替案として検討したが、`docs/P006-test-plan.md` 5章で既に`node --test`采用が確定しており、この方針自体を覆す矛盾は本来存在しない(欠けているのはローダー指定のみ)ため、既存方針を維持したまま最小修正する方が影響範囲が小さい。
- 波及して確認・修正が必要になる他の文書・箇所: `docs/P009-acceptance-direction/A0NN-*.md` のうちクライアント側テストを持つもの(A001〜A004, A006, A010, A011)は `.js`(Playwright等によるブラウザ操作、`.tsx`をNode側で直接importしない)であるためローダー指定は不要。ただし `docs/P006-test-plan.md` にこの区別(P008は`.tsx`+ローダー必須、P009クライアント側は`.js`+ブラウザ操作でローダー不要)を明記し、今後の検証で再度この違いが「不統一」として指摘されないようにする。
- 修正の優先度: 高(記載どおりに実行すると即座に失敗するため)

## 矛盾点 #2

- 概要: `docs/P002-frontend-spec.md` 内で予約の時刻表現が、`GET /api/reservations`(4.6節)は結合ISO8601、他のreservations系エンドポイント(4.7〜4.9.1節)は分割 `date`/`start_time`/`end_time` と不統一で、理由の説明が無い。
- 修正すべき文書と箇所: `docs/P002-frontend-spec.md` 4章冒頭(4.6節の直前)。
- どちらの記述を正とすべきか(判断とその理由): どちらかに統一するのではなく、**現状の使い分けを維持したまま、使い分けの理由を明記する**。理由: `GET /api/reservations`はカレンダーグリッド描画(会議室×時間帯のセル配置)に使われ、連続的な日時軸上での比較が必要なため結合ISO8601が扱いやすい。一方、作成・編集フォーム(S03/S04)は「日付」「開始時刻」「終了時刻」という個別の入力欄を持つため、フォームの値とAPIのフィールドが1対1対応する分割形式の方が実装上素直である。両者を無理に統一すると、いずれか一方の呼び出し元(カレンダー側またはフォーム側)で変換処理が増えるだけであり、統一の実益より使い分けを説明する方が合理的と判断した。
- 波及して確認・修正が必要になる他の文書・箇所: `docs/P003-backend-spec.md` 4.6〜4.9.2節(内部実現)は既にDB上は`start_datetime`/`end_datetime`で保持し、APIごとに変換していることが読み取れるが、この変換方針(フォーム系は分割、一覧系は結合)を明記する一文を追加する。`docs/P007-impl-direction/U003-reservation-core-and-calendar.md`・`U004-reservation-detail-and-mylist.md` のタスク内容自体は変更不要(既にそれぞれのAPI形式どおりに実装する指示になっている)。
- 修正の優先度: 中

## 矛盾点 #3

- 概要: `GET /api/users/directory` の外部契約(パス・リクエスト・レスポンス形式)が、外部契約を確定する役割のP002ではなく、内部実現を確定する役割のP003で定義されている。
- 修正すべき文書と箇所: `docs/P002-frontend-spec.md` 4.10節(現状「確定はP003に委譲する」という仮決めのまま止まっている箇所)を、外部契約の確定箇所として書き換える。`docs/P003-backend-spec.md` 4.10節は、確定済みの外部契約(P002参照)を前提に、内部の認可判定(ログイン済みなら誰でも可、という認可方針)のみを記載する形に修正する。
- どちらの記述を正とすべきか(判断とその理由): レスポンス形式・エンドポイントパス自体はP003 4.10節に既に具体的に書かれている内容(`GET /api/users/directory`、`[{ "employee_id": string, "name": string }]`)をそのまま採用し、記載場所のみをP002に移す。内容自体に矛盾は無く、置き場所の役割違反のみが問題であるため。
- 波及して確認・修正が必要になる他の文書・箇所: `docs/P004-traceability-matrix.md` 4章(過剰実装の確認表)は「`docs/P003-backend-spec.md` 4.10節」を出典として記載しているため、修正後は「`docs/P002-frontend-spec.md` 4.10節(外部契約)/`docs/P003-backend-spec.md` 4.10節(内部認可方針)」という形に更新する。`docs/P007-impl-direction/U003-reservation-core-and-calendar.md` U003-T3の「参照すべき仕様箇所」に `docs/P003-backend-spec.md` 4.10節とあるが、これも参照先をP002に揃える(外部契約はP002、認可方針の詳細はP003という2箇所参照に変更)。
- 修正の優先度: 中
