# ADR.md

本プロジェクトで現在有効な設計判断を管理する。
過去に廃止された設計判断は `ADR_master.md` に移動する(本バージョンでは廃止されたADRはまだ無いため、`ADR_master.md` は作成していない)。

* 1つの決定 = 1つの ADR-NNN とする。
* 「決定内容」「理由」は、後続のAI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。長い経緯や検討の過程そのものは書かず、結論とその根拠だけを残す。
* 状態が「廃止」になったADRは、本文を `ADR_master.md` に移し、この `ADR.md` の一覧・本文からは削除する。`ADR_master.md` 側には、廃止日と廃止理由(何のADRに置き換えられたか)を追記する。

状態は次のいずれかを取る。

```text
採用     現在この決定が有効である
検討中   採用未確定だが記録している
廃止     過去に採用されたが現在は無効(本文はADR_master.mdへ移動済み)
```

## ADR-001

### タイトル

フロントエンド技術スタックとしてReact 18 + TypeScript + Viteを採用する

### 状態

採用

### 日付

2026-08-09

### 関連要求

* REQ-SCREEN-001〜007(`docs/P004-traceability-matrix.md` 1章、全画面)

### 背景

社内向け会議室予約システムを構築する。カレンダーグリッドのようなインタラクティブなUIが必要であり、`docs/P001-requirement.md` はReact + TypeScript + Viteを指定している。P002実行時点でnpmレジストリ(`registry.npmjs.org`)への到達を実際に確認できたため、パッケージ取得を前提にした技術選定が可能と判断した。

### 決定内容

フロントエンドはReact 18 + TypeScript + Viteを採用する。状態管理はReact標準(useState/useContext)のみを用い、Redux等の外部状態管理ライブラリは導入しない。ルーティングは`react-router-dom`を使う。

### 理由

* SPA(カレンダーのようなインタラクティブなUI)構築の実績が豊富
* コンポーネント分割による画面再利用性が高い
* 画面数が7画面と少なく、専用状態管理ライブラリを導入するほどの複雑さが無い

### 検討した代替案

#### Starlette配信のプレーンHTML + ESモジュールJS(`V0.7_testbed`方式)

却下。理由: `V0.7_testbed`ではサンドボックス環境がnpm/pypiレジストリに到達できずやむを得ず採用した代替構成だったが、本バージョン(V0.8)ではネットワーク接続を実際に確認できたため、この制約は存在しない。`docs/P001-requirement.md`が指定する本来の技術スタックを採用できる。

#### Redux等の外部状態管理ライブラリ

却下。理由: 画面数(7画面)・状態の複雑さの規模では、Reactの標準機能(useState/useContext)で十分に対応でき、追加の依存・学習コストに見合わない。

### 残存リスク

なし(現状の要件範囲では)。将来的に画面数・状態の複雑さが大きく増える場合は、状態管理ライブラリの導入を再検討する。

### 影響範囲

* Frontend

### 関連成果物

* `docs/P002-frontend-spec.md`
* `docs/P007-impl-direction.md`

### 備考

なし

## ADR-002

### タイトル

バックエンド技術スタック・データストアとしてFastAPI + SQLiteを採用する

### 状態

採用

### 日付

2026-08-09

### 関連要求

* REQ-API-001〜017(`docs/P004-traceability-matrix.md` 2章、全API)
* REQ-NFR-004(スケーラビリティ)、REQ-NFR-005(想定同時利用者数)

### 背景

`docs/P001-requirement.md` はPython + FastAPI、データストアSQLiteを指定している。想定規模は従業員300名程度・会議室10室・同時接続30程度であり、大規模なスケーラビリティは要求されていない。

### 決定内容

バックエンドはPython + FastAPIを採用する。データストアはSQLite(stdlib `sqlite3`)を採用する。

### 理由

* 型ヒントベースの実装で仕様との整合を取りやすい
* OpenAPI仕様が自動生成されフロントエンドとのAPI契約を明確化しやすい
* 予約の重複チェックなどの業務ロジックをテストしやすい
* 想定規模(300名、同時30接続)では単一サーバー・組み込みDBで要件を満たせる

### 検討した代替案

#### PostgreSQL等の外部DBサーバ

却下。理由: 想定規模に対して運用コスト(サーバー管理、接続プール等)が見合わない。SQLiteの単一ファイル構成で要件(可用性99%、同時30接続)を満たせると判断した。

### 残存リスク

SQLiteは複数プロセス・複数ホストでの水平スケールに適さない(書き込みロックが単一ファイル単位のため)。将来的な多拠点展開等でユーザー数・同時接続数が大幅に増える場合は、外部DBサーバへの移行をCRとして検討する必要がある(`docs/P003-backend-spec.md` 5章参照)。

### 影響範囲

* Backend
* Database

### 関連成果物

* `docs/P003-backend-spec.md`
* `docs/P007-impl-direction.md`

### 備考

なし

## ADR-003

### タイトル

認証方式としてCookieベースのサーバーサイドセッションを採用する(JWT不採用)

### 状態

採用

### 日付

2026-08-09

### 関連要求

* REQ-NFR-003(セキュリティ)

### 背景

`docs/P001-requirement.md` は「社内アカウント(ID/パスワード)によるログインを必須とする」とのみ規定しており、認証方式(セッション/JWT等)の詳細は次フェーズ(P002/P003)での確定が明記されていた。管理者によるユーザー無効化時に、そのユーザーの全セッションを即座に失効させる必要がある(`docs/P002-frontend-spec.md` 3.7節、`docs/P003-backend-spec.md` 4.11〜4.11.2節)。

### 決定内容

ログイン成功時にサーバーがセッションを発行し、`session_id`をHttpOnly Cookie(`SameSite=Lax`、8時間固定有効期限)としてブラウザに渡す。セッションはサーバー側の`sessions`テーブル(SQLite)で管理する(自己完結トークンではない)。パスワードは`hashlib.scrypt`でハッシュ化して保存する。

### 理由

* 即時ログアウト・強制失効(ユーザー無効化時の全セッション削除)をシンプルに実現できる
* セッションストアがDBテーブルであるため、アプリケーション再起動後もログイン状態が失われない(可用性・運用性の観点でも有利)

### 検討した代替案

#### JWT(自己完結トークン)

却下。理由: 即時失効(ログアウト、ユーザー無効化時の強制失効)を実現するには結局ブラックリストをDBまたはキャッシュで管理する必要があり、セッションテーブル方式と比べて実装が二重化するだけで単純化に寄与しない。

#### セッション有効期限のスライド延長方式

却下(固定8時間に対する代替として検討)。理由: 実装・テストの複雑さに対し、本アプリの利用シーン(社内勤務時間中の利用が中心)では固定8時間で十分と判断した。

### 残存リスク

セッションテーブルへの問い合わせがリクエストごとに発生する(想定規模: 300ユーザー・同時30接続程度では性能上の懸念は小さいと判断)。8時間を超える連続作業中にセッション切れが発生し得るが、再ログインで復帰可能であり業務影響は小さいと判断する。

### 影響範囲

* Backend
* Frontend(Cookie送受信)
* Security

### 関連成果物

* `docs/P002-frontend-spec.md`(2章)
* `docs/P003-backend-spec.md`(1.2節)

### 備考

なし

## ADR-004

### タイトル

マイグレーション方式としてバージョン管理テーブルによる差分適用を採用する

### 状態

採用

### 日付

2026-08-09

### 関連要求

* REQ-NFR-002(可用性)

### 背景

データストア(SQLite)を持つため、アプリケーションを停止・再起動しても正常に起動する必要がある。SQLiteの`ALTER TABLE ... ADD COLUMN`等は`IF NOT EXISTS`相当の条件付き構文を持たないため、初期スキーマが`CREATE TABLE IF NOT EXISTS`だけで構成される「全件再実行方式」は、将来カラム追加等のマイグレーションが発生した時点で2回目以降の起動が`duplicate column name`エラーで失敗する。

### 決定内容

アプリケーション起動時に`migrations/`配下の`NNN_description.sql`を番号順に確認し、`schema_migrations`テーブルに未記録のものだけをトランザクション内で適用する。マイグレーション適用と`schema_migrations`へのINSERTは同一トランザクションで行う。

### 理由

* `schema_migrations`による明示的な適用済み管理により、将来`ALTER TABLE`を含むマイグレーションが追加されても2回目以降の起動で失敗しない
* 外部マイグレーションツールを導入せずstdlib `sqlite3`だけで実現でき、依存が増えない

### 検討した代替案

#### 全件再実行方式(`CREATE TABLE IF NOT EXISTS`のみに依存)

却下。理由: 初回構築時は冪等に見えるが、将来`ALTER TABLE`を要するマイグレーションが追加された時点で破綻する(`docs/P003-backend-spec.md` 3章参照)。

#### 外部マイグレーションツール(Alembic等)の導入

却下。理由: テーブル数が6個と少なく、自前のバージョン管理テーブル方式で十分であり、追加の依存・学習コストに見合わない。

### 残存リスク

なし。この方式の冪等性は`docs/P006-test-plan.md` 4章・`docs/P009-acceptance-direction/A009-restart-resilience.md`の再起動耐性テストで実地検証する。

### 影響範囲

* Backend
* Database
* Ops(再起動耐性)

### 関連成果物

* `docs/P003-backend-spec.md`(3章)
* `docs/P006-test-plan.md`(4章)
* `docs/P009-acceptance-direction/A009-restart-resilience.md`

### 備考

なし
