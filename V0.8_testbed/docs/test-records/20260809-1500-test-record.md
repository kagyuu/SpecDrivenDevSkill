## T006: 予約作成成功

- 実行日時: 2026-08-09
- 実行者: Claude (Executor)
- 対象ブランチ/コミット: (未コミット、作業ツリー)
- 参照したテスト指示: docs/P008-test-direction/T006-reservation-create-success.md
- 実行環境: 上記共通
- 事前ビルド結果: 成功
- 実行コマンド: `cd client && node --import tsx --test tests/integration/reservationCreateSuccess.test.tsx`
- 結果: **FAIL**
- 期待結果: 手順2: S02へ遷移後、翌営業日のセルに「週次定例会議」(予約者名付き)が表示される
- 実際の結果: 手順1(登録)・手順3(DB確認、`title='週次定例会議', attendee_count=5`の行が存在)は成功。手順2で失敗: S02(CalendarPage)は既定で当日を表示するため、翌営業日のセルを見るには「次へ」ボタンを1回押す必要があるが、押しても表示日付(画面上の日付表示・グリッド内容)が変化せず、翌営業日のセルに到達できない。`screen.findAllByRole('button', { name: /週次定例会議/ })` がタイムアウトする。
- 失敗ログ抜粋:
  ```
  Error: Unable to find role="button" and name `/週次定例会議/`
  ```
- 再現手順: **根本原因を特定済み。** `client/src/pages/CalendarPage.tsx` の `addDays()` がタイムゾーン依存のバグを持つ。
  ```js
  function addDays(isoDate, days) {
    const date = new Date(`${isoDate}T00:00:00`) // ローカル時刻(JST)の午前0時として解釈される
    date.setDate(date.getDate() + days)
    return date.toISOString().slice(0, 10)       // UTCの日付文字列に変換される
  }
  ```
  `todayIsoDate()` は `new Date().toISOString().slice(0,10)` でUTC基準の日付文字列を返す。Asia/Tokyo(UTC+9)環境で現在時刻がUTCで08:00〜23:59(JSTで17:00〜翌08:59)の間、`addDays(today, 1)` を計算すると、ローカル午前0時として解釈された日付にUTC変換の際のオフセットが吸収され、**入力と同じ日付文字列を返してしまう**(実測: 2026-08-08T18:23 UTC時点で `addDays("2026-08-08", 1)` → `"2026-08-08"`、変化なし)。Reactは同一の文字列でstateを更新してもバッチ内で再レンダリングをスキップしないが、`date` stateの値自体が変わらないため `useEffect` の依存配列 `[date, selectedRoomIds]` が変化したと判定されず、`GET /api/reservations` が新しい日付で再実行されない。結果、「次へ」ボタンを押しても表示が当日のまま止まる。
  再現コマンド:
  ```js
  node -e "
  function addDays(isoDate, days) { const dt = new Date(isoDate + 'T00:00:00'); dt.setDate(dt.getDate()+days); return dt.toISOString().slice(0,10);}
  console.log(addDays(new Date().toISOString().slice(0,10), 1));
  "
  ```
- 影響がありそうなモジュール: `client/src/pages/CalendarPage.tsx`(`todayIsoDate`/`addDays`)。同じ関数パターンは他ページでは使われていないが、この画面の日付ナビゲーション(「前へ」「次へ」)全体が、実行環境のタイムゾーンと時刻次第で断続的に効かなくなる。UTCから離れたタイムゾーン(特にUTCより進んでいる地域、日本を含む)ほど発生しやすい。
- テスト指示との矛盾の疑い: なし(テスト指示・実装とも翌営業日の予約を前提としており妥当。バグは実装側)
- 次工程への申し送り: P202(修正計画)へ。`addDays`/`todayIsoDate` を、日付文字列をローカル時刻経由でDateオブジェクト化せず、文字列operationまたはUTC基準の`Date.UTC(...)`で計算するよう修正が必要。

## T009: カレンダー画面での予約一覧表示

- 実行日時: 2026-08-09
- 実行者: Claude (Executor)
- 対象ブランチ/コミット: (未コミット、作業ツリー)
- 参照したテスト指示: docs/P008-test-direction/T009-calendar-list-display.md
- 実行環境: 上記共通
- 事前ビルド結果: 成功
- 実行コマンド: `cd client && node --import tsx --test tests/integration/calendarListDisplay.test.tsx`
- 結果: **FAIL**
- 期待結果: 手順2: 該当会議室列の10:00-10:30・10:30-11:00両セルに「週次定例会議」表示、参加予定人数は非表示
- 実際の結果: **4回連続でFAIL(再現性あり)。** グリッドに会議室列自体が1つも表示されず(時間帯の行のみ)、予約セルが見つからない。原因はT006とは別。サーバー側で `GET /api/rooms` または `GET /api/me` が500を返していた(下記参照)。★テスト指示自体は「T006の予約(翌営業日)」を前提とするが、T006で判明した`addDays`不具合を本テストで重複して踏まないよう、予約日を「当日」に差し替えて実施した(会議室フィルタ・セル表示自体の検証がこのテストの主目的であり、日付ナビゲーション自体はT006が担当するため)。当日データに差し替えても本FAILは解消しなかった。
- 失敗ログ抜粋:
  ```
  {"timestamp": "2026-08-08T18:28:27.934992+00:00", "level": "ERROR", "event": "unhandled_exception", "path": "/api/reservations", "error_type": "ProgrammingError"}
  INFO:     127.0.0.1:56972 - "GET /api/reservations?date_from=2026-08-08&date_to=2026-08-08 HTTP/1.1" 500 Internal Server Error
  sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread. The object was created in thread id 39440 and this is thread id 56008.
  {"timestamp": "2026-08-08T18:28:27.941226+00:00", "level": "ERROR", "event": "unhandled_exception", "path": "/api/me", "error_type": "ProgrammingError"}
  ```
- 再現手順: **根本原因を特定済み。重大度: 高。** `server/app/db/connection.py` の `get_connection()` は `sqlite3.connect(str(path))` を `check_same_thread=False` なしで呼び出している。CalendarPage(S02)はマウント時に `GET /api/me`・`GET /api/rooms`・`GET /api/reservations` を並行して呼び出す(3つの独立した `useEffect`)。この並行リクエストをFastAPIが処理する際、同期の依存性(`Depends(get_db)` の generator)の実行がAnyIOのスレッドプール経由でディスパッチされるが、1リクエスト内であっても常に同一OSスレッドで実行される保証が無く、まれに「コネクションを作成したスレッド」と「そのコネクションでクエリを実行するスレッド」が食い違う。この場合 `sqlite3.ProgrammingError` が送出され、`app/errors.py` の catch-all ハンドラ(U005-T5で追加)により500として返る。4回の再実行すべてで再現したが、単体のPOSTのみのフロー(例: T004, T007, T008)や、並行呼び出しが少ない画面では発生しないか、発生確率が低い。同一バグはT012・T013・T014・T015でも断続的に観測されている(発生頻度は実行のたびに変動する、典型的な競合状態の挙動)。
- 影響がありそうなモジュール: `server/app/db/connection.py`(`get_connection`)。`Depends(get_current_user)` と他の `Depends(get_db)` を併用するほぼ全エンドポイント(認証必須の全API)が理論上の影響範囲。フロントエンドが1画面表示につき複数のAPIを並行呼び出しする構成(Header + ページ本体など)であるほど発生しやすい。
- テスト指示との矛盾の疑い: なし
- 次工程への申し送り: P202へ。修正候補: `sqlite3.connect(str(path), check_same_thread=False)` を指定する(SQLiteの同時アクセス自体はファイルロックで安全に処理されるため、単一コネクションを複数スレッドで順に使う分には安全)。★重大: このバグは他の複数テスト(T012・T013・T014・T015)にも影響しており、優先度高で修正すべき。
