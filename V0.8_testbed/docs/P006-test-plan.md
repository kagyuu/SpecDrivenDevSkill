## 2. 機能観点

### 2.1 バックエンドAPI(単体テスト、`docs/P007-impl-direction.md` で実装指示)

各エンドポイントについて、次を最低限カバーする。

* 正常系: 仕様どおりのリクエストで期待するレスポンス・ステータスコードが返ること
* 異常系(該当するAPIのみ):
  * バリデーションエラー(400): 必須項目欠落、文字数超過、時刻の前後関係違反、収容人数超過など `docs/P002-frontend-spec.md` 4章に列挙した各ルール
  * 認証エラー(401): 未ログインでのアクセス
  * 認可エラー(403): 一般ユーザーによる管理者専用APIへのアクセス
  * Not Found(404): 存在しないID指定
  * 競合(409): 予約の重複作成・更新(`docs/P003-backend-spec.md` 4.6〜4.9.2節)
* 業務ロジックの境界値: 収容人数ちょうど・超過、時間帯の端点が接する(重複としない)ケースと1分でも重なるケース、自己無効化・最後の管理者保護の境界(管理者が2名から1名になるケースと1名から0名になるケース)
* **CR-001対応(※P903内側のP006再実行で追記)**: `POST`/`PUT /api/reservations` のオンライン会議URL(`meeting_url`)バリデーションを異常系テストの対象に追加する。境界値: (1) 未入力(`null`/空文字列)→登録・更新成功、値は`null`として保存、(2) `http://`/`https://` で始まる妥当な値→成功、(3) `ftp://` やスキームなし(`example.com`)→400 `VALIDATION_ERROR`、(4) ちょうど500文字→成功、501文字→400。`GET /api/reservations`(一覧)は`meeting_url`を含めないことを確認するテストも追加する(`docs/P002-frontend-spec.md` 4.6節)。

### 2.2 フロントエンド画面(単体テスト、`docs/P007-impl-direction.md` で実装指示)

各画面のコンポーネントについて、次を最低限カバーする。

* 入力バリデーションの表示・非表示切り替え(`docs/P002-frontend-spec.md` 3章の各画面のバリデーションルール)
* 終日チェックボックスの自動入力・手動上書き(S03/S04)
* API呼び出し結果(成功・エラー)に応じた画面遷移・エラーメッセージ表示
* **CR-001対応(※P903内側のP006再実行で追記)**: S03のオンライン会議URL入力欄のクライアント側バリデーション(スキームチェック・文字数)表示、S04でのオンライン会議URLのリンク表示(設定時)/「(未設定)」表示(未設定時)の切り替え、S04編集モードでの入力・保存・空欄への変更を確認する。

### 2.3 画面とAPIの接続・モジュール間連携(結合テスト、`docs/P008-test-direction.md` で実装指示)

* スプリント内で完結する範囲での画面→API→DBの一連の流れ(例: U003スプリント内でのS03予約作成画面からのPOST /api/reservations呼び出しとDB反映確認)
* 詳細は `docs/P008-test-direction.md` 参照

### 2.4 業務シナリオ・画面遷移・権限まわり(システムテスト/受け入れテスト、`docs/P009-acceptance-direction.md` で実装指示)

* 画面一覧に挙げた全画面の主要操作(予約の作成・編集・取消、会議室/ユーザー管理のCRUD)をシナリオベースで確認(`docs/P001-requirement.md` テスト方針に対応)
* 権限まわり(一般ユーザーが管理者専用画面・APIにアクセスできないこと)を必ず確認(`docs/P001-requirement.md` テスト方針に対応)
* ログイン〜カレンダー表示〜予約作成〜マイ予約確認〜予約編集〜予約取消、という一連の主要業務フロー(スプリントをまたぐ)

## 3. 非機能観点(システムテスト、`docs/P009-acceptance-direction.md` で実装指示)

| 観点 | 内容 |
| --- | --- |
| 性能 | カレンダー画面(S02)表示が3秒以内に完了すること(`docs/P002-frontend-spec.md` 7章の見積りの実測確認) |
| 負荷 | 同時30接続程度を想定したシナリオで、予約作成API(`POST /api/reservations`)への同時リクエストが重複チェックの排他制御により正しく1件のみ成功し、他は409で拒否されること(`docs/P003-backend-spec.md` 4.6〜4.9.2節の排他制御の実地検証) |
| セキュリティ | 未ログインでの管理者API・一般APIへのアクセス拒否(401)、一般ユーザーによる管理者専用APIへのアクセス拒否(403)、パスワードがハッシュ化されて保存されていること(平文が保存されていないことをDBファイルを直接確認) |
| 運用(ログ監視) | `docs/P003-backend-spec.md` 6章の構造化ログが標準出力に出力されること、エラーレベルのイベント(未処理例外など)が判別可能な形式であること |

## 4. 運用観点(再起動耐性) — 必須

* データストア(SQLite)を持つため、**アプリケーションを停止・再起動しても正常に起動すること** を確認する観点を含める(`docs/P003-backend-spec.md` 3章のマイグレーション方式の冪等性に対応)。
* 具体的な確認方法: サーバープロセスを起動→正常稼働確認→プロセスを停止→再度起動→2回目の起動が例外なく完了し、既存データ(会議室・予約等)が保持されたままAPIが正常応答することを確認する。この観点はテストごとに新しい一時データベースを使う単体テスト・結合テストでは検出できない(常に初回起動になるため)。`docs/P009-acceptance-direction.md` 側で独立したテストタスクとして実装する。

## 5. テスト遂行上の技術的な決め事

* **テストフレームワーク**: バックエンドは `pytest`、フロントエンドは `node --test`(Node.js標準テストランナー、Vite/Reactコンポーネントは `@testing-library/react` 相当のユーティリティを利用する想定。★FIXME★ 具体的なテストライブラリの組み合わせはP007実装時に、実際にnpmレジストリから導入可能なものを確認して確定する。本書執筆時点(P006)ではnpmレジストリへの到達を確認済みのため、`@testing-library/react` + `jsdom` の利用を第一候補とする)。
  * **TypeScript+JSX(`.tsx`)テストファイルの実行方法(※P010初回レビューで発見された不足を補うため追記)**: Node.js標準テストランナーは `.tsx` 構文(TypeScript型注釈・JSX)を単体では解釈できない。`docs/P007-impl-direction.md`・`docs/P008-test-direction.md` 配下のフロントエンド結合テスト(コンポーネントを直接レンダリングして検証するもの)は、npmパッケージ `tsx`(TypeScript/JSXをその場でトランスパイルするNode.js用ローダー)をESMローダーとして読み込み、`node --import tsx --test <path>` の形式で実行する。`tsx` パッケージは `docs/P007-impl-direction/U001-foundation-and-auth.md` U001-T1で開発依存関係に追加する。
  * **`docs/P009-acceptance-direction.md` 側のフロントエンドテストとの違い**: P009のクライアント側受け入れテスト(`docs/P009-acceptance-direction/A0NN-*.md` のうちブラウザ操作を伴うもの)は、コンポーネントをNode.js側で直接importしてレンダリングするのではなく、ビルド後の実アプリケーションをブラウザ自動化ツール(例: Playwright)経由で操作する形を取る。テストファイル自体はNode.js側でJSX/TSXを解釈する必要が無いプレーンな `.js` のままでよく、`node --test`(`tsx`ローダー不要)で実行する。この違いは意図的なものであり、P008側の`.tsx`+ローダー方式とP009側の`.js`方式が異なることを「表記ゆれ」として統一する必要はない(★ACCEPTED★ 検討した代替: P009も`.tsx`でコンポーネントを直接レンダリングする方式に統一する。不採用理由: P009はスプリントをまたぐ・画面遷移を含むシナリオ確認が主目的であり、実際のビルド成果物に対するブラウザ操作の方が本番相当の確認として妥当なため。残存リスク: 特になし、テスト階層ごとに適切な手法を使い分けているだけである)。
* **外部APIのモック方針**: 本アプリケーションは外部APIとの連携を持たない(`docs/P001-requirement.md` に「連携・参考にする既存システムの有無: なし」と明記、Googleカレンダー等連携は対象外)ため、外部APIモックの方針は不要。
* **テストデータの準備方法**:
  * 単体テスト・結合テストは、テストごとに新しい一時SQLiteファイル(`:memory:` またはテンポラリファイル)を使用し、テスト間でデータが干渉しないようにする。
  * システムテスト・受け入れテストは、固定のテストデータセット(会議室3〜5室、一般ユーザー2〜3名、管理者1名、予約数件)を各テスト実行前にセットアップスクリプトで投入する。テストデータセットの詳細は `docs/P009-acceptance-direction.md` の各テストタスクで定義する。
  * 再起動耐性テスト(4章)のみ、一時ファイルではなく永続ファイルパスのSQLiteファイルを使用する(再起動前後でファイルが保持される必要があるため)。
