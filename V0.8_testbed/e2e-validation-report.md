# spec-driven-dev Skill V0.8 — フルパイプライン実地検証レポート

作成日: 2026-08-09

## これは何か

`spec-driven-dev` Skill V0.8 を、`V0.7_testbed` の起点要件定義書(CR-001適用前の原本、会議室予約システム)を流用し、`docs/P002-frontend-spec.md` 以降をV0.8のルールで新規に実行した実地検証の記録。V0.8はV0.7_testbedで発見された44件の不備のうち高重大度5件・中重大度28件(V0.8/review-report.md参照)を解決したバージョンであり、本検証の主目的は**それらの修正が実際に機能するかを実地で確認すること**にある。

* V0.7→V0.8の変更内容: [`../V0.8/review-report.md`](../V0.8/review-report.md)

## 検証の構成

7ラウンドに分けて実施した(V0.7_testbedと同じ構成)。いずれも実際にコードを書き、実際にテストを実行している。

1. Plan Loop Step(P002〜P010、2ラウンドで矛盾解消)
2. Overview Step(P020〜P022)
3. Executor・スプリントU001 — **意図的に中断を注入**(修正1-1の検証)
4. 中断からの再開(別セッション)+ Executor・スプリントU002〜U005・P103・P104
5. Reviewer Loop(P201〜P205)
6. Closing(P301〜P302)
7. Refactor(CR-001)— **P902の重複実行**(修正1-4の検証)+ **P903内側での中断**(修正1-5の検証、別セッションで再開)+ CR完了までの残り全フェーズ

各ラウンドは独立したエージェントセッション(一部は意図的に「前セッションの記憶を持たない」フレッシュなセッション)として実行し、報告内容は都度、実際のファイル・テスト実行結果と突き合わせて独立に検証した(エージェントの自己申告をそのまま採用していない)。

## 結果サマリ

**V0.8で修正した高重大度5件は、いずれも実地で意図どおり機能することを確認した。** 特にデータ損失を伴う2件(1-4・1-5)は、修正前なら再現していたはずの具体的なシナリオ(P902の重複実行、P903内側での中断)を実際に発生させ、修正が効いていることをファイルのハッシュ値・`.inprogress`の実際の内容で裏付けた。

最終テスト件数: **228件、全PASS**(サーバ153 + クライアント単体46 + クライアント結合17 + クライアント受け入れ12)。CR-001(予約へのオンライン会議URL追加、API契約変更+データモデル変更)は完了まで処理し、`docs/CR.md`の状態は`完了`、`docs/.inprogress`は正しく削除された。

副次的に、Skillの検証プロセス自体が機能していることの証拠として、**本ラウンドの中で2件の実際のアプリケーションバグ**(タイムゾーン依存の日付計算バグ、SQLite接続のスレッド安全性バグ)を検出し、Reviewer Loopで実際に修正した。

新たに見つかったSkillの不備は**3件、いずれも低重大度**(下記「3. 新たに見つかった論点」参照)。V0.7からV0.8への変更で高・中重大度の問題を解消した結果として、想定どおり検証の焦点が「新しい欠陥の発見」から「既存修正の動作確認」に移ったことを反映している。

## 1. 高重大度5件の検証結果

### 1-1. 中断からの再開(タスク粒度) — **機能した**

スプリントU001の実行中、意図的にタスクT1・T2を完了・T3を「Repository層のみ実装済み、Service層未着手、テスト未作成」の状態で中断させ、加えて未着手のT4が所有すべきファイル(`app/routers/auth.py`)にスタブを先行作成する「先行実装違反」も意図的に混入させた。

その後、**この中断について一切の事前情報を与えていない、完全に別のエージェントセッション**に再開を依頼した。結果:

* タスク一覧の`[~]`マークだけを信用せず、`SKILL-P102-implement.md`の指示どおり実際に該当タスクの完了条件(単体テスト)を再実行して現状を確認した(pytestを実行し、T3のテストが実際には1件も存在しないことを自ら発見)。
* 先行実装の違反ファイル(`app/routers/auth.py`)を、正規のタスクT4に到達した時点で実装として正式に書き直す形で解消した(削除ではなく、違反の痕跡を残さない形での解消)。
* T1・T2(完了)、T3(部分完了)、T4・T5(未着手、ただし違反ファイルの残骸あり)を正しく区別し、中断以降の作業を正しく完了させた(検証: サーバ側25/25テストPASS、独立に確認済み)。

### 1-2. 結合・受け入れテストのコード作成者 — **機能した**

Executor(P103)は、`docs/P008-test-direction.md`の15件のテストタスクすべてについて、既存のテストコードが無い状態から指示書どおりに新規にテストコードを作成し、実行した(結合テスト15件: サーバ4件・クライアント11件)。Reviewer Loop(P201)も同様に、`docs/P009-acceptance-direction.md`の受け入れテスト11件を新規作成・実行した。「新規作成」と「改ざん」が区別されているかを確認したところ、いずれのテスト記録でも「テスト指示との矛盾の疑い: なし」が正しく判定されており、既存テストの期待値を弱める操作は発生しなかった。

### 1-3. 「テスト指示側の誤り」という結果区分 — **仕組みは機能したが、本ラウンドでは分岐しなかった**

`TEMPLATE-test-record.md`の「テスト指示との矛盾の疑い」欄は全26件のテスト記録すべてで明示的に判定・記載された(すべて「なし」)。P202で見つかった6件のテスト失敗は、調査の結果いずれも実際のアプリケーションコードの欠陥(後述)であり、「テスト指示側の誤り」区分は該当しなかった。したがって**区分自体の存在と判定手順は機能したが、「テスト指示側の誤りだった」という分岐が実際に選ばれる場面は本ラウンドでは発生しなかった**(V0.7_testbedのT016・A001のような事例は今回は起きなかった)。この区分の実効性そのものは今回のデータでは証明も反証もされていない。

### 1-4. P902バックアップ上書き(データ損失) — **機能した**

P902の実行完了直後、意図的にP902をもう一度実行させ(セッション中断後の誤った再開を模擬)、実行前後でバックアップファイルと`docs/P001-requirement.md`のハッシュ値・サイズ・更新日時を比較した。

* バックアップファイル(`docs/P001-requirement_20260809_CR-001.md`): 実行前後でSHA-256・サイズ・mtimeが完全に一致(上書きされなかった)。
* `docs/P001-requirement.md`: 実行前後でSHA-256が完全に一致(二重適用されなかった)。

2段階の冪等性チェック(バックアップ先の存在確認、本体のCR注記の存在確認)が意図どおり機能し、原本の上書きも内容の二重適用も発生しなかった。

### 1-5. `.inprogress`の入れ子表記(Refactor中の再開) — **機能した**

P903が内側のP002〜P303再実行中、P004着手前の時点で意図的に中断し(`docs/.inprogress`の内容: `P903:P004`)、**この中断について一切の事前情報を与えていない、完全に別のエージェントセッション**に再開を依頼した。結果:

* `SKILL.md`の入れ子表記ルールを正しく適用し、`docs/CR.md`の状態(`対応中`)を先にチェックすることなく、入れ子表記が示すP004からCR文脈のまま再開した。
* 実際にP002・P003が更新済みでP004が未実行であることをファイル内容から独立に確認してから作業した(記録ファイルの記載を鵜呑みにしなかった)。
* 作業完了後、`.inprogress`を`P903:P005`に更新し、入れ子表記の形式を正しく維持した。

再開担当は「台帳の`対応中`を見て先にP904に飛びたくなる誘惑があった」と報告しており、`SKILL.md`の「台帳のチェックより先に」という明示的な優先順位づけが実際に機能したことが確認できた(下記「3-2」も参照)。

## 3. 新たに見つかった論点(いずれも低重大度)

### 3-1. P101がスプリントごとに再実行されるかの記述が曖昧

`SKILL-P102-implement.md`の「続けて次のスプリントのP101〜P102を実行する」という記述は、P101(実装コンテキスト構築)がスプリントごとに再実行されることを示唆するが、`SKILL.md`のフェーズ表は`docs/P101-impl-context.md`を単一文書として説明しており、スプリント単位で更新されるかどうかが不明瞭である。本ラウンドでは既存のP101文書で十分だったため実害は無かったが、ソースツリーの状態が大きく変わるスプリントの境目では、P101の更新要否が曖昧なままだと古い情報を参照し続けるリスクがある。

### 3-2. ステップ0の記述順序が、入れ子表記より先にレビュー担当の目を台帳へ誘導しうる

`SKILL.md`のステップ0は、入れ子表記の優先を明示的に述べている(「台帳のチェックより先に」)ものの、文書全体の構成としては台帳ベースの`対応中`/`反映確認中`分岐も同じ節内に近接して記載されている。1-5の検証では最終的に正しく判定されたが、担当者は「先に台帳を見て`P904`に飛びたくなる誘惑があった」と申告しており、既存の優先順位づけの文言に頼っている状態である。実害としては顕在化しなかったため修正は見送るが、次版で構成上の分離(入れ子表記の判定を独立した項目として先頭に出すなど)を検討する価値はある。

### 3-3. P202「テスト指示側の誤り」区分は、V0.8_testbedでは実証機会が無かった

1-3で述べたとおり、本ラウンドで発生した全6件のテスト失敗はアプリケーションコードの欠陥であり、テスト指示側の誤りは1件も発生しなかった。区分自体・証拠要件の運用は妥当に見えるが、V0.7_testbedのT016・A001のような実例での動作確認は次回以降に持ち越しとなる。

## 4. 参考: 本ラウンドで検出された実際のアプリケーション不具合

Skillの不備ではなく、Skillが正しく機能して検出できた例。

* `client/src/pages/CalendarPage.tsx`の`addDays()`がタイムゾーン依存のバグを持ち、JST環境で特定の時間帯に「次へ/前へ」ボタンが無反応になる。P103で検出、P202〜P205で修正(UTC基準の計算に変更)。
* `server/app/db/connection.py`の`sqlite3.connect()`に`check_same_thread=False`が指定されておらず、認証必須のほぼ全APIで並行リクエスト時に間欠的な500エラーが発生しうる欠陥。P103で検出(1件のテストで顕在化、他4件のテストにも波及)、P202〜P205で修正。
* 上記の修正過程で、テストコード自身の欠陥4件(あいまいなARIA role指定によるハングアップ、フィルタ文言と衝突するテストデータ、ハードコードされたボタンインデックスの誤り、非同期描画要素へのawait漏れ)も発見・修正され、アプリケーション側の欠陥と正しく区別して記録された。
* CR-001の受け入れテスト(A001)作成時、`ReservationDetailPage.tsx`が編集権限を持つユーザーには常に編集フォームを表示し、リンクとしての表示確認ができないという、CR-001とは無関係な既存の設計上の制約を発見。テスト指示側の代替手段(API応答での確認)で対応し、記録に残した。

## 5. 総評

V0.8で修正した高重大度5件は、いずれも実地で意図どおり機能していることを確認できた。特にデータ損失を伴う2件(1-4・1-5)は、修正が無ければ確実に再現していたはずのシナリオを意図的に発生させ、ファイルハッシュや`.inprogress`の実際の内容という具体的な証拠で機能を裏付けられたことが本ラウンドの最大の成果である。1-1(中断再開)も、完全に文脈を持たない別セッションによる再開という最も厳しい条件で検証し、意図どおりに機能した。

新たに見つかった論点は3件、いずれも低重大度で実害は顕在化しなかった。V0.7からV0.8への変更が対象を「高+中重大度」に絞ったことの効果として、本ラウンドの検証は新規欠陥の発見よりも既存修正の動作確認が中心となった。これはV0.7_testbedとの検証方式の違い(全面再構築+3件の新規変更の検証、対28件の修正の動作確認)を反映した自然な結果であり、V0.8の劣化を意味しない。

次版に向けては、3-1・3-2・3-3を低重大度の記録として残し、必要であれば見送った低重大度17件(`V0.8/review-report.md`参照)と合わせてV0.9の対象を検討することを推奨する。
