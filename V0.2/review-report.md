## 1. 開発体系の整合性(最重要・最多の不備)

### 1-1. フェーズ1の出力ファイル名の不一致(全下流フェーズに波及)

`SKILL.md` のフェーズ表では、フェーズ1の成果物は `docs/01-requirement.md` と定義されている。しかし `SKILL-02-frontend-spec.md` `SKILL-03-backend-spec.md` `SKILL-04-impl-plan.md` `SKILL-05-test-plan.md` の「インプット文書」は揃って `docs/01-overview.md` という、どこにも定義されていないファイルを参照していた。上位文書(フェーズ表)と下位文書(各フェーズの指示書)が最初の入口から食い違っており、この状態で `SKILL-02` 以降を実行すると Claude Code は存在しないファイルを探しにいくことになる。

→ **Ver0.2で修正**: `docs/02〜05` の全インプット記述を `docs/01-requirement.md` に統一。

### 1-2. `SKILL-09-deliver.md` が完全に別体系だった

これが今回見つかった最大の不整合。`SKILL-09-deliver.md` だけ、他の8ファイルとは無関係な「11フェーズ体系」(`01-overview.md` `02-detailed-spec.md` `03-implementation-plan.md` `04-test-plan.md` `05-implementation-instructions.md` `06-test-instractions.md`(誤字含む) `07-test-record.md` `08-fix-instructions.md` `09-fix-result.md` `10-unresolved-tests.md` `11-deliverable-summary.md`)を参照しており、`SKILL.md` の9フェーズ体系とは1つも噛み合っていなかった。frontmatter の `description` も他ファイルの3〜4倍の長さで、独自のトリガー文言(「/deliverable-summary-planner を明示的に呼び出した場合」)まで含んでいた。おそらく別プロジェクトで作った「成果物まとめSkill」をそのまま持ち込み、番号体系を合わせずに置いた状態だったと推測される。

→ **Ver0.2で修正**: 内容(トレーサビリティ表、バージョン/ビルド履歴管理、Docker Compose/CLI/バッチの配布手順、リリース判定など、作り込み自体は良い内容だった)はほぼそのまま活かしつつ、参照ファイル名を現行9フェーズ体系(`docs/01-requirement.md`〜`docs/08-fix-plan.md`)に全面的に付け替え、出力ファイルも `docs/11-deliverable-summary.md` → `SKILL.md` のフェーズ表通り `docs/09-deliver.md` に変更。frontmatter description も他ファイルと同じ長さ・文体に短縮し、構成見出しも他フェーズと同じ型(目的/インプット文書/アウトプット文書/動作)に合わせた。

### 1-3. フェーズ8のサブフォルダ名がフェーズ本体と食い違っていた

フェーズ6は本体 `docs/06-impl-direction.md` に対し子文書フォルダが `docs/06-impl-direction/`、フェーズ7も本体 `docs/07-test-direction.md` に対し `docs/07-test-direction/` と、本体名とフォルダ名が一致している。しかしフェーズ8だけ、本体は `docs/08-fix-plan.md` なのに子文書フォルダは `docs/08-fix-direction/` で、命名パターンが崩れていた。加えて「解決済み一覧」は `docs/08-fix-direction/08-fix-resolved.md`(フォルダの下)に置く指示なのに、「未解決一覧」は `docs/08-fix-unresolved.md`(フォルダの外＝docs直下)という配置も左右不揃いだった。

→ **Ver0.2で修正**: フォルダ名を `docs/08-fix-plan/` に統一し、解決済み・未解決の一覧ファイルも両方このフォルダの下に配置するよう統一。

## 2. 実行可能性(Claude Code が実際にこの指示書通りの Markdown を作れるか)

### 2-1. 「OKF形式」が一度も定義されていなかった

`SKILL-04` `SKILL-05` `SKILL-06` `SKILL-07` は繰り返し「目次は **OKF形式** で作成する」と指示しているが、Ver0.1 全9ファイル+5テンプレートのどこにも OKF形式の定義がなかった。この状態で Claude Code にフェーズ6を実行させると、目次ファイル(`docs/06-impl-direction.md`)をどう書けばよいか分からず、実行のたびに異なる形式で目次を作ってしまう(=このSkillの目的である「実行可能な指示書」の要件を満たせない)。

→ **Ver0.2で修正(暫定定義・要確認)**: `SKILL.md` の共通指示に、「状態チェックボックス `[ ]`/`[~]`/`[x]` + 番号 + タイトルへのリンク + 一言概要」を1行で表す形式として OKF形式を定義した。ただし **これは記述内容から実行可能にするための私の推測に基づく暫定定義であり、Ver0.1作成時に想定していた本来の「OKF」の意味と異なる可能性がある**。残課題として後述。

### 2-2. テンプレートの項目が、指示書本体が要求する項目数と食い違っていた

`SKILL-06-impl-direction.md` は実装タスクに含めるべき項目を9つ(目的/作成・編集対象ファイル/参照すべき仕様箇所/実装内容/実装してはいけないこと/Unit Test内容/実行コマンド/完了条件/次タスクに進む前の停止条件)列挙しているが、実際に使う `TEMPLATE-06-impl-direction.md` には「実行コマンド」と「次タスクに進む前の停止条件」の項目が無く、7項目しかなかった。同様に `SKILL-07-test-direction.md` が要求する「次タスクへ進む条件」も `TEMPLATE-07-test-direction.md` に項目として存在しなかった。指示書(上位)とテンプレート(下位)が食い違っているため、テンプレート通りに作ると指示書の要求を満たさない実装指示書ができてしまう。

→ **Ver0.2で修正**: 両テンプレートに不足項目を追加し、項目名も指示書側の文言と完全一致させた。

### 2-3. テンプレートの表組みが壊れていた

`TEMPLATE-08-fix-resolved.md` `TEMPLATE-08-fix-unresolved.md` はどちらも、表のヘッダ行が5列なのに区切り行(`|---|---|...`)が6列になっており、Markdownとして列がずれる状態だった。この壊れたテンプレートをそのまま複製すると、生成されるテスト記録・修正記録の表が正しく描画されない。

→ **Ver0.2で修正**: 区切り行を5列に修正。修正後、V0.2全ファイルに対して表のヘッダ列数と区切り行列数が一致しているかをスクリプトで機械的に検証済み(不一致0件)。

### 2-4. フェーズ6/7/8内の「スプリント/テスト単位の進捗」をどう記録するかが未定義だった

Ver0.1は `docs/.inprogress` でフェーズ単位の進捗は追えるが、フェーズ6(複数スプリント)・7(複数テスト)・8(複数修正)のように1フェーズに複数の子タスクがある場合、どのスプリント/テストまで終わったかを記録する仕組みがなかった。これはOKF形式の目次を「作って終わり」ではなく「進捗管理表として更新し続ける」ものと位置づければ解決できるため、Ver0.2ではOKF形式の定義に合わせて「作業完了時に目次のチェックボックスを `[x]` に更新する」処理を各フェーズの指示書に追記した。

## 残課題(要ユーザー確認・未着手の論点)

1. **「OKF形式」の本来の意図は確認済み(採用は見送り)**: Ver0.1にはOKF形式の定義が一切なく、Ver0.2では「状態チェックボックス+番号+リンク+概要」という形式を暫定的に定義していた。その後ユーザーに確認したところ、Google Cloud が提唱する **Open Knowledge Format(OKF)** を指すことが判明したが、調査の結果、実装指示・テスト指示・修正指示のような複数の実行タスクファイルの目次役としては不適切と判断し、採用を見送った。詳細は本レポート末尾の「追記: OKF形式(目次形式)の採用検討について」を参照。Ver0.2で定義した独自の目次形式(チェックボックス+番号+リンク+概要)は、名称の由来だけを外した独自形式として維持している。
2. **サブフォルダ単位(スプリント/テスト/修正)の進捗管理は未検証**: OKFチェックボックスで進捗を追う仕組みをVer0.2で追記したが、実際にClaude Codeへ複数回のセッションにまたがってこの指示書を実行させ、目次の更新が意図通り行われるかは実地検証していない。

5. **End-to-Endの実地検証は未実施**: 今回はテキスト・構造レベルでの整合性レビューであり、実際にClaude Codeに `SKILL.md` から通しでフェーズ1〜9を実行させて動作確認したものではない。特にフェーズ6で生成される `U000-*.md` を実装担当Agentに渡して実行させ、期待通りのコード・テストが生成されるかは、次のステップとして実地検証することを推奨する(2026-07-29時点でユーザーからは「いずれ行うので今は不要」との回答済み)。

## 追記: OKF形式(目次形式)の採用検討について

*(2026-07-29 追記)*

### 経緯

Ver0.2 に対してユーザーから、「OKF形式」とは Google Cloud Blog で発表された **Open Knowledge Format(OKF)** を指すという指定があった([参考: How the Open Knowledge Format can improve data sharing](https://cloud.google.com/blog/ja/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing/))。これを前提に Ver0.2 → Ver0.3 への書き直しを行う予定だったが、事前調査の結果、本Skillでの目次役としては不適切と判断し、Ver0.3の作成には至らなかった(ユーザー了承済み)。Ver0.2 は変更せず現行のまま維持している。

### OKFの実態(調査結果の要約)

Google Cloud Blog の記事によれば、OKF は次のような性質を持つ。

* **目的**: 組織内に散在するナレッジ(テーブルスキーマ、ビジネス指標の定義、ランブック、API仕様など)を、Markdown + YAMLフロントマターという最小限の制約で統一表現し、AIエージェントが横断的に参照・相互運用できるようにするための、Googleが提唱するオープンな形式。
* **構造**: ディレクトリ構造で概念の親子関係を表現し、各ディレクトリの `index.md`(予約ファイル名)が配下の概念ファイルへリンクする。各概念は1つのMarkdownファイルとし、YAMLフロントマターの必須項目は `type` のみ(他は自由)。変更履歴用に `log.md` という予約ファイルもある。
* **想定用途**: データセットのメタデータカタログ化、ビジネスナレッジ管理、運用ランブック、AIエージェント向けの参照コンテキスト(=グラウンディング用の事実・定義の共有)。
* **明示的に持たない概念**: タスクの実行順序、進捗状態(未着手/進行中/完了)、合否判定、「次のタスクに進んではいけない」といった、ワークフロー・タスク管理のための標準的な表現。仕様書自身が「コンテンツモデルではなく相互運用性サーフェスを定義するもの」と位置づけている。

### 不採用の理由

* 本Skillの `docs/06-impl-direction.md` → `U000-{sprint-name}.md` のような「1つの目次が複数の子ファイルにリンクする」という構造自体は、OKFの `index.md` + 配下ファイルという構造と表面的には類似している。
* しかし本Skillの目次に本当に必要なのは、各スプリント/テスト/修正が「完了しているか」「合格したか」「次に進んでよいか」というタスクのライフサイクル管理であり、これはOKFの標準機能には含まれない。追加するとすれば独自のカスタムフィールド(例: `status:`)をYAMLフロントマターに増設することになるが、それはOKF本来の「組織・システム横断でのナレッジ共有」という目的からは外れた、体裁だけの流用になる。
* OKFは複数の組織・ツール間でのナレッジ相互運用を課題とした標準であり、単一プロジェクト内部の実行タスクの索引(本Skillの用途)に、この種の相互運用標準を持ち込む必然性は薄いと判断した。

### 結論

* OKF形式(Google Cloud版)は、実装指示・テスト指示・修正指示の目次役としては採用しない。
* Ver0.2 で定義した独自の目次形式(状態チェックボックス `[ ]/[~]/[x]` + 番号 + リンク + 概要)はそのまま維持する。ただし「OKF形式」という呼称は紛らわしいため、今後 Ver0.3 以降で改訂する際は、呼称を独自の名称(例:「進捗目次形式」など)に変更することを推奨する。
* この呼称変更以外の Ver0.2 の内容(整合性・実行可能性・記述一貫性の修正)には影響しない。
