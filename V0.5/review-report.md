# Spec-Driven Dev Skill Ver0.4 → Ver0.5 改訂レポート

作成日: 2026-08-03

## 経緯

V0.4に対し、実際に会議室予約システム(テストヘッド)を題材に、`docs/P001-requirement.md` を起点にP002〜P302まで人間のレビューを挟まず連続実行し、実際にコードを書き・テストを実行し・不具合が出れば修正サイクルを回し、最後にRefactor(P901〜P905)まで1件のCRで検証するEnd-to-Endフルパイプライン実地検証を行った(詳細は `V0.4_testbed/e2e-validation-report.md` を参照)。この検証で見つかったSkillの不備・曖昧点23件(高重大度5件・中重大度13件・低重大度5件、致命的で処理続行不能なものはなし)を、`e2e-validation-report.md` 末尾の「V0.5での対応方針」に沿って、V0.5としてSKILL側のルールに明文化した。V0.4のファイル自体は変更せず、本レポートの内容はすべてV0.5の新規フォルダへの反映である。

対応方針(`e2e-validation-report.md` より):

* 高重大度6件(1-1, 1-3, 1-4, 1-5, 1-6, 2-1)はすべて対応する。
* 中重大度13件のうち、記述修正で対応できるものは全て対応する(1-2, 2-2〜2-9, 3-1〜3-4)。
* 低重大度5件は、記述修正で対応可能なものは合わせて対応する(3-5〜3-11)。
* ただし1-3・2-5・1-5の3件は、部分的な緩和はV0.5で行うが、設計そのものの再検討は次バージョン(V0.6)の検討課題として人間に判断を委ねる(本レポート末尾「今回あえて反映しなかった判断」参照)。

以下、`e2e-validation-report.md` の「Skillの不備一覧」の項番に対応させて記載する。

## 3. 記述の一貫性・その他

### 3-1. 非機能要件のうちインフラ寄りの項目をP002/P003どちらが担うか未定義 — 重大度: 中 への対応

* **事象**: 可用性・TLS・スケーラビリティ・ログ集約基盤などの非機能要件は、P004/P010で「充足確認」の対象になるにもかかわらず、担当フェーズが明記されていなかった。実地検証ではP003が「P005/P302に委譲する」と明記する運用を独自に採用した。
* **V0.5での変更**:
  * `SKILL-P003-backend-spec.md` に、非機能要件のうちインフラ寄りの項目について、P003ではアプリケーションコード側の前提のみを明記し、実際のインフラ構成の決定は`docs/P005-impl-plan.md`・`docs/P302-deliver.md`に委譲する旨を明記するルールを追加した。この委譲の明記が無い場合、P004/P010はMISSING/PARTIALとして扱う旨も追加した。
  * `SKILL-P002-frontend-spec.md` にも、これらの項目は原則P002では確定させず、P003側の委譲の記載を根拠にP004/P010が充足確認を行う旨の相互参照を追加した。
  * `SKILL.md` Plan Loop Stepの「その他」欄にも同旨を追記し、実行担当が独自に採用した運用をSkill全体のルールとして明文化した。

### 3-2. P022のADR粒度(1決定=1ADR か、関連決定をまとめるか)の基準がない — 重大度: 中 への対応

* **事象**: `TEMPLATE-ADR.md`のサンプル(Spring Boot+MyBatisを1つのADRにまとめている)と、細かく分ける方針のどちらもSKILL上は正当化でき、実行者によってADR件数が大きくブレる。
* **V0.5での変更**:
  * `SKILL-P021-adr.md`(1-2の番号入れ替え後のADRフェーズ)に、ADR粒度のガイドラインを追加した。実務上切り離せない決定(例: フレームワーク選定に付随するORM選定)は1つのADRにまとめてよく、独立に覆される可能性がある決定は別々のADRに分ける、という基準を明記した。
  * `TEMPLATE-ADR.md`のADR-001(Spring Boot+MyBatisの例)を「切り離せないためまとめる」ケースの例示として参照する一文を追加した。
  * 判断に迷う場合の目安(「後から一方だけを覆す変更要求が来たときに、1つのADRの一部だけを『廃止』にできるか」)も追加した。

### 3-3. P202の「修正成功時に更新するdocs」の3類型に、ADRの前提条件が未実現だったケースが無い — 重大度: 中 への対応

* **事象**: 「実装が仕様と違う」「テスト指示が誤り」「仕様の曖昧さを明確化」の3類型はあるが、「ADRの決定自体は正しいが、その前提条件(例: TLS終端環境)が実現されていない」ケースの扱いが定義されていなかった。
* **V0.5での変更**:
  * `SKILL-P202-fix-plan.md`の3類型に4番目のケースを追加した。ADRの決定自体は正しいがその前提条件が本実行環境で実現されていない場合は、コード・テスト・仕様書のいずれも変更せず、環境上の制約であることを既知の制約として記録する(`docs/P302-deliver.md`の未整備事項、または修正内容詳細への記載)ことを明記した。
  * `SKILL-P302-deliver.md`の「未整備事項・人間による確認事項」にも、この4番目のケースに対応する記載項目(ADRの前提条件が本環境で実現されていないもの)を追加し、P202とP302で扱いを一貫させた。

### 3-4. 「図に関しては記述内容を評価しない」がP010のレビュー対象から図と本文の整合性を除外してしまう — 重大度: 中 への対応

* **事象**: 図は本文とズレやすい典型箇所であるにもかかわらず、この共通指示を字面通りに読むとP010横断レビューの対象から外れてしまう。
* **V0.5での変更**:
  * `SKILL.md`「各フェーズ共通指示」の該当ルールに、「記述内容を評価しない」は図そのものの完成度・網羅性を採点しないという意味であり、図と本文の食い違いをレビュー対象から除外するものではないことを明記した。
  * `SKILL-P010-design-review.md`のレビュー観点に「図と本文の整合性」を明示的に追加し、SKILL.mdの上記注記を参照する形で、図と本文の矛盾チェックがP010の対象範囲であることを明確化した。

### 3-5. P005「コード量を均等にする」指標が技術的難易度を反映しない — 重大度: 低 への対応

* **事象**: 画面数・API数などの機械的指標は、実装リスクの高いスプリント(例: 排他制御を含む)を過小評価しうる。
* **V0.5での変更**: `SKILL-P005-impl-plan.md` の「コード量を同じにする」原則に、機械的な量の指標だけに頼らず、排他制御・並行処理・複雑な状態遷移・外部システム連携などの技術的難易度・リスクも重みとして加味する旨を追記した。

### 3-6. 「多数」/「小数」の閾値が未定義 — 重大度: 低 への対応

* **事象**: 共通指示の「不足する項目が多数にわたる場合」/「小数な場合」の分岐基準が数値化されていなかった。
* **V0.5での変更**: `SKILL.md`「各フェーズ共通指示」に、「少数=3件以下」「多数=そのドキュメントで期待される項目のうち4件以上、または全体の半数以上が不足している場合」という具体的な閾値を追加した。あわせて「小数」という表記も「少数」に修正した。

### 3-7. P004の「対応する要求なし」(過剰実装検出)がブロッキングかどうか不明 — 重大度: 低 への対応

* **事象**: MISSING/PARTIALは明確に「次フェーズに進んではならない」とあるが、過剰実装の検出に同等のルールがなかった。

### 3-8. P007の目次ヘッダに技術スタック名がハードコードされ、代替実装後に陳腐化する — 重大度: 低 への対応

### 3-9. `TEMPLATE-CR.md`に実際の人間起票者の特定方法の言及がない — 重大度: 低 への対応

## 今回あえて反映しなかった判断

`e2e-validation-report.md`「V0.5での対応方針」の指示どおり、以下の3件は、V0.5では部分的な緩和(ワーディング修正)にとどめ、設計そのものの再検討は行っていない。深い設計判断はV0.6の検討課題として人間に委ねる。

* **1-3(P008テストIDとP102実装命名の対応)**: V0.5では、P102のインプット文書にP008のT0NNファイルを追加し、「P008が実行コマンドとして明記するテスト関数名にP102の実装が厳密に一致させる」という運用ルールを明文化するにとどめた。テストIDと実装コードを機械的・形式的に紐付ける仕組み(例: IDをコード側のアノテーションやコメントに埋め込み自動検証する、など)は導入していない。この対応づけを構造として保証する方式そのものの設計は、V0.6での検討課題とする。
* **2-5(1根本原因・多テスト波及時の修正ファイル粒度)**: V0.5では、「同一の根本原因と具体的に説明できる場合に限り複数テストIDを1ファイルにまとめてよい」という例外規定を追加し、`TEMPLATE-P202-fix-direction.md`等のテストID欄をリスト対応にするにとどめた。「根本原因」をどう定義し、いつ・どのようにグルーピングするかを判定するための形式的な基準や、修正ファイルの粒度単位そのものを再設計することはしていない。この点はV0.6での検討課題とする。
* **1-5(P903のCRスコープ判断)**: V0.5では、実行担当が実地検証で独自に発明した「対象/対象外+理由の記録」運用と、CR影響カテゴリの目安対応表を明文化するにとどめた。CRの影響範囲を自動的・体系的に分類する仕組み(影響分析エンジンのような機構)は導入していない。この仕組み化自体は、V0.5の実地検証結果とあわせてV0.6で人間が方向性を判断する。
