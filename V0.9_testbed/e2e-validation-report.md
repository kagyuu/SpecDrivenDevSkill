# spec-driven-dev Skill V0.9 — フルパイプライン実地検証レポート

## これは何か

`spec-driven-dev` Skill V0.9 を、`V0.7_testbed`/`V0.8_testbed`と同じ起点要件定義書(CR-001適用前の原本、会議室予約システム)を流用し、`docs/P002-frontend-spec.md` 以降をV0.9のルールで新規に実行した実地検証の記録。V0.9はV0.8_testbedで見送っていた低重大度20件+V0.8_testbedで新たに見つかった論点2件を解決したバージョンであり、本検証の主目的は**それらの修正の実地動作確認**と、**V0.8_testbedで検証未了だった1-3(「テスト指示側の誤り」区分)を実例で検証すること**にある。

* V0.8→V0.9の変更内容: [`../V0.9/review-report.md`](../V0.9/review-report.md)

## 検証の構成

5ラウンドに分けて実施した(V0.8_testbedより粗いが、V0.9の変更が低重大度の周辺的修正中心のため妥当と判断)。いずれも実際にコードを書き、実際にテストを実行している。

1. Plan Loop Step(P002〜P012)+ Overview Step(P020〜P022) — **意図的にテスト指示側の誤りを1件混入**(A004、修正1-3の検証準備)
2. Executor(P101〜P104、全4スプリント)
3. Reviewer Loop(P201〜P205) — **混入したA004の誤りを、事前情報なしで発見・分類できるかを検証**
4. Closing(P301〜P302)
5. Refactor — CR-001(実施完了)+ CR-002(却下)

## 結果サマリ

**V0.9で解決した20件+2件のうち、実地で動作を確認できたものはすべて意図どおり機能した。** 特に、V0.8_testbedで「仕組みは存在するが実例が無く検証できなかった」とされていた**1-3(テスト指示側の誤り区分)を、V0.9_testbedで意図的に実例を作って検証し、正しく機能することを確認した**。これにより、V0.7_testbedが発見した高重大度5件は、V0.8・V0.9を通じてすべて実地で動作確認済みとなった。

## 1. 1-3(テスト指示側の誤り区分)の実例検証

### 検証方法

Plan Loop Stepの実行担当(Round 1)に、P009受け入れテストの中に**意図的に1件、上位仕様と矛盾する誤った期待値**を混入させるよう依頼した。混入内容は、実行担当自身にのみ伝え、後続フェーズ(Round 3のReviewer Loop、完全に別セッション)には一切知らせなかった。

混入内容: `docs/P009-acceptance-direction/A004-*.md`の手順3・4で、`docs/P003-backend-spec.md` §5.9が明記する「背中合わせの予約(時刻が接するのみ)は重複とみなさない」という半開区間ルールに反し、誤って「409重複エラーになる」ことを期待値として記載した。

### 検証結果: ✅ 合格

Round 3(Reviewer Loop、事前情報なし)は、P201でA004のFAILを検出し、P202での原因調査の結果、以下を正しく行った。

* コード側(`overlaps()`・`find_conflicting()`)を先に確認し、`docs/P003-backend-spec.md` §5.9の規定と一致していることを確認した。
* 既存の単体テスト・API結合テストが同じ規則を独立に検証しPASSしていることを確認し、**カバレッジが失われないこと**を確認した。
* 上記2点の証拠とともに、「テスト指示側の誤り」区分を適用し、コードは一切変更せず、`docs/P009-acceptance-direction/A004-*.md`のみを訂正した(訂正箇所には「※P202 F004にもとづき訂正」と注記)。
* `TEMPLATE-P202-fix-resolved.md`の「変更したソースコード」欄には「なし」の分岐が実際に使われた。

判定・証拠要件・記録形式のすべてが設計どおりに機能し、コードを変更せずテスト指示側だけを是正するという、意図した経路をそのまま辿った。

## 3. 新たに見つかった論点(いずれも低重大度、次版で検討)

* **P007の「コード格納先を初期化する」の実施主体が曖昧**: P007(計画フェーズ)のアウトプット記載内容に置かれているため、P007自身が実施するように読めるが、実際はExecutor(P102)が行うべき作業である。P007の他の記述はすべて「指示書を書く」内容なので、この1項目だけ実施主体が異なって見える。
* **「完了」の語がP007/P008/P009のOKF完了(Executor時点)とPlan Loop Stepの終了条件(P010時点)で意味が重なる**: 各フェーズ自身の記述を読めば正しく解釈できるが、共通指示だけを読むと誤読しうる。
* **クライアント・サーバ分離構成でのE2Eハーネストのトポロジー決定主体が未規定**: P103が結合テストを実行する際、開発時のクロスオリジンCookie問題(実際に発生した)を解決するためのハーネス構成(プロキシの要否など)を、P003/ADRの知識を借りて場当たり的に決める必要があった。
* **CR却下時の優先度の扱いが未規定**: `docs/CR.md`の優先度列は高/中/低のみで「却下のため対象外」を表す値が無く、実行担当は便宜的に中を割り当てた。実害は無いが値の意味が曖昧。
* **初回リリース時のバージョン初期値が未規定**: `SKILL-P302-deliver.md`の版数更新方針はCR対応後の増分のみを扱い、初回リリース(0.x.x→1.0.0など)の基準が無い。今回は実行担当の判断で1.0.0とした。

いずれも実害は限定的で、次版(V1.0以降)で他の変更のついでに検討すればよいレベルと判断する。

## 4. 参考: 本ラウンドで検出された実際のアプリケーション不具合

* `CalendarPage.tsx`がログインユーザー名・ログアウト操作を表示していなかった(仕様漏れ)。
* 日付計算に`toISOString()`(UTC)を使っており、タイムゾーンによっては「今日」の判定がずれる。
* `sqlite3.connect()`に`check_same_thread=False`が無く、実サーバー環境で間欠的な500エラーが発生しうる(V0.8_testbedでも同型の欠陥を検出しており、独立に生成された別のコードベースで同種の欠陥が再発した=Skillの検証プロセスが再現性を持って機能していることの傍証)。
* アクセスログミドルウェアが失敗レスポンスの`error_code`を記録していなかった。
* CR-001の作業中、`Field(max_length=...)`のバリデーション失敗が独自の400/`VALIDATION_ERROR`契約ではなくPydantic既定の422を返す、CR-001と無関係の既存欠陥を発見(記録のみ、対応はスコープ外として次回送り)。
* `npm run build`(本番ビルド)がこの検証環境のNode.js/Windows組み合わせ固有のネイティブモジュール問題でクラッシュすることを確認したが、コード自体の欠陥ではなく環境要因と正しく切り分けて記録した(誤魔化さず正直に記録する、というSkillの規律が機能した一例)。

## 5. 総評

V0.9で解決した22件(低重大度20件+新規2件)は、実地で確認できた範囲すべてにおいて意図どおり機能した。特に、V0.8_testbedで唯一「部分検証」にとどまっていた1-3(テスト指示側の誤り区分)を、意図的な実例作成によって完全に検証できたことが本ラウンドの最大の成果である。これにより、V0.7_testbedが発見した高重大度5件はすべて、V0.8・V0.9の2バージョンを通じて実地で動作確認済みとなった。

新たに見つかった論点は5件、いずれも低重大度で実害は限定的。V0.7_testbedの44件の発見事項は、これで大部分(高5件・中28件・低20件の計33件を解決、残り低7件相当は判断により見送り・別カテゴリに整理済み)に対処したことになる。
