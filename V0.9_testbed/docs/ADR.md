# ADR.md

本プロジェクト(会議室予約システム)で現在有効な設計判断を管理する。
過去に廃止された設計判断は `ADR_master.md` に移動する(本バージョンでは廃止されたADRは無いため `ADR_master.md` は作成しない)。

* 1つの決定 = 1つの ADR-NNN とする。
* 「決定内容」「理由」は、後続のAI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。

```text
採用     現在この決定が有効である

廃止     過去に採用されたが現在は無効(本文はADR_master.mdへ移動済み)
```

## ADR-001

### タイトル

フロントエンド技術としてReact + TypeScript + Viteを採用する

### 状態

採用

### 日付

2026-08-11

### 関連要求

* REQ-SCREEN-001〜007(全画面)

### 背景

`docs/P001-requirement.md` で「フロントエンドで使う技術: React 18 + TypeScript + Vite」が要件として明示されている。本セッションはnpmレジストリ(registry.npmjs.org)への接続を確認できたため、要件どおりの技術を採用可能と判断した。

### 決定内容

フロントエンドはReact 18 + TypeScript + Viteで構築する。状態管理はReact標準機能のみとし、Redux等の追加ライブラリは導入しない(要件定義どおり、画面数が少ないため)。

### 理由

* 要件定義で明示的に指定されている。
* SPA(カレンダーのようなインタラクティブなUI)構築の実績が豊富。
* コンポーネント分割による画面再利用性が高い。

### 検討した代替案

#### Vue.js / Angular

却下。理由: 要件定義で明示的にReactが指定されており、代替を採る技術的必然性がないため検討のみで終了した。

#### サーバーサイドレンダリング(Next.js等)

却下。理由: 社内ツールでSEOやSSRの必要性が無く、Viteによる単純なSPA構成で要件を満たせるため。

### 残存リスク

なし(要件定義どおりの採用であり、意識的な割り切りを伴う決定ではないため★ACCEPTED★は付さない)。

### 影響範囲

* Frontend全体(`client/`)

### 関連成果物

* `docs/P001-requirement.md`
* `docs/P007-impl-direction.md`

### 備考

なし

## ADR-003

### タイトル

データアクセスに標準ライブラリsqlite3を直接使用する(ORM不使用)

### 状態

採用

### 日付

2026-08-11

### 関連要求

* REQ-API-001〜017(全API、データアクセスを伴うもの)

### 背景

`docs/P001-requirement.md` はデータストアとしてSQLiteを指定しているが、ORMの使用有無までは指定していない。本アプリの規模(300名・10会議室程度)ではクエリが単純であり、業務ロジック(特に予約重複判定)がSQLの条件式に直結するため、ORMの抽象化を経由せず素のSQLを直接記述する方針とした。

### 決定内容

`server/app/repositories/` 配下の各Repository関数は、標準ライブラリ `sqlite3` を用いてSQLを直接発行する。SQLAlchemy等のORMは導入しない。

### 理由

* SQLを明示管理でき、`docs/P003-backend-spec.md` §5.9の重複判定のような業務ロジックに直結するクエリの見通しが良い。
* 追加の外部依存を増やさない(標準ライブラリのみで完結する)。
* 想定データ量・クエリの複雑さの範囲では、ORMによる生産性向上効果が薄い。

### 検討した代替案

#### SQLAlchemy(ORM)

却下。理由: モデル定義とSQL発行の二重管理になり、`docs/P003-backend-spec.md` §5.9のような境界値を含む複雑な条件式をORMのクエリAPI経由で正確に表現する方が、素のSQLを書くより見通しが悪くなると判断したため。

### 残存リスク

★ACCEPTED★ 将来的にテーブル数・クエリの複雑さが増えた場合、素のSQL管理はORMに比べて保守コストが上がる可能性がある。本バージョンの規模(6テーブル程度)では許容範囲と判断し、この点は検討済みの割り切りとする。テーブル数・クエリ複雑度が大幅に増える変更要求が来た場合は、CRとして再検討する。

### 影響範囲

* Backend / Repository層 / Database

### 関連成果物

* `docs/P003-backend-spec.md`
* `docs/P007-impl-direction.md`

### 備考

なし

## ADR-004

### タイトル

パスワードハッシュにbcryptを採用する

### 状態

採用

### 日付

2026-08-11

### 関連要求

* REQ-NFR-003(セキュリティ、パスワードのハッシュ化)

### 背景

`docs/P001-requirement.md` の非機能要件で「パスワードはハッシュ化して保存する」ことが求められている。具体的なハッシュアルゴリズムは指定されていない。

### 決定内容

パスワードハッシュには `bcrypt`(PyPI配布パッケージ)を用いる。

### 理由

* パスワードハッシュ用途で広く実績があり、ソルトの取り扱いがライブラリ内に隠蔽されるため実装ミスのリスクが低い。
* PyPIへの接続が確認できたため、標準的な実績あるライブラリを追加依存として導入するコストは小さいと判断した。

### 検討した代替案

#### 標準ライブラリ`hashlib.scrypt`

却下。理由: `bcrypt`と同等の目的を果たせるが、本セッションはPyPIへの接続に成功しており外部ライブラリ導入の制約が無いため、より広く使われている`bcrypt`を優先した。ネットワーク接続が制約された環境であれば`hashlib.scrypt`が有力な代替となる(過去バージョンの `V0.7_testbed`/`V0.8_testbed` はこの制約下で`hashlib.scrypt`相当の代替を選んでいる)。

#### Argon2

却下。理由: `bcrypt`より新しく理論的には優れるが、本用途(300名規模の社内ツール)では`bcrypt`で要件を十分満たせ、追加の学習・検証コストに見合わないと判断した。

### 残存リスク

なし。

### 影響範囲

* Backend / 認証

### 関連成果物

* `docs/P003-backend-spec.md`
* `docs/P007-impl-direction.md`

### 備考

なし

## ADR-005

### タイトル

セッション管理をSQLite永続化+Cookie方式で実装する(JWT不採用)

### 状態

採用

### 日付

2026-08-11

### 関連要求

* REQ-API-001, REQ-API-002, REQ-API-003(ログイン/ログアウト/自分情報取得)
* REQ-NFR-002(可用性)

### 背景

`docs/P001-requirement.md` は認証を「社内アカウント(ID/パスワード)によるログイン必須」とのみ定めており、セッションの実現方式(JWT/サーバーサイドセッション、保存先)は指定していない。

### 決定内容

ログイン成功時にサーバー側で不透明なトークンを生成し、SQLiteの `sessions` テーブルに保存する。クライアントには `HttpOnly` Cookieでトークンのみを渡す(JWTのような自己完結型トークンは使わない)。

### 理由

* サーバー側にセッション状態を保持するため、ログアウト・強制失効が即座に反映できる(JWTは失効の仕組みが別途必要になる)。
* SQLiteへの永続化により、プロセス再起動やスケールアウト時にもセッションが失われない(`docs/P003-backend-spec.md` §7の可用性要件への配慮)。

### 検討した代替案

#### JWT(自己完結型トークン)

却下。理由: 失効の仕組み(ブラックリスト管理等)を別途実装する必要があり、本アプリの規模(300名)ではサーバーサイドセッションの方が単純で堅牢。

#### インメモリ(プロセス内)セッション保存

却下。理由: プロセス再起動のたびに全ユーザーが強制ログアウトされ、300名規模の社内ツールとして利用者影響が大きいため。

### 残存リスク

★ACCEPTED★ セッションテーブルの行数はログイン頻度に比例して増加し、期限切れセッションの物理削除は本バージョンでは行わない(参照時に無効判定するのみ)。実害が出るデータ量に達した場合は、バッチ削除の追加をCRとして検討する。

### 影響範囲

* Backend / 認証 / Database

### 関連成果物

* `docs/P002-frontend-spec.md`
* `docs/P003-backend-spec.md`

### 備考

なし
