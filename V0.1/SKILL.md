# 仕様駆動開発 (Spec-Driven Dev)

* 本格的なアプリケーションをコードを書く前に設計を行うための、使い回し可能なフェーズ・ワークフロー。
  * 各フェーズは、現在のプロジェクトの `docs/` 配下にMarkdown成果物を生成する。**1回の実行につき1フェーズだけ**進め、そこで止めてユーザーのレビューを待つこと。
  * 次フェーズに必要な情報が技術的に揃っていても、複数フェーズを一度に進めてはいけない。
  * 各フェーズは前フェーズの内容が正しいことを前提にしているため、レビューの区切りを飛ばすとこの手順の意味がなくなる。
* ソースコードの作成やテストの実施は、この SKILL が生成する Mardown (定義書、または定義書兼作業指示書) を別途実行して作成する。この SKILL 自体はソースコードやテストの実施を行うものではない。
* このワークフローは日本のシステム開発で標準的なソフトウェアの製造工程(ウォーターフォール/V字モデル)を実行する

|フェーズ|フェーズ名|

## 各フェーズ共通指示

* Markdown 内の図について
  * Markdown 内に図を作成する場合は Mermaid記法 で作成する
  * Agent 側で図の記述内容を類推できる場合は Agent 側で想定する図を作成する (人間に一から書かせない)
  * 図に関しては記述内容を評価しない
* 各フェーズで作成するドキュメントがない場合、あるいは不足する項目が多数にわたる場合は、ドキュメントのひな形を作るかどうかを人間に判断させる
  * 人間がひな形の提供を望んだ場合は、必要なアウトプット項目を網羅するひな形ドキュメントを作成する。項目に対する設定値は、Agent 側の想定をもとに作成し、末尾に "★FIXME★" を記載する。`docs/.inprogress` に、現在のフェーズ番号を記入する。
  * 人間が Agent とともにドキュメントを作り上げるのを望んだ場合は、Agent はアウトプット項目を記載するために人間に質問を行い、アウトプット文書を作り上げる。アウトプット文書が完成したら、`docs/.inprogress` に、次のフェーズ番号を記載する。
* 各フェーズで作成するドキュメントがあり、かつ不足する項目が小数な場合は、ドキュメントの記述内容の十分性を評価する。
  * 記述不足箇所がある場合、人間に対して、記述不足箇所を指摘して、それらを補完するための質問を人間に行い、アウトプット文書を作り上げる。アウトプット文書が完成したら、`docs/.inprogress` に、次のフェーズ番号を記載する。
  * 記述不足の箇所が無ければ、そのフェーズは完了とする
* 最後のフェーズが完了した場合は、`docs/.inprogress` を削除する

## ステップ0: どのフェーズを実行するか判定する

現在のプロジェクトの `docs/` を確認する:
* どのフェーズを実行するかを推定する
  * 9フェーズとも存在しない → **フェーズ1** の実行を仮確定
  * `docs/.inprogress` ファイルが存在する → ファイルに書かれている数字に対応するフェーズの実行を仮確定
  * 1が存在するが、2が存在しない → **フェーズ2** の実行を仮確定
  * 1,2が存在するが、3が存在しない → **フェーズ3** の実行を仮確定
  * 1,2,3が存在するが、4が存在しない → **フェーズ4** の実行を仮確定
  * 1,2,3,4が存在するが、5が存在しない → **フェーズ5** の実行を仮確定
  * 1,2,3,4,5が存在するが、6が存在しない → **フェーズ6** の実行を仮確定
  * 1,2,3,4,5,6が存在するが、7が存在しない → **フェーズ7** の実行を仮確定
  * 1,2,3,4,5,6,7が存在するが、8が存在しない → **フェーズ8** の実行を仮確定
  * 1,2,3,4,5,6,7,8が存在するが、9が存在しない → **フェーズ9** の実行を仮確定
  * 1,2,3,4,5,6,7,8,9が存在する → 全フェーズ完了済みを仮確定
* フェーズ1～9と工程名を一覧表示して、実行を仮確定しているフェーズを太字にする。そしてユーザにどのフェーズを実行するかを入力させて、どのフェーズを実行するかを確定する。
  * 未入力(Enterのみ) → 実効を仮確定したフェーズを実行
  * 1～9の数字を入力 → 対応するフェーズを実行
