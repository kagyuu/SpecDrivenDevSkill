# spec-driven-dev Skill V0.7 — フルパイプライン実地検証レポート

作成日: 2026-08-05

## これは何か

`spec-driven-dev` Skill V0.7 を、`docs/P001-requirement.md` を起点に **P002〜P302まで人間のレビューを挟まず連続実行**し、そのうえで **CR-001をP901〜P905のフルフローで処理**した実地検証の記録。

過去のテストヘッド(`V0.5_testbed`・`V0.6_testbed`)は、いずれも前バージョンのテストヘッドをコピーして `.claude/skills/` だけを差し替える差分検証だった。**V0.7_testbedは、V0.4_testbed以来はじめての「要件定義から全面再構築」による検証**である(ユーザー判断)。これにより、過去バージョンから引き継いだ成果物の影響を受けず、**V0.7のルールだけで作られた成果物**が得られている。

* V0.6→V0.7の変更内容: [`../V0.7/review-report.md`](../V0.7/review-report.md)
* CR運用変更の設計仕様: [`../CR運用変更仕様.md`](../CR運用変更仕様.md)
* 確認観点ごとの結果: [`testbed.md`](./testbed.md)

## 検証の構成

7ラウンドに分けて実施した。いずれも実際にコードを書き、実際にテストを実行している(シミュレーションではない)。

1. Plan Loop Step(P002〜P012)
2. Overview Step(P020〜P022)
3. Executor(P101〜P104、スプリントU001・U002)
4. Executor(スプリントU003・U004、P103・P104完了)
5. Reviewer Loop(P201〜P205)
6. Closing(P301〜P302)
7. Refactor(P901〜P905、CR-001)

題材は従来どおり会議室予約システム。過去のテストヘッドでCR-001〜CR-003として追加した3項目(S03の終日チェックボックス、S06の説明文、予約の参加予定人数)は、**最初から要件に含まれるもの**として要件定義書に取り込んだうえで再構築している。

サンドボックス制約(pypi.org / registry.npmjs.org へ接続不可)により、Starlette+Pydantic v2+stdlib sqlite3 / hashlib.scrypt / プレーンHTML+ES module JS / unittest / `node --test` で代替した。これはSkillの欠陥ではなく実行環境固有の制約であり、V0.4_testbed以来と同じ扱いとする(ADR-001〜003に記録済み)。

## 結果サマリ

**V0.7の3つの変更は、いずれも意図どおり機能した。** 特に中心的な変更であるCR運用の構造変更は、実際にCRを1件処理した結果、狙いどおりの効果を確認できた。

* **CR3ファイル構成の役割分離は成立した**。書きたい内容がどのファイルにも溢れず、判断の置き場が一意だった。
* **P904は実際に自明な作業になった**。V0.6では本文の移動と既存記法の複製を要し、それが2バージョンにわたって欠陥を生んでいたが、V0.7のP904で書き込んだのは**既存ファイル1つの1節と、台帳の1セルだけ**である。
* **★ACCEPTED★は繰り返し実際に機能した**。全7ラウンドで、既決着の論点の再提起を実際に止めた場面が複数あった(詳細は後述「★ACCEPTED★の評価」)。
* マイグレーション冪等性のルールは、V0.6_testbedのように「クラッシュしてから気づく」のではなく、**スコープ決定の段階で事前に検知**できた。

最終テスト件数: **486件、全PASS**(バックエンド262 + フロントエンド単体146 + フロントエンド結合46 + フロントエンド受け入れ32)。結合テストT001〜T019 全19件PASS、受け入れテストA001〜A012 全12件PASS。リリース判定は**保留**(Dockerデーモンが無く配布資産の動作未検証。Skillの規定どおりの判定)。

一方、全面再構築という検証方式が効いて、**過去の差分検証では踏まなかった箇所を多数通過した結果、V0.7に44件の不備・曖昧点を発見した(高5件・中22件・低17件)**。うち2件は**データ損失を伴う具体的な欠陥**である。致命的に処理続行不能なものは無かったが、件数が過去バージョンより大幅に多いのは、差分検証では通らないフェーズ(P020〜P022、P101〜P104、P201〜P205、P301〜P302の初回実行)を全て通したためである。

## 1. 高重大度の発見(5件)

### 1-1. ステップ0がタスク粒度の進捗を持たないため、フェーズ途中で中断すると再開できない — 重大度: 高

* **事象**: 本検証では実際にトークン上限でExecutorが**スプリントU001の途中で中断**した。再開時、`docs/.inprogress` は `P102` を指していたが、これは「P102の途中」以上の情報を持たない。P102の再開規則は「チェックボックスが `[ ]` の最初のスプリント」であり、U001は `[ ]` のまま、しかし6タスクのうち5タスク分のファイルが部分的に作られ、かつ `main.py` が壊れた状態(存在しないハンドラをimport)だった。
* SKILL.mdは「目次ドキュメント側でスプリント/テスト単位の細かい進捗を追跡できる」としているが、OKFチェックボックスは**スプリント単位**であり、P007自身の§4はスプリントファイル内に複数タスクを定義する。この粒度差により、**スプリント途中の中断は構造的に不可視**である。
* さらに悪いことに、中断した実行は**スコープ先行**していた(U002〜U004のハンドラ用ルートを先に書いていた)。再開担当は「先行して書かれたもの」と「完了したもの」を区別できない。
* **影響**: 再開担当は全タスクの完了条件を読み直し、テストを実行して状態を再構成する必要があった。実際にそうした。長時間実行されるパイプラインで中断は例外ではなく通常事象であり、この再構成コストは毎回発生する。

### 1-2. 結合テスト・受け入れテストの「コードを書く」フェーズが存在しない — 重大度: 高

* **事象**: P008/P009はテスト**指示書**を作る。`SKILL-P102-implement.md` は「ここで行うのはコードの実装と単体テストのみである」。`SKILL-P103-integration-test.md` は「T0NN に記載された手順どおりにテストを**実行**する」とし、禁止事項に「テストコードをその場で都合よく変更しない」を挙げ、アウトプットは `docs/test-records/*.md` のみ。**`tests/integration/test_t001_*.py` を誰が書くのかが、どのフェーズにも定義されていない。**
* この欠落はP201で最も深刻になった。`SKILL-P201-review.md` のアウトプット文書は `P201-review-report.md` とテスト記録の2つだけだが、A001の【実行コマンド】は実在しないファイルを指す。実行担当は**2,709行のテストコードを、成果物がMarkdown2枚と宣言されているフェーズの中で書いた**。
* **影響**: 3ラウンド(Executor・Reviewer Loop・Refactor)すべてで再現した。CRのたびに毎回踏む。さらに、P103の「テストコードを都合よく変更しない」という禁止と「新しいテストIDのコードを新規に書く必要がある」ことが同一フェーズ内で緊張する。実行担当がT016のテストを書く過程で自分のテストのバグと本物の仕様矛盾の両方に遭遇したが、外から見ると「自分のテストのバグを直した」と「本物の欠陥を隠すために期待値を書き換えた」は区別できない。低能力のモデルが実行した場合、本物の欠陥を静かに「修正」しうる。

### 1-3. P202に「テスト指示そのものが誤っていた」という一級の結果区分が無い — 重大度: 高

* **事象**: 本検証では、テスト指示側が誤っている失敗が**2件**発生した。T016(サーバ側400を期待するが、P002 §3.3はクライアント側検証でAPIを呼ばないと定めている)と、A001(13:00-13:30の予約が13:00と13:30の両方を占有すると期待するが、ADR-007は半開区間 `[start, end)` を採用しており、A001自身の手順8は半開区間と整合している=文書内で自己矛盾)。
* この扱いは、P202の「修正成功時は関連する docs/* も更新する」という**副作用の一項目**として埋まっているだけである(「テスト指示や期待結果に誤りがあった → `docs/P009-acceptance-direction.md` …を修正する」)。一級の結果区分ではない。
* 帰結が3つ出た。(1) `TEMPLATE-P202-fix-resolved.md` の「変更したソースコード:」が必須フィールドで「なし」を想定しておらず、「アプリケーションコードの差分0」と書く場所がない。`TEMPLATE-P202-fix-direction.md` の【ロールバック条件】も完全にソースコード前提。(2) `SKILL-P205-integration-retest.md` は「**期待値改ざん禁止**」を掲げるが、実行中の修正そのものが期待値の変更だった。**改ざん(合格させるための弱体化)と訂正(上位仕様に合わせた是正)を区別する記述がV0.7に無い**。実行担当はこの区別を発明し、各修正ファイルで証拠(上位文書の引用+カバレッジが失われていないことの確認)をもって弁護した。(3) P103にはこの判定を置く場所が無いため延期しかできず、延期先も受け止める形になっていない。
* **推奨**: P202に「テスト指示の誤り」を明示的な結果区分として設け、証拠要件(上位文書を引用し、カバレッジが失われないことを示す)を課す。`TEMPLATE-P202-fix-resolved.md` に「変更なし(仕様側が正)」の分岐を追加する。

### 1-4. P902完了直後に中断すると、要件定義書の原本バックアップが失われる — 重大度: 高(具体的欠陥)

* **事象**: `SKILL-P902-requirement-update.md` は「状態列(`docs/CR.md`)の `対応中` への更新は、P903が着手時に行う。本フェーズでは状態を変更しない」と定める。一方ステップ0は「`docs/CR.md` に状態が `未対応` のCRの行がある → そのCRについて **P902** から開始する」。
* したがって**P902完了直後**(`docs/P001-requirement.md` は既に更新済み、台帳はまだ `未対応`)にセッションが切れると、再開時にP902がもう一度実行される。P902のバックアップ手順は「更新前の `docs/P001-requirement.md` を `docs/P001-requirement_{YYYYMMDD}_{CR番号}.md` にコピー」であり、ファイル名は日付+CR番号なので**必ず同名衝突する**。結果、**既に更新済みのP001でバックアップを上書きし、原本が失われる**。
* V0.5でわざわざCR番号を命名に加えて衝突を防いだ(defect 2-9)にもかかわらず、この経路では衝突が保護にならない。
* **推奨**: P902が着手時に台帳を `対応中` に更新する、またはバックアップ先が既に存在する場合は上書きしない、のいずれか。

### 1-5. `docs/.inprogress` がRefactor中の位置を表現できず、ステップ0の判定順序と衝突する — 重大度: 高

* **事象**: P903はP002〜P302を内部で再実行するが、`.inprogress` は「現在実行中のフェーズ番号」1値のみを持つ。実行担当は内側の番号(P002…P302)を書いたが、これでは「P903の内側である」情報が消える。
* ステップ0の**第1条件**「`docs/.inprogress` が存在する → そこに記録されたP番号から再開する」は台帳チェックより**先に**評価される。したがって `.inprogress=P006` かつ `CR.md=対応中` の状態で再開すると、**CRを読まずに通常のPlan Loopとして再開する**。CRの内容を反映しない全面書き直しになりうる。
* **推奨**: `P903:P006` のような入れ子表記にするか、ステップ0で台帳を先に評価する順序にする。1-1(タスク粒度)のRefactor版だが、実害はこちらが大きい。

## 4. V0.7の3つの変更に対する評価

### 4-1. 変更点1(CR運用の構造変更)— 意図どおり機能した

## 6. 総評

V0.7の3つの変更は、いずれも実地で意図どおり機能した。特にCR運用の構造変更は、V0.5・V0.6が2バージョンにわたって文言修正で塞いできた欠陥クラスを、実際に構造ごと消していることを確認できた(P904が自明な作業になったことがその証拠である)。★ACCEPTED★も、既決着の論点の再提起を実際に止めるという狙いを果たした。

一方、44件という発見件数は過去バージョンより大幅に多い。これはV0.7が劣化したのではなく、**検証方式を「差分」から「全面再構築」に変えた結果、差分検証では一度も通らなかったフェーズ(P020〜P022・P101〜P104・P201〜P205・P301〜P302の初回実行)を全て通したため**である。実際、発見の多くは V0.4 以来ずっと存在していたはずの潜在的な不備であり、V0.7で新たに作り込まれたものは★ACCEPTED★関連の3件(2-5・2-6・2-7)と、CR構造変更に伴う4件(1-4・1-5・3-18・3-20)に限られる。全面再構築という検証方式の判断は、この意味で正しかった。

発見のうち特に対処を推奨するのは、**データ損失を伴う 1-4**、**CRを無視した再開を招く 1-5**、そして**テスト指示の誤りという類型を扱えない 1-3** である。1-1(中断からの再開)と 1-2(テストコードの作者が未定義)は、いずれもV0.4以来の構造的欠落であり、対処には設計判断を要する。
