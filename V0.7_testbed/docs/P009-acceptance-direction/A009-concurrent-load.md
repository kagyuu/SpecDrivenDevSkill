# 【テストID】A009 — 同時接続の負荷

## 【目的】

* P001の「ピーク時に同時30接続程度」という前提のもとで、エラー応答(5xx)が発生しないことを確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 3.2 V-N-02、4.3
* 仕様: `docs/P001-requirement.md` 非機能要件(想定同時利用者数)、`docs/P003-backend-spec.md` 4.5(WAL・ロックタイムアウト)、5.3

## 【対象モジュール】

* `main.py`、`db.py`、`handlers/*`

## 【前提条件】全モジュールビルドが成功していること

* 第2章のビルドコマンドが終了コード0で完了していること。

## 【使用するテストデータ】

* ユーザー10名(全員ログイン済みセッションを保持)、会議室10室、1週間分の予約100件程度。

## 【事前準備】

1. DBファイルを削除し、上記データを投入してサーバーを起動する。
2. 10名分のセッションCookieを取得しておく。
3. 負荷ツールは導入できないため、標準ライブラリのスレッド(またはプロセス)で同時実行を作る。

## 【実行手順】

1. **参照系**: 30スレッドから同時に `GET /api/reservations`(1週間分)を各3回、合計90リクエスト送る。
2. すべての応答ステータスと所要時間を集計する。
3. **更新系**: 30スレッドから、**互いに重ならない時間帯・会議室**に対する `POST /api/reservations` を同時に1回ずつ送る。
4. 応答ステータスとDBの予約件数を確認する。
5. サーバーログに `DB_LOCK_TIMEOUT` が出ていないかを確認する。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.acceptance.test_a009_concurrent_load -v`

## 【期待結果】

* 手順2: **5xxが0件**。すべて200。
* 手順4: 30件すべてが201で、DBの予約が30件増える(重ならないため409は発生しない)。
* 手順5: `DB_LOCK_TIMEOUT` が0件。

## 【合否判定基準】

* 5xxが1件でも出た場合はFAIL。409(重複)はこのテストでは発生しない設計なので、発生した場合もFAILとして原因を記録する。
