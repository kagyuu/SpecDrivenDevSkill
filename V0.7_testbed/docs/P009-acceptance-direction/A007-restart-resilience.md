# 【テストID】A007 — 再起動耐性とデータ永続(運用観点・必須)

## 【目的】

* **同一のデータベースファイルに対してアプリケーションプロセスを停止・再起動しても正常に起動し、既存データが失われないこと**を確認する。マイグレーション方式が冪等でない場合、2回目以降の起動で失敗してアプリが立ち上がらなくなるが、この欠陥は毎回新しい一時DBを作る単体テスト・結合テストでは検出できないため、独立したテストとして必ず実施する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` **3.3 V-O-01 / V-O-02(運用観点)**、3.2 V-N-08、4.3
* 仕様: `docs/P003-backend-spec.md` 3.5(マイグレーション方式・冪等性)、3.6(初期管理者シード)

## 【対象モジュール】

* `db.py`(`apply_migrations` / `seed_initial_admin`)、`main.py` の起動処理、`server/migrations/*.sql`

## 【前提条件】全モジュールビルドが成功していること

* 第2章のビルドコマンドが終了コード0で完了していること。

## 【使用するテストデータ】

* 初期管理者(環境変数)、基準データセット、`user001` の予約1件。

## 【事前準備】

1. **DBファイルを削除する。このテストは以降、同じDBファイルを使い回す(他のテストのように途中で作り直さない)。**

## 【実行手順】

1. サーバーを起動する。`schema_migrations` の行数、`users` の行数を記録する。
2. 基準データセットと `user001` の予約1件を投入する。
3. サーバーを停止する(SIGTERM)。
4. **同じDBファイルのまま**サーバーを起動する。
5. 起動ログにエラーが無いことを確認し、`schema_migrations` と `users` の行数を再確認する。
6. `user001` でログインし、手順2で作った予約が `GET /api/reservations/mine` で取得できることを確認する。
7. 手順3〜6をもう一度繰り返す(合計3回起動)。
8. WALファイル(`*.db-wal` / `*.db-shm`)が残っている状態で停止・起動しても問題ないことを確認する。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.acceptance.test_a007_restart_resilience -v`

## 【期待結果】

* 手順4・7: **エラーなく起動する**(`duplicate column name`、`table already exists` 等で異常終了しない)。
* 手順5: `schema_migrations` の行数が手順1から**増えていない**。初期管理者が二重に作られていない。
* ※CR-001: `004-meeting-url.sql`(`ALTER TABLE reservations ADD COLUMN`)が追加されたため、手順1で記録する `schema_migrations` の行数は **4** である。手順4・7でこの行数が増えず、かつ `duplicate column name: meeting_url` が発生しないことをもって、`ADD COLUMN` を含む差分適用が冪等であることの確認とする。★ACCEPTED★ この「2回以上起動して成功する」基準は冪等性の必要条件であって十分条件ではない(`SKILL-P903-refactor-execute.md` の同名の★ACCEPTED★と同じ論点)。より強い検証(適用済み判定の仕組みの説明、エラー捕捉スコープの確認)は費用に見合わないと判断して行わない。適用済み判定が `schema_migrations` による**事前スキップ**であり、エラー捕捉による読み飛ばしではないことは `docs/P003-backend-spec.md` 3.5 が設計として明記しており、そちらが担保する。
* 手順6: 予約・ユーザー・会議室のデータがすべて残っている。
* 手順8: 起動に成功する。

## 【合否判定基準】

* 2回目・3回目の起動がいずれも成功し、データが保持され、`schema_migrations` の行数が増えていなければPASS。
