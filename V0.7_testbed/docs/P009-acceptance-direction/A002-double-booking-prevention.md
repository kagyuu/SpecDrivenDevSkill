# 【テストID】A002 — 二重予約の防止

## 【目的】

* P001が解決すべきとした「二重予約」が、逐次リクエストでも並行リクエストでも発生しないことを、システムレベルで確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 3.1 V-F-07、4.3。`docs/P001-requirement.md` テスト方針(重複チェックの重点確認)
* 仕様: `docs/P003-backend-spec.md` 5(重複チェックと排他制御)

## 【対象モジュール】

* `services/reservation_service.py`、`repositories/reservations_repo.py`、`db.py`(`BEGIN IMMEDIATE`)

## 【前提条件】全モジュールビルドが成功していること

* 第2章のビルドコマンドが終了コード0で完了していること。

## 【使用するテストデータ】

* 会議室A、日付「本日+1日」、時間帯 10:00-11:00。利用者 `user001` / `user002`。

## 【事前準備】

1. DBファイルを削除し、基準データセットを投入してサーバーを起動する。
2. `user001` と `user002` の両方でログインし、それぞれのCookieを保持する。

## 【実行手順】

1. `user001` で 10:00-11:00 を登録する。
2. `user002` で同じ会議室・同じ日・10:30-11:30 を登録する。
3. DBの `reservations` の件数を確認する。
4. DBを初期状態に戻す(予約0件)。
5. `user001` と `user002` から、**同一の会議室・日付・時間帯(10:00-11:00)への登録を同時に**送信する(スレッドまたはプロセスを2つ使い、送信タイミングを揃える)。
6. 2つの応答と、DBの `reservations` の件数を確認する。
7. 手順5を、同時実行数を5に増やして繰り返す。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.acceptance.test_a002_double_booking -v`

## 【期待結果】

* 手順1: 201。
* 手順2: 409 `RESERVATION_CONFLICT`。
* 手順3: 1件。
* 手順6: **一方が201、他方が409。DBは1件のみ。** 両方成功(2件)になってはならない。500(ロックタイムアウト)も許容しない。
* 手順7: 5本のうち**ちょうど1本が201、残り4本が409**。DBは1件のみ。

## 【合否判定基準】

* 手順3・6・7でDBの件数がいずれも1件であり、成功応答がちょうど1件であればPASS。2件以上作られた場合はFAIL(重大度「高」)。
