# 【テストID】A011 — 利用者視点の受け入れシナリオ

## 【目的】

* 一般社員が、画面の表示だけを頼りに「空きを探す → 予約する → 内容を直す → 取り消す」を完了できること、およびP001が挙げた課題が解消されていることを、発注者・利用者の視点で確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 4.4(受け入れテスト)、3.1 V-F-15
* 仕様: `docs/P001-requirement.md` アプリケーションの概要(解決する課題)

## 【対象モジュール】

* 全画面・全API

## 【前提条件】全モジュールビルドが成功していること

* 第2章のビルドコマンドが終了コード0で完了していること。

## 【使用するテストデータ】

* 基準データセット。会議室3室、既存予約数件。

## 【事前準備】

1. DBファイルを削除し、基準データセットを投入してサーバーを起動する。

## 【実行手順】

1. `user001` でログインし、**S02だけを見て**、翌営業日に会議室Aが空いている時間帯を特定できるか確認する。
2. 空きセルから予約を作成する(件名・参加予定人数を入力)。
3. 誤って重複する時間帯を選んだ場合に、**何が問題かが画面のメッセージから分かる**か確認する。
4. 作成した予約をS05から見つけ、S04で時間帯を変更する。
5. 変更後、S02に変更が反映されていることを確認する。
6. 予約を取り消し、S02とS05の両方から消えることを確認する。
7. 以下を**手動確認**として実施し、結果を記録する(自動テストでは検証できないため)。
   * ブラウザで実際に表示したときに、グリッドの列・行が崩れずに読めるか。
   * ボタン・リンクが実際のクリックで反応するか。
   * エラーメッセージが画面のどこに出るか(入力欄の近くか)。

## 【実行コマンド】

* `cd client && node --test tests/acceptance/test_a011_user_acceptance.js`(手順1〜6)
* 手順7は手動確認。実施できない環境の場合は **NOT RUN** として理由を記録する。

## 【期待結果】

* 手順1: 空き/予約済みが視覚的に区別でき、予約済みには予約者名と件名が出ている。
* 手順2: 入力から登録完了までがS03だけで完結する。
* 手順3: 「選択した時間帯はすでに予約されています。」と競合時間帯が表示され、次に何をすればよいかが分かる。
* 手順4〜6: 変更・取消が2画面に矛盾なく反映される。
* 手順7: 崩れ・無反応がない(または、あれば具体的に記録される)。
* **P001の課題との対応**: 二重予約(手順3で防止)、空き状況が分からない(手順1で解消)、変更・取消の連絡漏れ(手順5・6でS02/S05の最新状態から確認できる)。★FIXME★ 通知機能は要件に存在しないため、「最新状態を随時確認できること」をもって代替確認とする(`docs/P002-frontend-spec.md` 8章 指摘#3)。
