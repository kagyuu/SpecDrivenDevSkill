# 【テストID】T004 — 既存DBに対する再起動とマイグレーション差分適用

## 【目的】

* **Sprint 1 の起動処理とDBの連携**を確認する。具体的には、同じデータベースファイルを使い回してアプリケーションを2回以上起動しても、マイグレーションが差分適用され(2回目以降は何も適用されず)、エラーなく起動できることを確認する。単体テストは毎回新しい一時DBを作るため、この欠陥はDBファイルを使い回すテストでしか検出できない。
* **役割分担**(※P011矛盾点#2にもとづき明記): 本テストが対象とするのは Sprint 1 に含まれるマイグレーション(`001-init.sql`)と初期管理者シードだけである。**システムレベルの再起動耐性・データ永続(`docs/P006-test-plan.md` 3.3 の V-O-01 / V-O-02)は `docs/P009-acceptance-direction/A007-restart-resilience.md` が正式に担当する。** 本テストはその前倒しの早期検出であり、A007の代替ではない。

* `docs/P006-test-plan.md` 4.2(Sprint 1 の「起動処理とDBの連携」)、および 3.3(V-O-01 / V-O-02 の役割分担の記載)

## 【実行手順】

1. サーバーを起動し、起動に成功することを確認する。`schema_migrations` の行数と `users` の行数を記録する。
2. サーバーを停止する。
3. **同じDBファイルのまま**サーバーを再度起動する。
4. `schema_migrations` の行数と `users` の行数を再度確認する。
5. 起動後に `POST /api/auth/login` で初期管理者としてログインできることを確認する。
6. サーバーを停止し、3回目の起動を行う。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.integration.test_t004_restart_migration -v`

## 【期待結果】

* 手順1: 起動成功。`schema_migrations` の行数がマイグレーションファイル数と一致。`users` に初期管理者が1件。
* 手順3: **エラーなく起動する**(`duplicate column name` 等で異常終了しない)。
* 手順4: `schema_migrations` の行数が**手順1から増えていない**。`users` の初期管理者も1件のまま(シードが二重に走らない)。
* 手順5: 200でログインできる。
* 手順6: 3回目も起動に成功する。

## 【合否判定基準】

* 2回目・3回目の起動がいずれも成功し、`schema_migrations` と `users` の行数が増えていなければPASS。1つでも満たさなければFAIL(このFAILは重大度「高」として記録すること)。
* 本テストがPASSしても、システムレベルの再起動耐性(データ永続を含む)はA007で改めて確認する。本テストの結果をもってA007を省略しないこと。
