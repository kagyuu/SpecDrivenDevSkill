# 【テストID】T012 — 予約の重複検出と境界時刻

## 【目的】

* 同一会議室・同一日での時間帯の重なりが 409 `RESERVATION_CONFLICT` として検出され、境界が接するだけの予約は許可されることを、API経由で確認する。更新時に自分自身が競合扱いされないことも確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 4.2(Sprint 3)、3.1 V-F-07
* 仕様: `docs/P003-backend-spec.md` 5.1・5.2・5.3、`docs/P002-frontend-spec.md` 5.7(409の応答形式)

## 【対象モジュール】

* `services/reservation_service.py`、`repositories/reservations_repo.py`(`find_conflicts`)

## 【前提条件】対象スプリントの全モジュールビルドが成功していること

* Sprint 3 の単体テストが全件PASSしていること。

## 【使用するテストデータ】

* 会議室A、日付「本日+1日」。既存予約: 10:00-11:00(`user001`)。

## 【事前準備】

1. DBファイルを削除し、サーバーを起動し、基準データセットを投入する。
2. `user001` でログインし、既存予約(10:00-11:00)を1件登録する。

## 【実行手順】

1. 同じ会議室・同じ日で 10:00-11:00 を登録する。
2. 10:30-11:30 を登録する。
3. 09:30-10:30 を登録する。
4. **11:00-12:00** を登録する。
5. **09:00-10:00** を登録する。
6. 会議室Bで 10:00-11:00 を登録する。
7. 「本日+2日」に会議室Aで 10:00-11:00 を登録する。
8. 手順4で作った予約(11:00-12:00)を、時間帯を変えずに件名だけ変更する `PUT` を行う。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.integration.test_t012_reservation_conflict -v`

## 【期待結果】

* 手順1〜3: すべて 409 `RESERVATION_CONFLICT`。本文の `error.conflicts` に既存予約の `reservation_id` / `start_time` / `end_time` が含まれる。
* 手順4・5: **201(境界が接するだけなので重複しない)**。
* 手順6・7: 201(会議室違い・日付違い)。
* 手順8: **200(自分自身は競合として扱わない)**。

## 【合否判定基準】

* 上記すべてが一致すればPASS。手順4・5・8のいずれかが409になる場合はFAIL(重複判定に `<=` を使っている、または自己除外が漏れている可能性が高い)。
