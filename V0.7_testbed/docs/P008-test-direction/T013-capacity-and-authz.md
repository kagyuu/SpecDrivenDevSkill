# 【テストID】T013 — 収容人数超過と予約の認可

## 【目的】

* 参加予定人数が会議室の収容人数を超える場合に 400 `CAPACITY_EXCEEDED` となること、および予約者本人でも管理者でもない利用者が予約を更新・取消できないことを確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 4.2(Sprint 3)、3.1 V-F-05 / V-F-09
* 仕様: `docs/P002-frontend-spec.md` 3.3・5.7、`docs/P003-backend-spec.md` 6.4

## 【対象モジュール】

* `services/reservation_service.py`(`_validate_business`)、`auth.py`(`require_owner_or_admin`)

## 【前提条件】対象スプリントの全モジュールビルドが成功していること

* Sprint 3 の単体テストが全件PASSしていること。

## 【使用するテストデータ】

* 会議室B(収容4)、会議室C(無効)、`user001`(予約者)、`user002`(第三者)、`admin001`(管理者)。
* **時間帯**(※P011矛盾点#4にもとづき明記): 事前準備で作る既存予約は「本日+1日」**13:00-14:00**、実行手順1〜3・5で新規に登録する予約は「本日+1日」**16:00-17:00** を用いる(既存予約と重ならないようにして、収容人数超過の検証が重複エラーに紛れないようにするため)。手順5の過去日のケースのみ「本日-1日」16:00-17:00 とする。

## 【事前準備】

1. DBファイルを削除し、サーバーを起動し、基準データセットを投入する。
2. `user001` で会議室Bに「本日+1日」13:00-14:00 の予約を1件作る。

## 【実行手順】

1. `user001` で、会議室B・「本日+1日」16:00-17:00 に `attendee_count=5` の予約を登録する。
2. 同じ会議室・同じ時間帯で `attendee_count=4` にして登録する。
3. 手順2で作った予約を取り消したうえで、同じ枠に `attendee_count=0` で登録し、次に `attendee_count` 未指定で登録する。
4. 無効な会議室C を指定して(「本日+1日」16:00-17:00)登録する。
5. 会議室B・「本日-1日」16:00-17:00 で登録する。
6. `user002` のセッションで、**事前準備で作成した `user001` の予約(13:00-14:00)** を `PUT` する。
7. `user002` のセッションで、同じ予約を `DELETE` する。
8. `user002` のセッションで、同じ予約を `GET` する。
9. `admin001` のセッションで、同じ予約を `PUT` および `DELETE` する。

## 【実行コマンド】

* `cd server && python3 -m unittest tests.integration.test_t013_capacity_and_authz -v`

## 【期待結果】

* 手順1: 400 `CAPACITY_EXCEEDED`。メッセージに収容人数(4)が含まれる。
* 手順2: 201(境界値。収容人数ちょうどは許可)。
* 手順3: `0` は 400 `VALIDATION_ERROR`、未指定は 201(任意項目)。
* 手順4: 400 `VALIDATION_ERROR`(`details[].field == "room_id"`)。
* 手順5: 400 `VALIDATION_ERROR`(`field == "reserved_date"`)。
* 手順6・7: **403 `FORBIDDEN`**。DBの予約が変化していない。
* 手順8: 200(閲覧は全ログインユーザーに許可)。
* 手順9: 200 / 204(管理者は他人の予約を操作できる)。

## 【合否判定基準】

* 上記すべてが一致すればPASS。手順6・7が成功する場合はFAIL(重大度「高」)。
