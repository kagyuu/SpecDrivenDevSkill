# 【テストID】T016 — S02→S03の値の引き継ぎと登録完了

## 【目的】

* S02の空きセルクリックからS03へ値が引き継がれ、登録が成功するとS02へ戻ること、重複・収容人数超過のエラーが所定の位置に表示されることを確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` 4.2(Sprint 4)、3.1 V-F-11 / V-F-12 / V-F-14
* 仕様: `docs/P002-frontend-spec.md` 3.3・2.4・4・5.7

## 【対象モジュール】

* `client/src/views/s03-reservation-new.js`、`client/src/components/reservation-form.js`、`client/src/views/s02-calendar.js`、`client/src/lib/validation.js`(※CR-001)

## 【前提条件】対象スプリントの全モジュールビルドが成功していること

* Sprint 4 のクライアント単体テストが全件PASSしていること。

## 【使用するテストデータ】

* 会議室A(収容10)、会議室B(収容4)。既存予約: 「本日+1日」会議室A 10:00-11:00。

## 【事前準備】

1. DBファイルを削除し、サーバーを起動し、基準データセットと既存予約を投入する。
2. `user001` でログインする。

## 【実行手順】

1. S02で「本日+1日」会議室A 14:00 の空きセルをクリックし、S03の初期値を確認する。
2. 終日チェックボックスをONにする。
3. 開始時刻を手動で 10:00 に変更する。
4. 件名を入力せずに「登録」を押す。
5. 件名「打合せ」を入力し、参加者候補のプルダウンが取得できていることを確認する。
6. そのまま登録する(会議室A 10:00-18:00 は既存予約と重複する)。
7. 開始 14:00 / 終了 15:00 に直し、参加予定人数に 11(会議室Aの収容人数10を超える値)を入れて登録する。
8. 参加予定人数を 5 に直して登録する。
9. ※CR-001: 続けて別の空きセル(会議室A 16:00)からS03を開き、オンライン会議URLに `example.com/meet`(スキームなし)を入れ、件名を入力して「登録」を押す。
10. ※CR-001: オンライン会議URLを `https://example.com/meet/t016` に直して「登録」を押す。

## 【実行コマンド】

* `cd client && node --test tests/integration/test_t016_create_flow.js`

## 【期待結果】

* 手順1: 会議室A・日付「本日+1日」・開始 14:00・終了 14:30 が初期値になっている。
* 手順2: 開始 09:00 / 終了 18:00 が自動入力される。
* 手順3: 開始が 10:00 のまま保持され、チェックは自動で外れない。
* 手順4: APIが呼ばれず、件名欄の直下に「件名を入力してください。」が表示される。
* 手順5: `GET /api/users?scope=attendee_candidates` の結果が候補として描画されている(一般ユーザーでも取得できる)。
* 手順6: 409 が返り、重複エラー領域に「選択した時間帯はすでに予約されています。」と競合時間帯(10:00-11:00)が表示される。画面はS03のまま。
* 手順7: **`POST /api/reservations` は呼ばれず**、参加予定人数欄の直下に「参加予定人数が会議室の収容人数(10名)を超えています。」が表示される。画面はS03のまま。
  * 根拠: `docs/P002-frontend-spec.md` 3.3 は「参加予定人数の検証タイミング」を「会議室選択の変更時と**送信時にクライアント側で検証する**」と定め、同 2.4 は「クライアント側バリデーション違反ではAPIを呼ばない」と定める。同 7.2 のシーケンス図もクライアント側検証をPOSTの前に置き、400の分岐に「収容人数超過(**サーバー側検出**)」と明記している。したがって会議室が選択済みで収容人数超過が確定しているケースでは、APIには到達しない。
  * 同 3.3 の「表示項目」は収容人数超過エラーメッセージ領域を「**400 `CAPACITY_EXCEEDED` 時**」の表示先と定めており、クライアント側検証のメッセージは項目表どおりフィールド単位で表示する。
  * **サーバー側の 400 `CAPACITY_EXCEEDED` は `docs/P008-test-direction/T013-capacity-and-authz.md` 手順1 が API レベルで確認する**ため、本手順の変更で被覆は欠落しない。
  * ★この期待結果は Reviewer Loop の修正タスク F001(`docs/P202-fix-plan/fixed/F001-t016-capacity-expectation.md`)で修正した。修正前は「400 `CAPACITY_EXCEEDED` が返り、収容人数超過エラー領域に表示される」であり、P002 3.3 の規定と両立しなかった(`docs/P007-impl-direction.md` 5章 #18)。
* 手順8: 201。`#/calendar` へ戻り「予約を登録しました。」が表示され、S02のグリッドに新しい予約が現れる。
* 手順9(※CR-001): **`POST /api/reservations` は呼ばれず**、オンライン会議URL欄の直下に「オンライン会議URLは http:// または https:// で始まるURLを入力してください。」が表示される(クライアント側検証違反ではAPIを呼ばない。P002 2.4)。画面はS03のまま。
* 手順10(※CR-001): 201。送信ボディの `meeting_url` が `https://example.com/meet/t016` であり、`#/calendar` へ戻り「予約を登録しました。」が表示される。
