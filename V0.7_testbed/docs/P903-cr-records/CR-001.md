### マイグレーション方式の確認(「データモデル変更」に該当する場合のみ)

* `docs/P003-backend-spec.md` に記載されている適用方式: **差分適用型**(3.5「スキーマの適用方式」)。`server/migrations/*.sql` をファイル名昇順に走査し、`schema_migrations`(P003 3.3)に未記録のファイルのみを適用する。1ファイル = 1トランザクションで、ファイル内の全SQLの実行と `INSERT INTO schema_migrations` を同一トランザクションにまとめる。実装は `server/src/meeting_room/db.py` の `apply_migrations()`。ADR-009 が根拠。
* その方式は冪等か: **冪等である。** P003 3.5 が「冪等かどうか」の項で明記しており、根拠は「同じマイグレーションが2回以上『実行対象になる』ことがない(手順3で `schema_migrations` により除外される)」ため。したがって `ALTER TABLE ... ADD COLUMN`(SQLiteに `ADD COLUMN IF NOT EXISTS` は無い)を新規ファイル `004-*.sql` として追加しても、2回目以降の起動で `duplicate column name` にならない。コード(`db.py: apply_migrations`)を読んでも、適用済み判定は `version in applied` によるファイル単位の**事前スキップ**であり、「エラーを捕捉して読み飛ばす」方式ではないことを確認した。
* 冪等でない場合、冪等化を本CRの対応範囲に含めるか、その判断理由: **該当なし(既に冪等であるため、冪等化作業は本CRの対応範囲に含めない)。** ただし「冪等である」という設計上の主張が実際に成り立つことを、`SKILL-P903-refactor-execute.md` の規定どおり **初期化処理を2回連続で実行して2回目も成功すること**で確認し、結果をテスト記録に残す(既存の結合テスト T004「既存DBに対する再起動とマイグレーション差分適用」および受け入れテスト A007「再起動耐性」が同じ観点を持つため、これらも `004-*.sql` 追加後に再実行する)。
* 遵守事項: 適用済みのマイグレーションファイル(`001-init.sql` / `002-rooms.sql` / `003-reservations.sql`)は**編集しない**。列追加は新規ファイル `004-meeting-url.sql` で行う(P003 3.5「マイグレーションファイルの作法」)。
