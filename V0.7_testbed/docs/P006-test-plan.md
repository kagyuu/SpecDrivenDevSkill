### 3.3 運用観点(再起動耐性) — 必須

| 観点ID | 観点 | 実施レベル | 判定基準 |
| --- | --- | --- | --- |
| V-O-01 | **同一のデータベースファイルに対してアプリケーションプロセスを停止・再起動しても、正常に起動すること** | システムテスト(独立観点) | 1回目の起動でマイグレーションが適用され、**2回目以降の起動でもエラーなく起動し、リクエストを処理できる**こと |
| V-O-02 | マイグレーションの差分適用が働いていること | システムテスト | 2回目の起動時に `schema_migrations` の行数が増えないこと。新しいマイグレーションファイルを追加した場合はそれだけが適用されること |

* ※CR-001: 本CRで `004-meeting-url.sql`(`ALTER TABLE ... ADD COLUMN`)を追加したため、V-O-01・V-O-02 は**本CRの対応範囲でも必ず再実行する**(`ADD COLUMN` は `IF NOT EXISTS` を持たないため、差分適用が働かなければ2回目の起動で `duplicate column name` になる。まさにこの観点が守るべき変更である)。

* **担当するテストレベルと、結合テストとの役割分担**(※P011矛盾点#2にもとづき明記): V-O-01・V-O-02 の正式な担当は**システムテスト**であり、`docs/P009-acceptance-direction.md` の独立したテストタスク(A007)が実施する。これとは別に、`docs/P008-test-direction.md` のT004(Sprint 1)は「**起動処理とDBの連携、すなわちマイグレーションが差分適用されること**」を、問題を最も早い段階で検出する目的で確認する。T004はSprint 1に含まれるマイグレーションだけを対象とし、データ永続やスプリント横断のデータ確認は行わない。したがって両者は重複ではなく、**T004 = Sprint 1 の起動処理の確認 / A007 = システムレベルの再起動耐性とデータ永続の確認**という役割分担である。
* **この観点を独立に設ける理由**: `docs/P003-backend-spec.md` 3.5 のとおり、マイグレーション方式が冪等でない場合、2回目以降の起動で失敗してアプリが立ち上がらなくなる。この欠陥は、テストごとに新しい一時データストアを作る単体テスト・結合テストでは**常に初回実行になるため検出できない**。したがって、既存のDBファイルを使い回して2回起動する専用の確認を、他の観点とは別に必ず実施する。
* 検証の具体手順は `docs/P009-acceptance-direction.md` のテストタスクとして定義する。

## 6. モック方針

* **外部APIは存在しない**(P001の「連携する既存システムなし」)。したがって外部サービスのモックは不要である。
* モックを使うのは次の場合に限る。
  * 単体テストで `handlers` を検証する際、認証ミドルウェアが解決する `request.state.user` をスタブする。
  * 単体テストで時刻依存の処理(セッション期限、「本日」判定)を検証する際、時刻取得関数(`now_utc()` / `today_local()`)を差し替える。**このため、時刻取得は必ず専用の関数に集約し、`datetime.now()` を各所に直書きしない**(実装指示に明記する)。
  * フロントエンドの画面描画テストで、APIクライアントを固定応答を返す関数に差し替える。
* Repository層のモックは作らない(一時DBを使う実テストのほうが安価で確実なため)。★ACCEPTED★ Repositoryをインタフェース化してモックする設計も検討したが、SQLite の一時DBは生成コストが低く、SQL自体の誤りを検出できる利点が大きいため採用しなかった。残る制約は、DB層の障害系(接続失敗・ロックタイムアウト)を単体テストで再現しにくいことであり、ロックタイムアウトは結合テストの並行実行シナリオで確認する。

  * 結合テスト・システムテスト・受け入れテスト: 全件PASS。FAILが残る場合はReviewer Loop(P202〜)へ引き渡す。
* **記録先**: `docs/test-records/YYYYMMDD-HHMM-test-record.md`。形式は `TEMPLATE-test-record.md` の共通形式に従う(P008・P009・P103・P201・P205で共通)。
* 結果は PASS / FAIL / BLOCKED / NOT RUN のいずれかで記録する。BLOCKED は前提条件(ビルド失敗、先行テストの失敗)により実行できなかった場合に用いる。
