## 矛盾点 #1(重大度: 中)— `meeting_url` の検証順序が「指定あり/指定なし」で食い違う

- 概要: `docs/P002-frontend-spec.md` 3.3「オンライン会議URLの検証仕様」(CR-001で追記)は `(1)500文字以内であること、(2)http:// または https:// で始まること` と番号付きで列挙しているが、`docs/P007-impl-direction/U003-reservation-core.md` U003-T5 は「検証順序はP002 3.3に指定がないためAgentの想定で補った」旨の★FIXME★を付けている。同じ論点について、一方は「規定がある」、他方は「規定がない」と述べている。
- 関係箇所(この矛盾が波及している範囲):
  - `docs/P002-frontend-spec.md` 3.3(検証仕様の本文)
  - `docs/P007-impl-direction/U003-reservation-core.md` U003-T5【実装内容】(サーバー側の検証順序)
  - `docs/P007-impl-direction/U004-reservation-ui.md` U004-T6【実装内容】(クライアント側の検証順序。「サーバー側と同じ順序」と書いているため、サーバー側の記述に従属している)
  - `docs/P008-test-direction/T019-meeting-url.md` 手順9・期待結果(501文字の入力に対して「500文字以内で入力してください。」を期待している。すなわち**文字数を先に判定する**前提でテスト期待値が書かれている)
- 実害の見積もり: 501文字かつスキーム不正なURL(例: `ftp://` + 500文字)に対して、順序が実装者ごとに分かれるとエラーメッセージが一致しない。クライアント側とサーバー側で順序が異なると、同じ入力でも画面の表示が送信前と送信後で変わる。T019の期待結果は既に「文字数を先」に固定しているため、実装が逆順になるとT019がFAILする。
- どちらの記述を正とすべきか(判断とその理由): **P002 3.3 を正とし、「文字数 → スキーム」の順に判定する**と明記する。理由は3点。(1)P002 3.3 の番号付き列挙が既にその順序を示唆している。(2)既存の他項目(件名・備考)も「必須 → 文字数」の順で判定しており、長さを先に見るのが本システムの一貫した作法である。(3)P008 T019 の期待結果が既にこの順序を前提にしており、これに合わせることで下流の修正が不要になる。
- 修正すべき文書と箇所(P012の作業対象):
  - `docs/P002-frontend-spec.md` 3.3 — 判定順序を明文化する(「両方に違反する場合は文字数のメッセージを返す」まで書く)。
  - `docs/P007-impl-direction/U003-reservation-core.md` U003-T5 — 「P002 3.3 の規定に従う」に改め、順序に関する★FIXME★を削除する(★FIXME★は「未解決」の目印であり、規定が存在するなら残してはならない)。
  - `docs/P007-impl-direction/U004-reservation-ui.md` U004-T6 — 同様に「P002 3.3 の規定に従う」に改める。
- 修正が不要な文書: `docs/P008-test-direction/T019-meeting-url.md`(既に「文字数を先」の期待値になっており、正とする判断と一致している)。`docs/P003-backend-spec.md` 4.2(順序に言及していないため、P002を正とする記述と矛盾しない。ただし可読性のため一言追記する)。
- スコープ上の注意: 本矛盾点はCR-001の対応範囲内で発生したものであり、CR-001と無関係な既存記述への波及はない(`meeting_url` 以外の項目の検証順序には触れない)。
