# ADR.md

本プロジェクトで現在有効な設計判断を管理する。
過去に廃止された設計判断は `ADR_master.md` に移動する(現時点で廃止されたADRはないため `ADR_master.md` は未作成)。

* 1つの決定 = 1つの ADR-NNN とする。実務上切り離せない決定(一方を選べば他方がほぼ自動的に決まるもの)は1つにまとめている。
* 「決定内容」「理由」は、後続のAI(実装担当・修正担当)がそのまま読み込んで判断できる程度に簡潔にする。長い経緯や検討の過程そのものは書かず、結論とその根拠だけを残す。
* 状態が「廃止」になったADRは、本文を `ADR_master.md` に移し、この `ADR.md` の一覧・本文からは削除する。

## ADR-001

### タイトル

フロントエンドは、ビルドツールを使わない素のHTML/CSS + ESモジュール構成で実装する

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-TECH-001(フロントエンド: React 18 + TypeScript + Vite)
* REQ-SCREEN-001〜007(全7画面)
* REQ-TRANS-001(画面遷移)

### 背景

P001はフロントエンドに React 18 + TypeScript + Vite を指定している。しかし本プロジェクトの実行環境は外部パッケージレジストリ(`registry.npmjs.org`)へ到達できず、React・TypeScript・Vite およびテストランナー(Jest等)を一切取得できない。指定どおりの構成では実装もテストも実行できない。

### 決定内容

* 素のHTML/CSS と ESモジュール形式のJavaScript(ブラウザが直接読む)で実装する。ビルド・トランスパイル工程を持たない。
* 単一のHTMLシェル `client/index.html` を入口とし、ハッシュフラグメント(`#/login` 等)で画面を切り替えるSPAとする。画面ごとに1つのESモジュール(`client/src/views/s0N-*.js`)を描画関数として分離する。
* 状態管理ライブラリは導入しない(P001の「React標準のみ」という方針に対応する)。
* フロントエンドの単体テストは Node.js 標準の `node --test` で実行する。**この決定は上記と切り離せない**(外部パッケージを取得できないという同一の制約から自動的に決まり、一方だけを覆せないため、同じADRに含める)。
* ★FIXME★ この代替はAgentの判断であり、人間は「(a) 代替構成のまま進める」「(b) レジストリに到達できる環境を用意しP001どおりReactで作り直す」のいずれかを確定すること。(b) を選ぶ場合、本ADRは廃止となりP002・P005・P007の再作成が必要になる。

### 理由

* 実行環境で確実に動作し、実装とテストの両方を完了できる唯一の構成である。
* P001の選定理由(コンポーネント分割による画面再利用性、SPA的なカレンダーUI)は、画面単位のESモジュール分割とハッシュルーティングで代替的に満たせる。
* ビルド工程がないため、配布物が `client/` の静的ファイルそのものになり、サーバーからの配信が単純になる(ADR-010)。

### 検討した代替案

#### React 18 + TypeScript + Vite(P001の指定どおり)

却下。理由: `registry.npmjs.org` に到達できず依存パッケージを取得できないため、実装・テストが実行できない。

#### CDN経由でReactを読み込む(ビルドなしでReactだけ使う)

却下。理由: 外部ネットワークに到達できない環境であり、CDNからも取得できない。またJSXを使えないため記述量の利点が失われる。

#### ヘッドレスブラウザによるE2Eテストの併用

却下。理由: ブラウザ自動化ツールも取得できない。描画関数が返すDOM構築結果を検証する方式とする(`docs/P006-test-plan.md` 1.1)。

### 影響範囲

* Frontend(`client/` 全体)
* テスト(フロントエンド単体テストの実行手段)
* 配布(ビルド成果物を持たない)

### 関連成果物

* `docs/P002-frontend-spec.md` 1.2 / 2.2
* `docs/P005-impl-plan.md` 2.1 / 2.4
* `docs/P007-impl-direction.md` 2章
* `client/INDEX.md`

### 備考

* ★ACCEPTED★ 実ブラウザ固有の挙動(CSSレイアウト崩れ、実際のクリック動作)を自動検証できない制約が残る。ヘッドレスブラウザによるE2Eテストを検討したが、ツールを取得できない環境のため採らなかった。この残存リスクは `docs/P009-acceptance-direction.md` の手動確認手順で補う。

## ADR-002

### タイトル

バックエンドは Starlette + Pydantic v2(明示検証)で実装し、テストは標準の unittest で行う

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-TECH-002(バックエンド: Python + FastAPI)
* REQ-API-001〜017(全17API)
* REQ-TEST-001(単体テストで重複チェックを重点的にカバー)

### 背景

P001はバックエンドに Python + FastAPI を指定している。本プロジェクトの実行環境は `pypi.org` へ到達できず、FastAPI およびその依存パッケージ、pytest を取得できない。

### 決定内容

* WebフレームワークとしてStarlette(ASGIアプリケーション層)を用いる。ルーティング・リクエスト/レスポンス・ミドルウェアはStarletteの機能を使う。
* リクエスト/レスポンスの検証は Pydantic v2 モデルを**ハンドラ内で明示的に呼び出して**行う(FastAPIの自動バインドは使えないため)。制約値はP002第3章の表と1対1に一致させる。
* OpenAPI仕様は自動生成しない。**API契約は `docs/P002-frontend-spec.md` 第5章を単一の正とする。**
* バックエンドのテストフレームワークは Python 標準の `unittest` とする。**この決定は上記と切り離せない**(pytestを取得できないという同一の制約から自動的に決まる)。
* ★FIXME★ この代替はAgentの判断であり、人間は「(a) 代替構成のまま進める」「(b) PyPIに到達できる環境を用意しFastAPIで作り直す」のいずれかを確定すること。

### 理由

* Starletteは FastAPI の下位層そのものであり、設計思想が同じであるため、将来FastAPIへ移行する際の書き換え範囲を小さくできる。
* Pydantic v2 を明示呼び出しすることで、P001の選定理由のうち「型ヒントベースで仕様との整合を取りやすい」「業務ロジックをテストしやすい」は維持できる。
* 満たせなくなるのは「OpenAPI仕様の自動生成」のみであり、API契約をP002第5章に一元化する運用で代替できる。

### 検討した代替案

#### FastAPI(P001の指定どおり)

却下。理由: `pypi.org` に到達できず取得できない。

#### Python標準の `http.server` / WSGI直書き

却下。理由: ルーティング・ミドルウェア・非同期処理を自前実装することになり、実装量とバグ混入リスクが増える。Starletteは入手済みであり、その必要がない。

#### pytest

却下。理由: 取得できない。`unittest` で同等のテスト観点を実装できる。

### 影響範囲

* Backend(`server/` 全体)
* API契約の管理方法(P002第5章が正)
* テスト実行手段(`python3 -m unittest discover -s tests -t .`)

### 関連成果物

* `docs/P003-backend-spec.md` 1.1 / 2.1 / 4.2
* `docs/P006-test-plan.md` 1.1
* `docs/P007-impl-direction.md` 2章
* `server/INDEX.md`

### 備考

* ★ACCEPTED★ OpenAPI仕様が自動生成されないため、API契約とコードの乖離を機械的に検出できない制約が残る。手書きのOpenAPI定義を別途保守する案も検討したが、二重管理により乖離リスクがかえって増えるため採らなかった。残存リスクは、P002第5章を正としてレビュー(P010・P201)と結合テスト(P008)で乖離を検出する運用で受け止める。

## ADR-003

### タイトル

パスワードのハッシュ化に `hashlib.scrypt` を用い、パラメータ込みの1カラム文字列で格納する

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-NFR-003(セキュリティ: パスワードはハッシュ化して保存する)
* REQ-PRE-003(ID/パスワードによるログイン必須)

### 背景

P001は「パスワードはハッシュ化して保存する」とのみ定めており、方式は未指定である。実行環境は `pypi.org` に到達できないため、bcrypt・argon2 のライブラリを利用できない。

### 決定内容

* `hashlib.scrypt(password, salt=<16バイト乱数>, n=2**14, r=8, p=1, dklen=32)` を用いる(Python標準ライブラリ)。
* 格納形式は `scrypt$<n>$<r>$<p>$<base64(salt)>$<base64(dk)>` の1カラム文字列(`users.password_hash`)。検証時は文字列からパラメータとsaltを復元して再計算し、`hmac.compare_digest` で定数時間比較する。
* パラメータを格納形式に含めるのは、将来コストパラメータを引き上げても既存ハッシュを検証できるようにするためである。
* ログイン時、ユーザーが存在しない場合もダミーのscrypt検証を1回実行し、応答時間差からのユーザー列挙を防ぐ。

### 理由

* scryptはメモリハード関数であり、標準ライブラリの範囲で要件を満たせる唯一の現実的な選択肢である。
* パラメータを格納形式に含めることで、方式変更・コスト引き上げを既存データの一括再ハッシュなしに段階移行できる(本ADRを覆さずにパラメータだけ変更できる)。

### 検討した代替案

#### bcrypt / argon2

却下。理由: ライブラリを取得できない。将来レジストリに到達できる環境になった場合は、格納形式のプレフィックス(`scrypt$`)により方式を識別して段階移行できる。

#### `hashlib.pbkdf2_hmac`

却下。理由: 標準ライブラリで利用できるが、メモリハードではなくGPUによる並列総当たりに対する耐性がscryptより低い。

#### ソルトを別カラムに持つ

却下。理由: パラメータとソルトが分離すると、方式変更時にスキーマ変更が必要になる。1カラム文字列にまとめればマイグレーション不要で移行できる。

### 影響範囲

* Backend(`security.py`、`services/auth_service.py`、`services/user_service.py`)
* Database(`users.password_hash` の値形式)

### 関連成果物

* `docs/P003-backend-spec.md` 1.1 / 4.3
* `docs/P006-test-plan.md` 3.2(V-N-03)
* `docs/P007-impl-direction/U001-foundation-auth.md`

### 備考

* パスワードハッシュはいかなるAPIレスポンスにも含めない(P002 5.3)。SELECT句にも含めない(P003 6.3)。

## ADR-004

### タイトル

データストアはSQLite単一ファイルとし、Python標準の `sqlite3` でSQLを直接記述する(ORMを使わない)

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-TECH-003(データストア: SQLite)
* REQ-NFR-004(スケーラビリティ: 単一サーバー構成で十分)
* REQ-NFR-005(想定同時利用者数: 同時30接続)
* REQ-NFR-001(性能: カレンダー表示3秒以内)

### 背景

P001はデータストアにSQLiteを指定している。データアクセス手段(ORMの要否)は未指定であり、実行環境は `pypi.org` に到達できないためSQLAlchemy等のORMを取得できない。

### 決定内容

* SQLite の単一DBファイルを唯一の永続化先とする(パスは環境変数 `DB_PATH`、既定 `./data/app.db`)。
* データアクセスはPython標準の `sqlite3` を用い、SQLを `repositories/` 層に直接記述する。ORM・クエリビルダは導入しない。
* 接続時の設定を固定する: `timeout=5.0`、`isolation_level=None`(自動コミット無効)、接続直後に `PRAGMA foreign_keys = ON`、起動時に1回 `PRAGMA journal_mode = WAL`。
* 接続はリクエスト単位で開き、応答後に閉じる。コネクションプールは持たない。
* 主要な検索経路にインデックスを用意する(`idx_reservations_room_date` / `idx_reservations_date` / `idx_reservations_user_date` / `idx_sessions_user_id`)。

### 理由

* ORMを取得できない環境であり、標準 `sqlite3` が唯一の選択肢である。
* SQLを明示管理できるため、重複判定(ADR-007)のような境界条件の厳しいクエリを直接検証できる。
* `PRAGMA foreign_keys` はSQLiteの既定がOFFであり、明示しないと参照整合性が効かない。WALは読み書きの同時実行性を上げ、想定同時接続数(30)に対応するために必要である。

### 検討した代替案

#### PostgreSQL / MySQL

却下。理由: P001がSQLiteを指定している。別プロセスのミドルウェアを起動する必要がなく、想定規模(従業員300名・会議室10室・同時30接続)ではSQLiteで十分である。

#### SQLAlchemy等のORM

却下。理由: 取得できない。加えて、重複判定SQLのような条件の込み入ったクエリはSQL直書きのほうが検証しやすい。

#### コネクションプールの導入

却下。理由: SQLiteはファイルベースで接続コストが低く、リクエスト単位の接続で十分。プールは接続ごとのPRAGMA適用状態の管理を複雑にする。

### 影響範囲

* Backend(`db.py`、`repositories/` 全体)
* Database(スキーマ・インデックス)
* 配布(DBファイルの永続化ボリューム。`docs/P302-deliver.md`)

### 関連成果物

* `docs/P003-backend-spec.md` 3.4 / 4.5
* `docs/P002-frontend-spec.md` 6章(テーブル定義)
* `docs/P005-impl-plan.md` 4章

### 備考

* ★ACCEPTED★ 単一ファイルDBのため、書き込みが直列化されプロセスを複数立てても書き込みスループットが上がらない制約が残る。RDBMSサーバーの採用も検討したが、P001が単一サーバー構成で十分としており、運用対象のミドルウェアを増やす負担が上回るため採らなかった。将来スケールアウトが必要になった場合は、`repositories/` 層に閉じたSQLの書き換えで移行できるようにしてある。

## ADR-005

### タイトル

認証はセッションCookie(`sid`)方式とし、JWTを採らない

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-PRE-003(ID/パスワードによるログイン必須)
* REQ-NFR-003(セキュリティ: 管理者機能の権限チェック)

### 背景

P001は認証を必須としているが、方式(セッション/JWT等)は次フェーズで確定するとしている。本システムは社内向けの同一オリジンWebアプリであり、外部クライアントやモバイルアプリ向けのAPI公開は要件にない。

### 決定内容

* ログイン成功時に不透明なセッションID(`secrets.token_urlsafe(32)`)を発行し、Cookie `sid`(HttpOnly / SameSite=Lax / Secure / Path=/)で受け渡す。クライアントJavaScriptはCookieを読まない。
* 有効期限は「最終アクセスから8時間の無操作でタイムアウト(スライディング)」かつ「発行から24時間の絶対上限」とする。
* 認可はハンドラ単位のヘルパで行う: `require_login` / `require_admin`(不成立は403 `FORBIDDEN`)/ `require_owner_or_admin`。認証不要な経路は `POST /api/auth/login` と静的ファイル配信のみ。
* ユーザーの権限変更・無効化時は、そのユーザーのセッションを全削除して即座に失効させる。

### 理由

* HttpOnly Cookie はJavaScriptから読めないため、XSSによるトークン持ち出しに対してlocalStorage保管のJWTより強い。
* 不透明なセッションIDはサーバー側で即時失効できる。JWTは自己完結型のため、権限降格・アカウント無効化を即時反映するには結局サーバー側の失効リストが必要になり、JWTの利点が失われる。
* 同一オリジン配信(ADR-010)であるためCookieのSameSite=Laxで十分にCSRF耐性を確保でき、トークンをヘッダで運ぶ必要がない。

### 検討した代替案

#### JWT(Bearerトークン)

却下。理由: 権限変更・無効化の即時反映に失効管理が必要になり、ステートレスという利点が失われる。加えて署名ライブラリの取得が必要になる可能性がある。

#### HTTP Basic認証

却下。理由: ログアウトの概念がなく、パスワードが毎リクエスト送信される。P001の画面遷移(ログイン画面・ログアウト操作)と整合しない。

#### CSRFトークンの併用

却下。理由: 同一オリジン + SameSite=Lax + JSON `Content-Type` 必須の組み合わせでクロスサイトからの書き込みは成立しない。トークン管理を増やす利益が小さい。

### 影響範囲

* Backend(`auth.py`、`services/auth_service.py`、`handlers/` 全体)
* Frontend(認証ガード、401時のS01への強制遷移)
* API契約(401 `UNAUTHENTICATED` / 401 `AUTH_FAILED` / 403 `FORBIDDEN`)

### 関連成果物

* `docs/P002-frontend-spec.md` 2.3 / 5.1 / 5.4
* `docs/P003-backend-spec.md` 4.3
* `docs/P006-test-plan.md` 3.2(V-N-04・V-N-05)

### 備考

* ★ACCEPTED★ CSRFトークンを持たないため、将来クロスオリジンでAPIを公開したり `SameSite` を緩めたりするとCSRF対策が不足する制約が残る。CSRFトークン併用も検討したが、同一オリジン配信かつ SameSite=Lax の前提では追加の防御効果が小さいため採らなかった。前提(同一オリジン配信)が変わる場合はCRとして見直す。
* Cookieに `Secure` を付けるため、動作にはHTTPSでの配信(ADR-010のTLS外部終端)が前提となる。

## ADR-006

### タイトル

セッションはSQLiteの `sessions` テーブルに永続化する(プロセス内メモリに保持しない)

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-NFR-002(可用性: 平日日中99%以上。計画メンテナンスによる再起動を許容)
* REQ-NFR-004(スケーラビリティ: 将来のスケールアウト)

### 背景

ADR-005でセッションCookie方式を採ったため、セッションの実体をどこに保持するかを決める必要がある。P001はプロセス再起動を伴う計画メンテナンスを許容しており、将来の多拠点展開時のスケールアウトにも言及している。

### 決定内容

* `sessions` テーブル(`session_id` PK / `user_id` / `created_at` / `last_accessed_at` / `expires_at`)に保持する。インデックスは `idx_sessions_user_id`。
* 認証のたびに `last_accessed_at` を更新する(スライディング期限)。期限切れ・無効ユーザーの場合は該当行を削除して401を返す。
* 期限切れ行の一括掃除は、ログイン処理のたびにDELETEを1回実行することで行う。専用のバッチプロセス・スケジューラは設けない。

### 理由

* プロセス再起動でセッションが失われないため、計画メンテナンス後に全ユーザーが強制ログアウトされない(REQ-NFR-002の前提)。
* 将来プロセスを複数立てても、セッション参照先が共有されるため破綻しない。
* 別のセッションストア(KVS)を導入せずに済み、運用対象のミドルウェアが増えない。

### 検討した代替案

#### プロセス内メモリ(dict)で保持する

却下。理由: 最も単純だが、再起動のたびに全ユーザーが強制ログアウトされ、スケールアウト時に破綻する。

#### Redis等のKVS

却下。理由: 取得・運用できるミドルウェアが増える。想定規模(同時30接続)ではSQLiteで十分である。

#### 有効期限を絶対期限のみにする(スライディングなし)

却下。理由: 業務時間中の作業途中で強制ログアウトされる。スライディング8時間 + 絶対24時間の二重制限のほうが、利便性と滞留セッションの抑制を両立できる。

### 影響範囲

* Backend(`repositories/sessions_repo.py`、`auth.py`)
* Database(`sessions` テーブル)

### 関連成果物

* `docs/P003-backend-spec.md` 2.2 / 3.2 / 4.3
* `docs/P009-acceptance-direction/A006-session-lifecycle.md`
* `docs/P009-acceptance-direction/A007-restart-resilience.md`

### 備考

* ★ACCEPTED★ 認証のたびに `last_accessed_at` のDB書き込みが発生するため、高負荷時に書き込みロック競合の一因となる制約が残る。メモリ保持や更新間引き(一定時間ごとにのみ更新)も検討したが、前者は再起動耐性を失い、後者は期限判定の精度と実装の単純さを損なうため採らなかった。想定同時接続数(30)では実測上の問題にならないと判断している。

## ADR-007

### タイトル

予約の重複は半開区間の交差で判定し、`BEGIN IMMEDIATE` トランザクション内で検査と更新を行う

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-API-011(POST `/api/reservations` は重複チェックを行う)
* REQ-API-012(PUT `/api/reservations/{id}` は重複チェックを行う)
* REQ-TEST-001(単体テストで重複チェックを重点的にカバー)
* P001の解決課題「二重予約の解消」

### 背景

二重予約の防止は本システムの中核要件である。P001は重複チェックの厳密な仕様(同時リクエスト時の排他制御)を詳細設計に委ねている。単一プロセス・単一SQLiteファイル構成(ADR-004)における TOCTOU(検査と更新の隙間への割り込み)をどう塞ぐかを決める必要がある。

### 決定内容

* **重複の定義**: 同一 `room_id`・同一 `reserved_date` の2予約 A・B が `A.start_time < B.end_time AND B.start_time < A.end_time` を満たすとき重複とする(半開区間 `[start, end)` の交差)。境界一致(09:00-10:00 と 10:00-11:00)は重複しない。
* 時刻は `HH:MM` のゼロ埋め固定長文字列として保持し、SQLの比較演算子(辞書順)をそのまま時刻順比較に用いる。形式は Pydantic の正規表現(`^([01]\d|2[0-3]):[0-5]\d$`)で担保する。
* 更新(API-16)では判定SQLに `exclude_reservation_id` を渡し、更新対象の予約自身を競合から除外する。
* **排他制御**: 「重複チェック → INSERT/UPDATE」を単一トランザクションで行い、そのトランザクションを `BEGIN IMMEDIATE` で開始する(開始時点でRESERVEDロックを取得するため、検査と更新のあいだに他の書き込みが割り込めない)。書き込みを伴う全処理(POST/PUT/DELETE)で同じ規約を適用する。
* ロック待ちは接続の `timeout=5.0` に従う。超過時(`database is locked`)は 500 `INTERNAL_ERROR` に変換し、ログに `error_code=DB_LOCK_TIMEOUT` を記録する。
* 409 応答には競合相手(最大5件の `reservation_id` / `start_time` / `end_time`)を含める。

### 理由

* 判定ロジックと排他制御は**切り離して覆せない**ため1つのADRにまとめている。判定SQLが正しい結果を返すという主張は「検査と挿入が同一の書き込みロック下にある」ことに依存しており、排他制御方式だけを差し替えると判定の正しさの根拠自体が崩れる。
* 半開区間の交差判定は、完全一致・部分重複・内包・被内包・境界接触のすべてを1つの条件式で正しく扱える。
* `BEGIN IMMEDIATE` はDBレベルのロックであり、プロセス数に依存せず正しい。

### 検討した代替案

#### アプリケーションレベルのロック(`threading.Lock`)で直列化する

却下。理由: 将来プロセスを複数立てた時点で無効になる。正しいロック境界はDBレベルにしかない。

#### DBのUNIQUE制約や排他制約で重複を防ぐ

却下。理由: SQLiteには期間の重なりを表現できる排他制約(PostgreSQLのEXCLUDE制約に相当するもの)がない。時間帯スロットを行に展開すれば表現できるが、データ量と更新の複雑さが増す。

#### 時刻を分単位の整数に変換して比較する

却下。理由: 変換の往復が増えるだけで、ゼロ埋め固定長文字列の辞書順比較で正しさは担保される。

#### ロック競合時に 503 + `Retry-After` を返す

却下。理由: P002第5.2節のエラーコード表に503がなく、API契約を増やすことになる。★FIXME★ この判断はP003 5.3のとおり人間の確認を要する(503のほうが意味的には正確である)。

### 影響範囲

* Backend(`services/reservation_service.py`、`repositories/reservations_repo.py`、`db.py` のトランザクションヘルパ)
* API契約(409 `RESERVATION_CONFLICT` と `conflicts` 配列)
* テスト(境界値の単体テスト、並行リクエストの結合・システムテスト)

### 関連成果物

* `docs/P003-backend-spec.md` 5.1 / 5.2 / 5.3 / 4.5
* `docs/P002-frontend-spec.md` 5.7(API-15・API-16)
* `docs/P008-test-direction/T012-reservation-conflict.md`
* `docs/P009-acceptance-direction/A002-double-booking-prevention.md`

### 備考

* ★ACCEPTED★ `BEGIN IMMEDIATE` を全書き込みに適用するため、単一プロセス構成では書き込みが事実上直列化される制約が残る。書き込み対象ごとにロック粒度を細かくする案も検討したが、SQLiteはDBファイル単位のロックしか持たないため実現できない。P001の想定同時接続数(30)では実測上の問題にならないと判断している。

## ADR-008

### タイトル

会議室・ユーザーの削除は `is_active` による論理削除とし、予約の取消は物理削除とする

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-ITEM-006 / REQ-API-007(S06の削除は論理削除)
* REQ-ITEM-007 / REQ-API-017(S07の削除は論理削除)
* REQ-API-013(予約の取消)

### 背景

P001は会議室・ユーザーの削除を「論理削除(無効化)」と明示している。一方、予約については「取消(削除)」とだけ書かれており、論理削除の指定はない。論理削除を採ると、一意制約・参照整合性・一覧の見え方に横断的な影響が生じるため、方針を1つの決定として固定する必要がある。

### 決定内容

* `rooms` / `users` は行を削除せず `is_active` を 0 に更新する(既に無効な対象への再実行は204で冪等)。
* 会議室名の一意性は「有効な行のなかで一意」とし、**部分ユニークインデックス** `uq_rooms_name_active`(`rooms(name) WHERE is_active = 1`)で実現する。全行ユニークにはしない(無効化した会議室と同名の会議室を新規登録できるようにするため)。
* 社員ID(`users.user_id`)は主キーであり、無効化済みの同一IDが存在する場合も新規登録は 409 `DUPLICATE_KEY` とする(IDの再利用を許さない)。
* 無効化が既存データを壊さないよう業務制約を置く: 本日以降の予約が1件以上ある会議室の無効化は 409 `CONSTRAINT_VIOLATION`、自分自身および最後の有効な管理者の無効化・降格も 409 `CONSTRAINT_VIOLATION`。
* 予約(`reservations` / `reservation_attendees`)の取消は**物理削除**とする。
* 無効化されたユーザーが持つ今後の予約はそのまま残す(自動取消しない)。★FIXME★ この扱いはP001に記載がないためAgentの想定である(P002 5.6)。

### 理由

* 論理削除は過去の予約が参照する会議室名・氏名を保持するために必要である(物理削除すると過去の予約が表示できなくなる)。
* 部分ユニークインデックスにしないと、一度無効化した会議室名を二度と使えなくなり、運用上の詰まりが生じる。
* 予約に論理削除を採らないのは、P001が論理削除を会議室・ユーザーにのみ指定していること、および重複チェック(ADR-007)の全問い合わせに「取消済みを除外する」条件が増えて誤りやすくなるためである。

### 検討した代替案

#### 会議室・ユーザーも物理削除する

却下。理由: P001が論理削除を明示している。加えて過去の予約の参照先が失われる。

#### 会議室名を全行ユニークにする

却下。理由: 無効化済みの名前が永久に予約されてしまい、同名の会議室を再登録できない。

#### 予約も取消済みフラグによる論理削除にする

却下。理由: 重複チェックの全クエリに除外条件が必要になり、条件漏れによる誤判定のリスクが上がる。監査要件(取消履歴)が発生した場合は、CRで取消履歴テーブルを追加する。

### 影響範囲

* Database(`rooms.is_active` / `users.is_active` / `uq_rooms_name_active`)
* Backend(`repositories/` の全SELECTにおける `is_active` の扱い、`services/room_service.py`・`user_service.py` の業務制約)
* Frontend(S06・S07の無効行のグレー表示、会議室プルダウンからの除外)

### 関連成果物

* `docs/P002-frontend-spec.md` 3.6 / 3.7 / 5.5 / 5.6 / 5.7(API-17)/ 6.2
* `docs/P003-backend-spec.md` 3.4 / 6.2 / 6.3
* `docs/P008-test-direction/T006-room-name-uniqueness.md` / `T014-room-deactivate-blocked.md`

### 備考

* ★ACCEPTED★ 予約を物理削除するため取消履歴が残らない制約が残る。取消済みフラグによる論理削除も検討したが、上記のとおり重複チェックの誤りやすさが増すため採らなかった。監査要件が生じた場合はCR(P901)で取消履歴テーブルを追加する。
* P004第5章のとおり、会議室・ユーザー無効化の業務制約(#4・#5)はP001に対応する要求がない追加である。削除は推奨しない旨が記録済み。

## ADR-009

### タイトル

スキーマは差分適用型マイグレーション(`schema_migrations` テーブル)で適用する

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-NFR-002(可用性: 計画メンテナンスによる停止・再起動を許容)
* REQ-TECH-003(データストア: SQLite)

### 背景

アプリケーションは起動時にスキーマを適用する。SQLiteは `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` を持たないため、「毎回全SQLを流し直す」方式はカラム追加が発生した時点で2回目の起動に必ず失敗する。この破綻は、テストごとに新しい一時DBを作る単体テスト・結合テストでは常に初回実行になるため検出できない。

### 決定内容

* `server/migrations/NNN-{説明}.sql`(3桁ゼロ埋め連番)をファイル名昇順に走査し、`schema_migrations` に未記録のものだけを適用する。
* 適用タイミングはプロセス起動時(ASGIアプリ生成直後、リクエスト受付開始前)に1回。失敗時はロールバックしてプロセスを異常終了させる(中途半端な状態で起動しない)。
* `CREATE TABLE IF NOT EXISTS schema_migrations (version TEXT PRIMARY KEY, applied_at TEXT NOT NULL)` のみ常に実行してよい(冪等)。
* 1ファイル = 1トランザクションで「ファイル内の全SQL実行」と「`schema_migrations` へのINSERT」を行う。SQLは**文単位で実行**し、`executescript()` は使わない(暗黙コミットでトランザクション境界が壊れるため)。
* **一度コミットしたマイグレーションファイルは編集しない。** スキーマ変更は必ず新しい連番ファイルを追加する。
* 初期管理者のシードは、パスワードのハッシュ化が必要なためSQLではなく起動処理側で「管理者が1人も存在しない場合にのみINSERTする」形で実装する(これも冪等)。
* この方式が実際に冪等であることは、同一DBファイルに対してプロセスを2回以上起動する専用の確認(P006 3.3 V-O-01 / V-O-02、P009 A007)でのみ検証できる。この検証は必須とする。

### 理由

* 差分適用であれば、条件付き構文を持たないDDL(`ALTER TABLE ... ADD COLUMN` 等)を含んでいても2回目以降の起動で失敗しない。
* 後からCRでスキーマ変更が発生することは確実に見込まれるため、最初から差分適用型にしておくことが最も安価である(後から方式を変えると既存環境の適用済み状態を手作業で埋める必要が生じる)。
* マイグレーションツールを取得できない環境であり、この程度の仕組みは標準ライブラリで自作できる。

### 検討した代替案

#### 全SQLを毎回流し直す(`CREATE TABLE IF NOT EXISTS` のみで構成する)

却下。理由: 初回構築時は冪等に見えるが、カラム追加が発生した時点で破綻する。SQLiteは `ADD COLUMN IF NOT EXISTS` を持たない。

#### Alembic等のマイグレーションツール

却下。理由: `pypi.org` に到達できず取得できない。

#### `executescript()` でファイルを一括実行する

却下。理由: 暗黙のコミットを行うためトランザクション境界が壊れ、途中失敗時のロールバックが効かない。

### 影響範囲

* Backend(`db.py` の `apply_migrations()`、`main.py` の起動処理)
* Database(`schema_migrations` テーブル、`server/migrations/` の運用規約)
* テスト(再起動耐性の独立観点 V-O-01・V-O-02)
* 配布(DBファイルを永続化ボリュームに置くこと。`docs/P302-deliver.md`)

### 関連成果物

* `docs/P003-backend-spec.md` 3.3 / 3.5 / 3.6
* `docs/P006-test-plan.md` 3.3
* `docs/P007-impl-direction/U001-foundation-auth.md`(U001-T1)
* `docs/P009-acceptance-direction/A007-restart-resilience.md`

### 備考

* ★ACCEPTED★ ロールバック用のダウンマイグレーションを持たない制約が残る。上り下り両方を持つ方式も検討したが、SQLiteはDDLのロールバック手段が限られ、実運用ではDBファイルのバックアップから戻すほうが確実であるため採らなかった。残存リスクは、誤ったマイグレーションを適用した場合にバックアップからの復元が必要になることであり、バックアップ手順を `docs/P302-deliver.md` で定める。

## ADR-010

### タイトル

単一プロセスでAPIと静的ファイルの双方を配信し、TLS終端・ログ集約はプロセスの外側に委ねる

### 状態

採用

### 日付

2026-08-04

### 関連要求

* REQ-PRE-002(クラウド環境へのデプロイ)
* REQ-NFR-003(セキュリティ: 通信は全てHTTPS)
* REQ-NFR-004(スケーラビリティ: 単一サーバー構成で十分)
* REQ-NFR-006(ログ出力先とその監視方法)

### 背景

P001の非機能要件には、アプリケーションコードの範囲を超え実行環境に依存する項目(可用性・TLS・スケーラビリティ・ログ集約)が含まれる。どこまでをアプリケーションプロセスの責務とするかを決めないと、実装フェーズで境界が曖昧になる。

### 決定内容

* **配信**: 1つのASGIプロセスが `/api/*` のAPIと、`client/` 配下の静的ファイル(`/`、`/src/*`、`/assets/*`)の双方を配信する。同一オリジンのためCORS設定を行わない。`/api/` に一致しない未知パスは `client/index.html` を返す。
* **TLS**: アプリはHTTPで待ち受け、**TLS終端はリバースプロキシ/ロードバランサ(プロセスの外側)で行う前提**とする。Cookieには `Secure` を付与するが、`X-Forwarded-Proto` は参照しない。
* **ログ**: Python標準 `logging` で標準出力に1リクエスト1行のJSONを出力する(`ts` / `level` / `method` / `path` / `status` / `duration_ms` / `user_id` / `error_code` / `message`。5xxのみ `stack`)。パスワード・Cookie値(`sid`)・セッションIDは出力しない。**転送先や監視設定はアプリの責務としない。**
* **プロセス構成**: 単一プロセス・単一SQLiteファイル。プロセス内状態(メモリセッション、プロセス内ロック)を持たない設計とし、将来のスケールアウトを妨げない。
* **委譲先**: リバースプロキシ構成・証明書配置・HTTPSリダイレクト、`restart` ポリシーとヘルスチェック、ASGIサーバーのワーカー数、標準出力の収集とCloudWatch Logs等への転送・アラート設定は `docs/P302-deliver.md`(納品物作成)で確定する。インフラ専用スプリントは設けない(`docs/P005-impl-plan.md` 4章)。

### 理由

* 同一オリジン配信により、CORS設定とプリフライトの考慮が不要になり、Cookie認証(ADR-005)の SameSite 設定も単純になる。
* TLS終端・ログ転送を外側に置くことで、アプリケーションコードが実行環境の構成に依存しなくなり、テスト時にHTTPで起動できる。
* 責務境界を明示することで、P004・P010が非機能要件の充足確認を「委譲先の記載箇所」で判定できる。

### 検討した代替案

#### フロントエンドを別のWebサーバー(nginx等)で配信する

却下。理由: ビルドツールを持たない静的ファイル構成(ADR-001)であり、同一オリジンで配信すればCORS設定とプリフライトが不要になる。運用対象のプロセスを増やす利益が小さい。

#### アプリケーションプロセス内でTLSを終端する

却下。理由: 証明書の配置・更新がアプリの関心事になり、テスト・開発時の起動が煩雑になる。クラウド環境ではロードバランサでの終端が一般的である。

#### ログをファイルに直接書き出し、ローテーションもアプリで行う

## ADR-011

### タイトル

予約に追加する任意テキスト項目(オンライン会議URL)は、NULLを使わず「NOT NULL DEFAULT ''」の列として差分マイグレーションで追加し、URLの検証はスキームの前方一致のみとする

### 状態

採用

### 日付

2026-08-05

### 関連要求

* REQ-ITEM-008(予約のオンライン会議URL。`docs/P004-traceability-matrix.md` 2.4)
* 起票元: CR-001(`docs/P901-cr-direction/CR-001.md`)

### 背景

ハイブリッド会議の増加により、予約にオンライン会議URLを保持する要求(CR-001)が出た。既存の `reservations` テーブルへの列追加が必要であり、次の3点を決める必要があった。(1) 列の追加方法、(2) 「未入力」の表現(NULL か空文字か)、(3) URLの検証をどこまで厳密に行うか。

### 決定内容

* **列の追加方法**: ADR-009 の差分適用型マイグレーションに従い、新規ファイル `server/migrations/004-meeting-url.sql` に `ALTER TABLE reservations ADD COLUMN meeting_url TEXT NOT NULL DEFAULT '';` の1文を置く。適用済みの `001`〜`003` は編集しない。**ADR-009 はこの変更で覆されておらず、むしろADR-009が想定していた使い方である。**
* **未入力の表現**: `NOT NULL DEFAULT ''`(空文字)とする。API応答の `meeting_url` も常に文字列であり `null` を返さない。`ADD COLUMN` に `NOT NULL` を付けられるのは既定値を伴う場合のみであり、`DEFAULT ''` により既存行にも適用できる。
* **URLの検証**: 「500文字以内」+「`http://` または `https://` で始まる」のみを検証する(判定順序は文字数 → スキーム)。URLパーサによる構文解析、ホスト名の妥当性検証、到達性確認、ドメインのホワイトリストは行わない。大文字スキーム(`HTTP://`)は許容しない。
* **表示**: S04(予約詳細)の閲覧モードでのみリンク(`a` 要素、別タブ)として表示する。S02(カレンダー)には表示しない。API応答には含まれるが、表示しないのは画面側の責務とする。

### 理由

* 既存の任意テキスト項目 `note`(備考)が既に `NOT NULL DEFAULT ''` であり、同じ性質の項目を `NULL` 許容にすると、画面・API・テストのそれぞれで「`null` と `''` の二重判定」が増える。`attendee_count`(数値)がNULL許容なのは「0人」と「未入力」を区別する必要があるためで、テキスト項目には同じ必要がない。
* 検証を要求どおり前方一致に留めるのは、社内の独自ホスト名(ポート番号付き、IPアドレス直指定、内部DNS名)を厳密なURL検証で誤って弾くリスクを避けるためである。CR-001 が要求しているのは「`http://` か `https://` で始まっていること」だけである。
* 列追加を新規マイグレーションファイルで行うのはADR-009の規約であり、本CRで方式変更は行わない。

### 検討した代替案

#### `meeting_url` を NULL 許容にする

却下。理由: 上記のとおり `null` と `''` の二重判定が全層に波及する。既存の `note` と扱いが分かれ、一貫性を失う。

#### `URL` パーサ(または厳密な正規表現)による構文検証

却下。理由: CR-001の要求を超える検証であり、社内の独自ホスト名を誤って弾く可能性がある。誤って弾いた場合、利用者には回避手段がない。

#### 既存の `003-reservations.sql` を編集して列を追加する

却下。理由: ADR-009 の「一度コミットしたマイグレーションファイルは編集しない」に反する。既に `003` を適用済みの環境では列が追加されない。

#### オンライン会議URL専用のテーブルを作る(1予約に複数URL)

却下。理由: CR-001は1予約に1つのURLしか要求していない。将来複数URLが必要になった場合は、その時点で新しいCRとして起票し、テーブル追加のマイグレーションを行えばよい(差分適用型であるため後からでも安全に追加できる)。

### 備考

* ★ACCEPTED★ `https://` の直後に何も無い値(例: `https://`)や、実在しないホストのURLでも保存できる制約が残る。厳密な検証は上記のとおり誤検知の害が大きいと判断して採らなかった。残存リスクは「リンクをクリックしても開けないURLが登録されうる」ことであり、影響は当該予約の参加者に限られ、S04で編集すれば直せる。
