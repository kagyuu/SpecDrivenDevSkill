# プログラム実装

## 目的

* `docs/P007-impl-direction.md` の目次で未完了(`[ ]`または`[~]`)になっている先頭のスプリントについて、対応する `docs/P007-impl-direction/U000-{sprint-name}.md` を実行し、実装と単体テストを行う。
* ここで行うのはコードの実装と単体テストのみである。結合テストの実行はP103で行う。

## インプット文書

* `docs/P101-impl-context.md`
* `docs/P007-impl-direction/U000-{sprint-name}.md` (着手対象の1スプリント分)
* `docs/P008-test-direction/` のうち、着手対象スプリントに関連する `T0NN-*.md`(結合テストが対象とするテスト関数名・実行コマンドを、実装するコード側の命名と一致させるため。詳細は下記「動作内容」参照)
* `docs/ArchitectureHandbook.md` / `docs/ADR.md` (詳細確認が必要な場合)

## アウトプット文書

* `{application root}/` 配下のソースコード(新規作成・編集)
* 単体テストコードと、その実行結果

### 動作内容

* `docs/P007-impl-direction/U000-{sprint-name}.md` に記載されたタスクを、記載された順に1つずつ実施する。
* タスクの範囲外のファイルは編集しない。
* テストコード(単体テスト、および結合テスト対象になりうるコード)を実装する際、対応する `docs/P008-test-direction/T0NN-*.md` が既に実行コマンドとして具体的なテスト関数名・ファイルパス(例: `tests/test_api_auth.py::test_login_success_then_me`)を明記している場合は、実装するテストコードの関数名・ファイル名をその記載と厳密に一致させる。これは、P103(結合テスト実行)がP008に書かれた実行コマンドをそのまま実行できるようにするためであり、勝手に別の名前を付けない。該当するP008のテストがまだ書かれていない、または対象スプリントの範囲外である場合は、この限りではない。
  * ★ACCEPTED★ P008のテストIDと本フェーズの実装命名の対応づけを、**構造的に保証する仕組み(命名規約の自動検証、ID対応表の機械的な突き合わせなど)は作らない**。検討はしたが、この種の自動検証は言語・テストフレームワークごとの命名規則の差異を吸収しきれず複雑化し、破綻しやすい(検証器自体が誤検知を出すようになり、やがて無視されるようになる)ため採用しなかった。上記の「P008の該当 `T0NN-*.md` を本フェーズのインプットに含める」+「記載された名前と厳密に一致させる」という指示が、この点に対する**恒久的な回答**である。残る制約は、一致の保証がAgentの遵守に依存することだが、不一致はP103(結合テスト実行)がP008の実行コマンドをそのまま実行した時点で必ず顕在化するため、検出は後段で担保される。この論点は判断済みであり、再度の指摘は不要。
* 各タスクの完了条件(Unit Test成功など)を満たしたことを確認してから、次のタスクに進む。
* 1つのタスクで単体テストが3回自己修正しても合格しない場合は、これ以上進めず処理を停止して人間に報告する(Executor Stepの停止条件)。
* スプリント内の全タスクが完了したら、`docs/P007-impl-direction.md` の該当スプリント行のチェックボックスを `[x]` に更新する。
* 未完了スプリントが他にもある場合は、続けて次のスプリントのP101〜P102を実行する。すべてのスプリントが `[x]` になったら、P103(結合テスト実行)に進む。
* 仕様外の拡張(`docs/P002-frontend-spec.md` `docs/P003-backend-spec.md` にない画面・API・DB項目・業務ルール)を行わない。矛盾や不足に気づいた場合は、実装を進めず `docs/P007-impl-direction.md` の「未解決事項」に記載する。
