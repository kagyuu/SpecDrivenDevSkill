## 1. V0.9_testbedで報告された5件の解決

### 1-1. P007の「コード格納先を初期化する」の実施主体が曖昧

* **事象**: `SKILL-P007-impl-direction.md` の「アウトプットの記載内容」に「コードの格納先を初期化する」という項目が置かれていたため、計画フェーズであるP007自身がビルドツールを実行して初期化するように読めた。しかし同ファイルの「目的」は「プログラム実装はExecutorが行うので、ここではコードの実装は行わない」と明記しており、正面から矛盾していた。P007の他の記載はすべて「指示書に何を書くか」であり、この1項目だけ実施主体が異なって見える状態だった。
* **V1.0での変更**:
  * `SKILL-P007-impl-direction.md`: 初期化を本フェーズでは実行しないことを明記し、**最初のスプリントの最初のタスク(`U0NN-T1`)の【実装内容】に初期化手順を書く**という指示に変更した。ビルドツールの対応表(Java: maven / Python: uv / React: npm / Angular: ng)は、指示書に書くツールを選ぶ判断材料として残した。あわせてアウトプット文書一覧から `{application root}/` を削除した。
  * `SKILL-P102-implement.md`: 初期化タスクが書かれている場合はそれを実行する旨を明記した。初期化タスクも他のタスクと同じ扱いとし、完了条件の確認・チェックボックス更新・中断時の再確認という既存ルールをそのまま適用する(初期化専用の再開処理は設けない)。
  * `SKILL-P020-source-index.md`: 「初期化済みだが未実装」のハイブリッド分岐について、その原因を「本Skill自身のP007が必ず作るケース」から「人間が本Skillを使い始める前にスキャフォールドしていた場合など」に修正した。分岐自体は削除していない(`SKILL-P104-source-index-update.md` が参照しているため、および人間の事前初期化では依然として発生しうるため)。
  * `TEMPLATE-P007-impl-direction.md`: `U0NN-T1` の【実装内容】に、初期化手順をここに書く旨のリマインダーを追加した。
* **根拠**: 「計画フェーズは指示書を書くだけであり、コードに触れるのはExecutorだけ」という本Skillの既存の役割分担を崩さずに矛盾を解消できる。またこの変更は新方式の発明ではなく、**実態の追認**である。`V0.9_testbed/docs/P007-impl-direction/U001-foundation-and-auth.md` を確認すると、実際のP007は初期化を自分で実行せず、Executorのタスク(「`uv init server` 相当の構成で初期化する」「`npm create vite@latest client -- --template react-ts` 相当で初期化」)として書いていた。SKILLのテキストだけが実態から乖離していた。
* **副次的に解消した不整合(2件)**:
  * `SKILL.md` の成果物表(P007行)には元々 `{application root}/` が記載されておらず、P102行にのみ存在していた。つまり `SKILL-P007-impl-direction.md` の記載は既にSKILL.mdと矛盾していた。今回の削除でこれも解消した。
  * `SKILL-P020-source-index.md` のインプット文書が「`docs/P005-impl-plan.md` で定めたコード格納先」としていたが、`SKILL-P005-impl-plan.md` には格納先に関する記述が一切存在しなかった。実際に定めているのはP007であるため、参照先を修正した。

#### 1-1補足: 方針レビューで発見した副作用と、その対策

実装前のレビューで、上記の方針をそのまま適用すると**新しい不具合が発生する**ことが判明したため、対策を `SKILL-P102-implement.md` に組み込んだ。

* **副作用の内容**: フェーズ順は P007(Plan Loop)→ **P020(Overview)** → P102(Executor)である。`SKILL-P020-source-index.md` は、ソースツリーのディレクトリが存在しない場合に**自らディレクトリを作成して `INDEX.md` を書き込む**と規定している。したがって初期化をP102に移すと、P102が着手する時点でコード格納先は既に存在し、中に `INDEX.md` が1件入った**非空ディレクトリ**になる。この状態で `npm create vite@latest .` のようなコマンドを素直に実行すると、「Current directory is not empty. Remove existing files and continue?」という**対話プロンプトで停止する**。本Skillは要件定義後の無人連続実行を中心的な設計コミットメントとしているため、これは致命的である。加えて、ツールによっては既存ファイルを削除するため、P020の成果物である `INDEX.md`(P104・P301が前提とする)が失われうる。
* **対策**: `SKILL-P102-implement.md` に次の3点を明記した。(1) スキャフォールドツールを対話モードで実行しない、(2) ツールが生成する構成と同等になるようファイルを配置してよい(非対話オプションがあればそれでもよい)、(3) 既存の `{ソースツリー}/INDEX.md` を削除しない。あわせて `SKILL-P007-impl-direction.md` 側に、初期化タスクを「`{ツール名}` 相当の構成で初期化する」という書き方で記載するよう指示を加えた。
* **根拠**: `V0.9_testbed` のP007が偶然この書き方(「相当の構成で」)を採っていたため、V0.9までは問題が表面化しなかった。実施主体を明文化する以上、この回避策も同時に明文化しなければ、次の実行担当が素直にコマンドを実行して停止する。

### 1-2. 「完了」の語がOKF完了とStep終了条件で意味が重なる

* **事象**: `SKILL.md` の共通指示に「完了」を指す3つの異なる基準が、互いへの参照なしに置かれていた。(a) 文書の記述が十分に書けたことをもって「そのフェーズは完了とする」(共通指示)、(b) 「P007・P008・P009・P202は目次内の全項目が `[x]` になって初めてフェーズ完了」(OKF形式の説明)、(c) Plan Loop Stepの終了条件はP010のレビュー合格のみ。各フェーズ自身の記述を読めば正しく解釈できるが、共通指示だけを通読すると「Plan Loop Stepが終わった時点でP007は完了なのか」が判断できなかった。
* **V1.0での変更**: `SKILL.md` の2箇所に、互いを参照する説明を追加した。(a)側には、ここでいう完了は記述の完了であり、P007・P008・P009・P202には別の基準が後述されていてこの時点では未達である旨を追記した。(b)側には、この基準がStepの終了条件とも記述完了とも別の実行結果ベースの基準であること、Plan Loop Stepの終了条件はOKF完了を要件に含まないこと、OKF完了は後続StepでP102・P103・P201・P203が実行された結果として遅れて確定すること、したがってPlan Loop Step完了時点でOKF目次が `[ ]` のままであるのが正常であることを追記した。
* **根拠**: 新しい用語を作ったり構造を変えたりせず、既存の3つの記述に相互参照を張るだけで誤読は解消できる。用語を増やすと、かえって既存の全ファイルへの波及が生じる。

### 1-3. クライアント・サーバ分離構成でのE2Eハーネストのトポロジー決定主体が未規定

* **事象**: P103(結合テスト実行)がクライアント・サーバ分離構成の結合テストを実行する際、開発時のクロスオリジンCookie問題を解決するためのハーネス構成(開発用プロキシの要否など)を、その場の判断で決める必要があった。この決定を誰がいつ行うかを規定するフェーズが存在しなかった。結果として、`V0.9_testbed` では**判断の理由が `client/vite.config.ts` のコメントにしか残らず**、ADRにも設計文書にも記録されなかった。
* **V1.0での変更**:
  * `SKILL-P003-backend-spec.md`: クライアントとサーバを**別プロセス/別ポートで開発・テストする構成**の場合、クロスオリジン問題の対処方針をP003で決め、理由とともに技術的決定として記録する旨を追加した。Cookie認証の場合に最も鋭く現れること(ワイルドカードのACAOと `Access-Control-Allow-Credentials: true` は併用できないため、CORSヘッダを緩めるだけでは解決しないこと)を明記し、採りうる方針を例示した。**どの方針を採るべきかは規定していない。**
  * `SKILL-P103-integration-test.md`・`SKILL-P201-review.md`: テストハーネスのトポロジーはADRに記録されたP003の決定に従い、本フェーズで新たに判断しない旨を追加した。ADRに記載が無い場合は、その旨をテスト記録に明記したうえで必要最小限の構成で実行する(勝手な決定を既定方針であるかのように扱わない)。
  * `SKILL-P009-acceptance-direction.md`: テストの「事前準備」「実行コマンド」に書く実行環境構成も、同じくP003の決定に従う旨を追加した。
* **根拠**: 本Skillの一貫した方針は「特定の技術解を決め打ちせず、判断はAIに委ね、判断とその理由の記録を義務付ける」ことである。したがって規定すべきは CORS/プロキシ/トークンのどれを使うかではなく、**誰がいつ決めて、どこに残すか**である。P003を決定者としたのは、同ファイルが既に認証の内部実現とP002の外部契約との対応を扱う節、およびインフラ寄り非機能要件の委譲を扱う節を持っており、この決定の置き場所として最も自然だからである。またP003がADRに記録すれば、`docs/P101-impl-context.md` が既にADRを要約してExecutorへ渡す仕組みを持っているため、**新しい配線を追加せずにExecutor側へ伝わる**。
* **P201を対象に含めた理由**: `SKILL-P201-review.md` は「対象テストのテストコードがまだ存在しない場合は、本フェーズが指示書どおりに新規作成してから実行する」と規定しており(V0.8の1-2で追加)、P103と全く同じ立場にある。`V0.9_testbed` の受け入れテストはPlaywrightによるE2Eであったため、P103だけを対象にすると同じ場当たり判断がP201で再発する。
* **不採用にした案**: 「ひとまず `Access-Control-Allow-Origin: *` を設定し、完成後に `FIXME.md` で変更を促す」案が検討されたが、次の2点により不採用とした。(1) ブラウザの仕様上、ワイルドカードのACAOは `Access-Control-Allow-Credentials: true` と併用できないため、**報告された不具合(Cookieが送受信できない)がそもそも直らない**。実際に効いたのはCORSヘッダの調整ではなく、開発用リバースプロキシによる同一オリジン化だった。(2) ルート直下に集約した `FIXME.md` は、「★FIXME★は該当箇所に隣接して置き、文書末尾にまとめない」という本Skillの既存の記法と正面から矛盾する。

### 1-4. CR却下時の優先度の扱いが未規定

* **事象**: `docs/CR.md` の優先度列が `高`/`中`/`低` の3値のみで、「却下のため対象外」を表す値が無かった。`V0.9_testbed` ではCR-002を却下する際、実行担当が便宜的に `中` を割り当てていた。実害は無いが値の意味が曖昧だった。
* **V1.0での変更**: 4つ目の値 `N/A`(Not Applicable)を追加した。
  * `TEMPLATE-CR.md`: 優先度の一覧に `N/A` を追加し、状態を `却下` に更新するときは同時に優先度も `N/A` に更新すること、`N/A` は `却下` のCRにのみ用いることを明記した。却下を決めるフェーズはP901とは限らないため、特定のフェーズ名を指定せず一般則として書いた。
  * `SKILL.md`: CR状態一覧表の `却下` 行に、同時に優先度列も `N/A` に更新する旨を追記した。この表はV0.9で「状態の扱いを1箇所にまとめる」ために新設したものであり、ここに書かないと「却下時の優先度はどこを見れば分かるのか」という同型の問題が再発する。
  * `SKILL-P901-cr-create.md`: 起票時点で却下が決まっている場合の記述に、優先度を `N/A` とすることを明記した。
* **根拠**: 値を1つ増やすだけで、「却下されたCRの優先度をどう扱うか」という判断自体が発生しなくなる。これはV0.7でCR運用を3ファイルに分離した際の考え方(判断が発生する構造そのものを無くす)と同じである。
* **既存ロジックへの影響が無いことの確認**: `SKILL-P902-requirement-update.md` は「状態が `未対応`(または `対応中` で優先度の高いもの)のCRを選ぶ」としているが、`N/A` は状態が `却下` のCRにしか付かないため、この選択ロジックと衝突しない。`SKILL-P011-impact-analysis.md`・`SKILL-P012-design-fix.md` に現れる「優先度」は設計矛盾の修正優先度であり、CRの優先度とは無関係である。

### 1-5. 初回リリース時のバージョン初期値が未規定

* **事象**: `SKILL-P302-deliver.md` の版数更新方針(V0.9で3-19として追加)はCR対応後の増分のみを扱っており、初回リリース時の初期値が規定されていなかった。`V0.9_testbed` では実行担当の判断で `1.0.0` としていた。
* **V1.0での変更**: `SKILL-P302-deliver.md` に次の2点を追加した。
  * **初期値は `0.1.0`** とする。`1.0.0` のような特別な意味を持つ値から始めない。スキャフォールドツールの既定値が入っている場合も `0.1.0` に統一する。
  * **MAJORが `0` の間は、破壊的変更であってもMAJORを上げずMINORを上げる**。`1.0.0` への移行は人間から明示的な指示があった場合にのみ行う。既存の「CR対応後の版数更新方針」には、MAJORが0の間はこの例外が優先する旨の但し書きを加えた(既存の規則自体は、MAJORが1以上になった後の規則として維持している)。
* **根拠**: 人間の判断により、バージョンは単なる連番として扱い、`1.0.0` に「正式版」等の特別な意味を負わせない方針とした。当初案は「初期値だけ `0.1.0` にして増分規則(破壊的変更=MAJOR)は維持する」であったが、レビューにより、それでは `0.2.0` の時点で破壊的変更が入った瞬間に `0.9.0` を経由せず一気に `1.0.0` へ到達してしまい、方針の意図と食い違うことが判明したため、0.x系の慣習(SemVer仕様§4の初期開発版の扱い)に合わせる形に改めた。この結果、実際の増分は機能追加・破壊的変更で `0.1.0 → 0.2.0 → 0.3.0`、バグ修正のみで `0.1.0 → 0.1.1` となる。
* **遡及適用はしない**: `V0.9_testbed` は `1.0.0` から始めて `1.1.0` になっているが、既存プロジェクトへ遡って適用はしない(V0.6以降一貫している方針)。

## 2. 人間の指示により新設した一般ルール: 報告時の対処案提示

* **事象**(欠陥報告ではなく、人間からの要望): 各Stepの停止条件に該当して処理を止めるとき、本Skillは「人間に報告する」とだけ規定しており、報告の内容について何も定めていなかった。人間からは、問題の報告だけでなく**対処案も併せて提示してほしい**、提示できない場合はその旨を明示してほしい、という要望が出された。
* **V1.0での変更**: `SKILL.md` の各フェーズ共通指示に「人間への報告時に対処案を示すことについて」の節を新設した(★ACCEPTED★の説明の直後)。内容は次の4点。
  1. 停止条件に該当して報告する場合・人間の判断を仰ぐ場合は、可能な限り対処案を提示する。複数案があれば利点・欠点を添えてよい。
  2. **求めているのは「提示」であり「実施」ではない。** 各フェーズの禁止事項(P302は仕様変更を行わない、P103は失敗テストをその場で修正しない、P205は期待値を改ざんしない)を、対処案を提示できることを理由に越えてはならない。
  3. 対処案を組み立てられない場合に限り提示を省略してよいが、黙って済ませず定型文言(「この問題に対して人間の判断が必要ですが、Claude Code は対処案を提示できません。その理由は{具体的な理由}です。」)と理由を明記する。
  4. 報告内容は `docs/.stop-report.md` に記録し、会話上の報告だけで済ませない。加えて、当該フェーズの成果物に停止事由を書く所定の欄がある場合(例: `docs/P302-deliver.md` の「10. 未整備事項」)はそちらにも記載する。ただし成果物のテンプレート構造を崩してまで書き込まない。
* **根拠**:
  * 2番目の項目が無いと、「対処案を出せ」が「対処してよい」と誤読され、P302の仕様変更禁止・P103の修正禁止・P205の改ざん禁止と正面衝突する危険がある。本Skillは、これらの禁止事項を守らせるために複数バージョンを費やしてきており、新ルールがそれを崩してはならない。
  * 4番目の項目は、**検証可能性を確保する**ために追加した。停止時の報告は本来チャット上にしか現れないため、そのままではテストベッドで検証も再現もできない。`V0.8_testbed` の検証記録は「エージェントの自己申告をそのまま採用していない」と明記しており、本Skillの検証プロセスはファイルとの突き合わせを前提に成立している。対処案が会話ログにしか無ければ、この前提が崩れる。
  * `docs/.stop-report.md` をドット始まりにしたのは、`SKILL.md` のステップ0が「`docs/` 配下に存在する成果物」からフェーズの進捗を判定するためである。通常のファイル名にすると再開判定を誤らせる恐れがあるため、`docs/.inprogress` と同じ制御ファイルとして扱い、判定対象外であることを明記した。
  * **記録先の規定は、`V1.0_testbed` の検証結果を受けて修正している**。当初は「そのフェーズの成果物文書に記録する。無い場合は `docs/.stop-report.md`」としていたが、差分実行時には成果物が既に存在するため、規定を文字どおり適用すると `docs/ADR.md` のようなテンプレート構造を持つ納品物に停止報告を書き込むことになり、成果物を汚染する。検証で実際にこの状況に到達したため、「原則として `docs/.stop-report.md` に記録し、所定の欄がある成果物にはそちらにも記載する。テンプレート構造を崩してまで書き込まない」に改めた(`V1.0_testbed/e2e-validation-report.md` 2-1参照)。
