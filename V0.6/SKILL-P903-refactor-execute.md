# 修正実施(Refactor)

## 目的

* P902で更新した `docs/P001-requirement.md` を起点に、Plan Loop Step(P002〜P012)、Overview Step(P020〜P022)、Executor(P101〜P104)、Reviewer Loop(P201〜P205)、Closing(P301〜P302)を通常のフローどおり再実行する。

## インプット文書

* 更新後の `docs/P001-requirement.md`
* `docs/CR.md`
* 既存の `docs/P002-frontend-spec.md` 〜 `docs/P302-deliver.md`、`docs/ArchitectureHandbook.md`、`docs/ADR.md`、各 `INDEX.md`

## アウトプット文書

* 更新された `docs/P002-frontend-spec.md` 〜 `docs/P302-deliver.md` (該当する範囲)
* 更新されたソースコード

### 動作内容

* 本フェーズを開始する前に、まず対象CRの影響範囲を分類し、P002〜P302のうちどのフェーズを実際に再オープンするかをスコープとして決定する。この決定と理由は、必ず対応するCRの記録(この時点では `docs/CR.md` の該当CR、完了後は `docs/cr-records/CR-{番号}.md`)に残す(下記「CRスコープの決定」参照)。これは実地検証で実行担当が独自に発明した運用を、必須の手順として明文化したものである。
* スコープ決定後、対象と判断したフェーズについてのみ、`SKILL.md` の「ステップ0」と同じ判定ロジックで、P002から順に再実行する。ただし各フェーズは「既存の文書 + P001の更新差分 + `docs/CR.md`」を入力として、差分更新を行う(全面的な書き直しはしない)。
* CRと無関係な既存の仕様・実装・テストは変更しない。
* 各StepのStopping Condition(差し戻し上限)は通常実行時と同じルールに従う。

#### CRスコープの決定(必須の手順)

* CRの影響を、まず次のようなおおまかなカテゴリに分類する(複数該当してもよい)。この分類は目安であり、実際のCR内容に照らして判断が異なる場合はその判断を優先し、理由を記録する。

| カテゴリ | 典型例 | 目安として再オープンするフェーズ |
|---|---|---|
| UI表示文言のみ | ラベル・メッセージ文言の変更 | P002(該当箇所のみ)、P007(該当タスクのみ) |
| 画面項目追加・変更(バックエンド契約変更なし) | 既存APIの範囲内で完結する画面項目の追加・並び替え | P002、P004、P005〜P009(該当スプリント/テストのみ) |
| API契約変更 | リクエスト/レスポンス形式、エンドポイントの追加・変更 | P002、P003、P004、P005〜P009(該当スプリント/テストのみ)、必要なら P022(ArchitectureHandbook) |
| データモデル変更 | テーブル追加・カラム変更、リレーション変更 | P002(該当する場合)、P003、P004、P005〜P009 |
| 非機能・インフラ変更 | 可用性・TLS・スケーラビリティ・ログ集約基盤などの変更 | P003(委譲先の明記)、P005、P302 |

* 「データモデル変更」カテゴリに該当する場合は、上記の再オープン対象に加えて、**スキーマ変更の適用方式が冪等かどうかを必ず確認する**。
  * `docs/P003-backend-spec.md` に記載されているマイグレーション方式(全件再実行/差分適用/バージョン管理テーブルの有無)を確認する。記載が無い場合は、実際のコード(マイグレーション実行処理)を読んで現在の方式を特定し、P003に追記する。
  * `ALTER TABLE ... ADD COLUMN` のように、条件付き実行の構文を持たないDDLを追加する場合は、既存の適用方式のままで**アプリケーションを再起動しても正常に起動するか**を必ず確認する。全件再実行方式のまま素朴に追加すると、2回目以降の起動で `duplicate column name` 等のエラーになりアプリが起動しなくなる。
  * 冪等でない場合は、冪等化(バージョン管理テーブルの導入、適用済みエラーの捕捉など)もCRの対応範囲に含め、その判断と実施内容をCRの記録に残す。
  * この確認は単体テスト・結合テストでは代替できない(テストごとに新しい一時DBを作る構成では常に初回実行になるため)。**実際に初期化処理を2回連続で実行し、2回目も成功すること**をもって確認とし、結果をテスト記録に残す。
* 上記の対応表はあくまで目安であり、機械的に当てはめるだけでは不十分な場合がある。次を必ず行う。
  * **対象としたフェーズ**とその理由を記録する。
  * **対象外とした(再オープンしなかった)フェーズ**と、なぜ再オープンが不要と判断したかの理由も記録する(過小スコープ・過大スコープのどちらにもブレやすいのはこの「対象外」の判断であるため、理由の言語化を必須とする)。
  * P020(実装構造)・P010(横断レビュー)・P201(実装横断レビュー)・P301(全体INDEX)・P302(納品物作成)は、対象範囲のフェーズに実質的な変更が入った場合は原則として再実行が必要になる(目次・成果物一覧の整合性を保つため)。除外する場合はその理由も記録する。
* この「対象/対象外+理由」の記録は、CRの記録(`docs/CR.md` の該当CR本文の「対処内容」欄、完了後は `docs/cr-records/CR-{番号}.md`)に残す。P904(変更要求の反映確認)は、この記録を参照してスコープの妥当性も確認する。
