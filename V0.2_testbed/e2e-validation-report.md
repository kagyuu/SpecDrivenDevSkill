# spec-driven-dev Skill(V0.2) End-to-End 実地検証レポート

## 概要

* **何を検証したか**: `spec-driven-dev` Skill(V0.2、`.claude/skills/spec-driven-dev/`)を、会議室予約システム(社内Webアプリ、`docs/01-requirement.md`)に対してフェーズ2〜9まで通しで自動実行し、Skillの指示書(`SKILL.md`, `SKILL-0N-*.md`, `TEMPLATE-0N-*.md`)自体に矛盾・実行不能な箇所がないかを実地検証した。フェーズ6以降は、生成した実装指示・テスト指示・修正指示を、本来別セッションに委ねる想定の実装/テスト/修正担当Agentとして自分自身で実際に実行し、コードを書き、テストを実際に走らせ、不具合が出れば修正サイクルも回した。
* **どこまで検証したか**: フェーズ1(人間レビュー済み)〜9まで全フェーズ。通常は1フェーズごとに人間レビューで停止するルールを、`testbed.md`記載の方針どおり無人実行のため自己レビューに置き換えて連続実行した。
* **いつ実施したか**: 2026-07-30。

### 実装上の逸脱(Skillの欠陥ではなく実行環境起因)

本検証環境はネットワーク分離されており、`registry.npmjs.org`・`pypi.org`等へのパッケージ取得アクセスが403で拒否される(プロキシの許可リストに含まれているにもかかわらず実際には403が返る状態だった)。そのため:

* バックエンド: 仕様上のFastAPIをPyPIから取得できず、その内部基盤であるStarlette + Pydantic(事前インストール済み)を直接用いて同等のREST APIを実装した。
* フロントエンド: 仕様上のReact 18 + TypeScript + Viteをnpmから取得できず、ビルド不要の素のHTML/CSS/JavaScriptで実装した。
* テスト: `pytest`が利用できず、標準`unittest`を使用した。
* UI自動化: ブラウザ自動化ツールが利用できず、画面操作はAPIシナリオスクリプトで代替した。
* `uv sync` / `npm install` / `docker compose build`は実行できず(または実行していない)、これらのビルド成立性は本検証の範囲外とした。

これらはいずれも`docs/06-impl-direction.md`・`docs/09-deliver.md`に明記し、Skill自体の指示は変更していない。

## Skillの不備一覧

### 1. 開発体系の整合性

#### 1-1. フェーズ2(外部API仕様の完全確定)とフェーズ3(認証方式の内部確定)の分担が噛み合わない箇所がある — 重大度: 中

* **該当ファイル:箇所**: `SKILL-02-frontend-spec.md`「アウトプットの記載内容」(全APIの完全な外部仕様を要求)と、`docs/01-requirement.md`(本検証の入力仕様書)の「認証方式(セッション/JWT等)…は次フェーズ(バックエンド詳細設計)で確定する」という記述。
* **事象**: `SKILL-02`はフェーズ2で全APIの「レスポンス形式、ステータスコード、エラーケース」まで含む完全な外部仕様の確定を要求する。ログインAPIの外部仕様には「Cookieを使うのかトークンを返すのか」というクライアント可視の挙動が本質的に含まれるが、これは一般に「認証方式」の一部として扱われ、`SKILL-03`(バックエンド詳細設計)側で決めるべき事項という理解も同時に成立してしまう。
* **影響**: フェーズ2の担当者が「認証方式はフェーズ3で決める」と誤解してフェーズ2を「未確定のまま」進めてしまう、あるいは逆にフェーズ3で「Cookie前提で書いたのに実は外部仕様側で確定していなかった」という手戻りが起きうる。
* **実際の解釈・対応**: フェーズ2の段階で「Cookie(`session_id`, HttpOnly)を使う」という外部から見える契約だけを先に確定し(`docs/02-frontend-spec.md` 2章)、Cookieの中身の生成方式・保存場所・有効期限などの内部実現(PBKDF2ハッシュ、SQLite `sessions`テーブル、8時間有効)はフェーズ3(`docs/03-backend-spec.md` 2〜3章)で確定するという分担で進めた。SKILL側にこの「外部から見える認証方式の骨格はフェーズ2、内部実現はフェーズ3」という分担の明記がないため、今回は自己判断で埋めた。

#### 1-2. `docs/08-fix-plan/08-fix-resolved.md` / `08-fix-unresolved.md` の「全体状態」列挙値に「全解決」を表す値がない — 重大度: 低

* **該当ファイル:箇所**: `TEMPLATE-08-fix-resolved.md` / `TEMPLATE-08-fix-unresolved.md` の「概要」節、`全体状態: PARTIAL / BLOCKED / SPEC_CONFLICT`。
* **事象**: 列挙されている3値(PARTIAL=部分解決, BLOCKED=ブロック中, SPEC_CONFLICT=仕様矛盾)には、いずれも「検出された修正課題を全件解決できた」という状態を表す値が存在しない。
* **影響**: 今回のように検出1件・修正1件(全件解決)というよくあるケースでも、テンプレートの語彙上「ぴったりの値」を選べない。
* **実際の解釈・対応**: 最も実態に近い`PARTIAL`を選び、備考で「全て解決済みだが〜」と補足する形で記載した(`docs/08-fix-plan/08-fix-resolved.md`)。

### 2. 実行可能性

#### 2-1. OKF目次のリンクが、修正完了後にファイル削除ルールとかみ合わずダングリングリンクになる — 重大度: 中

* **該当ファイル:箇所**: `SKILL.md`「目次(OKF形式)について」と`SKILL-08-fix-plan.md`「障害を修正できた場合」の手順(`docs/08-fix-plan/F000-{fix-name}.md`を`fixed/`にコピーした後、元の`docs/08-fix-plan/F000-{fix-name}.md`を削除する)。
* **事象**: `docs/08-fix-plan.md`(OKF目次)の各行は本来`docs/08-fix-plan/F000-{fix-name}.md`へのリンクを保持する形で作成される。修正完了後にその元ファイルを削除するルールになっているため、目次のリンク先を`fixed/`配下の新しいパスに更新するという指示がどこにも書かれていない場合、目次のリンクは機械的にはリンク切れになる。
* **影響**: 目次を辿って修正内容を確認しようとした人間・後続Agentがリンク切れに遭遇する。
* **実際の解釈・対応**: `docs/08-fix-plan.md`のF001行のリンク先を、修正完了と同時に`./08-fix-plan/F001-....md`から`./08-fix-plan/fixed/F001-....md`へ書き換えることで対応した。SKILL側にはこの「完了時にリンク先を`fixed/`に付け替える」という指示は明記されていないため、今回は自己判断で行った。

#### 2-2. フェーズ7の結果が「FAIL0件」だった場合にフェーズ8をどう扱うかが規定されていない — 重大度: 中

* **該当ファイル:箇所**: `SKILL.md`「ステップ0」のフェーズ8判定条件、および`SKILL-08-fix-plan.md`「目的」。
* **事象**: `SKILL.md`は「1,2,...,7,8が存在するが、8の目次に未解決の修正が残っている→フェーズ8」としか書いておらず、「7が完了したがFAILが0件だった場合に、空の`docs/08-fix-plan.md`を作ってフェーズ8を即完了とみなすのか」「そもそも`docs/08-fix-plan.md`自体を作らずフェーズ9に進んでよいのか」が明記されていない。`SKILL-08-fix-plan.md`の目的も「テストに失敗しているものを選び出して修正する計画をつくる」としか書かれておらず、失敗がない場合の挙動に触れていない。
* **影響**: 実行するAgentによって「フェーズ8をスキップしてフェーズ9へ進む」「空の`08-fix-plan.md`を作ってから進む」で解釈が割れうる。
* **実際の解釈・対応**: 今回はT004で実際に1件FAILしたため、この分岐には実際には入らなかったが、指示文の検査の過程でこの曖昧さを発見した。仮にFAILが0件だった場合は、「未解決障害数0件」の`docs/08-fix-plan.md`(目次に項目なし)と、その旨を明記した`08-fix-plan/08-fix-unresolved.md`を作成し、即フェーズ9へ進む、という解釈が最も`SKILL.md`の他の記述(「全解決していれば次フェーズへ」という一貫した設計思想)と整合すると考えられる。

#### 2-3. フェーズ6の「タスク分割9観点」をすべてのアプリ規模に機械的に適用すると、タスク数が過大になりうる — 重大度: 低

* **該当ファイル:箇所**: `SKILL-06-impl-direction.md`「実装担当Agentが一度に多くのことを考慮しなくてよいように、タスクは次のような観点で分割する」(9項目列挙)。
* **事象**: 型/スキーマ、バリデーション、Repository、Service、APIハンドラ、フロントエンド部品、画面とAPIの接続、横断機能、結合確認、の9観点を1スプリントごとに全て独立タスク化すると、本検証の4スプリント構成だけで最大30件超のタスクファイルが生成されうる。一方で`SKILL-04-impl-plan.md`は「各スプリントのコード量を同じにする」という原則を掲げるが、コード量の測定基準(LOC/画面数/API数など)は定義されていない。
* **影響**: 小〜中規模アプリでは9観点を機械的に全部独立させると過剰に細分化されたタスクファイルが量産され、逆に指示の見通しが悪くなる可能性がある。分割してよい/まとめてよい基準が示されていない。
* **実際の解釈・対応**: 今回は9観点を目安としつつ、関連の強いレイヤ(例: Repository+Service+APIハンドラ)を1タスクにまとめ、1スプリントあたり4タスク(計16タスク)に圧縮した。SKILL側に「まとめてよい条件」の記載がないため、時間的制約を踏まえた自己判断で対応した。

### 3. 記述一貫性

#### 3-1. `TEMPLATE-07-test-direction.md`のテストID記法(`TSTxxx`)がSKILLのファイル命名規則(`T000-{test-name}.md`)と食い違う — 重大度: 低

* **該当ファイル:箇所**: `TEMPLATE-07-test-direction.md` 1行目「【テストID】TSTxxx」。`SKILL-07-test-direction.md`・`SKILL.md`はいずれも成果物ファイル名を`docs/07-test-direction/T000-{test-name}.md`とし、OKF目次の例も`T001`表記である。
* **事象**: テンプレートのプレースホルダだけが`TSTxxx`という別の接頭辞を使っており、ファイル名・目次表記の`T001`等と字面が一致しない。
* **影響**: テンプレートをそのまま機械的に埋めると、テストIDの表記(`TST001`)とファイル名・目次のID(`T001`)が食い違ったドキュメントができあがる。
* **実際の解釈・対応**: ファイル名・OKF目次の表記に合わせ、テストIDは`T001`〜`T005`の形式で統一した(`TSTxxx`は採用しなかった)。

#### 3-2. `TEMPLATE-08-fix-direction.md`の修正タスクID記法(`FIXxxx`)が、Fの連番ファイル名・対応障害ID(`Fxxx`)と別系統になっている — 重大度: 低

* **該当ファイル:箇所**: `TEMPLATE-08-fix-direction.md`「【修正タスクID】FIXxxx」「【対応障害】Fxxx / TSTxxx」。`SKILL-08-fix-plan.md`はファイル名を`docs/08-fix-plan/F000-{fix-name}.md`、目次の項目キーも`F000`系(例: `F001`)としている。
* **事象**: 同一ドキュメント内に「修正タスクID(`FIXxxx`)」と「対応障害(`Fxxx`)」という2つの異なる接頭辞のID体系が併存しており、かつ`Fxxx`側の隣に`TSTxxx`(3-1と同じ問題)も併記されている。
* **影響**: 修正指示書を読む担当者が「`FIX001`と`F001`は同じ障害を指すのか、別物か」を誤解しうる。
* **実際の解釈・対応**: `docs/08-fix-plan/F001-....md`内で「修正タスクID: FIX001」「対応障害: F001 / T004」のように、テンプレートの記法をそのまま踏襲しつつ、F001(ファイル名・目次ID)とFIX001(タスクID)が同一障害の別ラベルであることが分かるよう本文中で明示して対応した。

## 問題がなかった/うまく機能した点

* **ファイル名・フォルダ名のクロスファイル整合性は完全に保たれていた**: `SKILL.md`の成果物一覧表、各`SKILL-0N-*.md`のインプット/アウトプット文書欄、`TEMPLATE-0N-*.md`の参照先を全て突き合わせたが、`V0.2/review-report.md`が指摘していたような「フェーズ間でのファイル名不一致」(例: 存在しない`01-overview.md`への参照)は**1件も見つからなかった**。V0.2での修正が実際に有効であったことが確認できた。
