## 1. V1.0で解決した5件の検証結果

### 1-1. #1(初期化の実施主体)— 前提の実在を実測で確認

V1.0はコード格納先の初期化の実施主体をP007(計画)からP102(Executor)へ移した。差分検証では既にコードが存在するため初期化そのものは再現できないが、**この変更が生む副作用の実在**を直接検証した。

`INDEX.md` のみを含むディレクトリ(P020実行直後の状態を模したもの)で、実際に次を実行した。

```
npm create vite@latest . -- --template react-ts
```

結果:

```
> create-vite . --template react-ts
—  Operation cancelled
---EXIT: 0 ---
---FILES---
INDEX.md          ← 1ファイルも生成されていない
```

**終了コードが `0` である点が重要である。** レビュー時には「対話プロンプトで停止して無人実行が止まる」と予測していたが、実際にはプロンプトがEOFを受けて即座にキャンセルされ、**成功を示す終了コードを返しながら何も生成しない**。終了コードだけを確認する実行担当は「初期化に成功した」と誤認し、スキャフォールドが存在しないまま実装タスクへ進むことになる。

V1.0が `SKILL-P102-implement.md` に追加した3つの規定(対話モードで実行しない / ツールが生成する構成と同等になるよう配置してよい / 既存の `INDEX.md` を削除しない)は、この失敗モードに対する妥当な対策である。あわせて `SKILL-P007-impl-direction.md` に加えた「`{ツール名}` 相当の構成で初期化する」という書き方の指示も、`V0.9_testbed` のP007が偶然採っていた回避策を明文化したものとして機能する。

### 1-2. #2(「完了」の語)— 文書レビューで確認

`SKILL.md` の2箇所(記述完了の判定・OKF完了の判定)に相互参照が入り、共通指示のみを通読しても次が読み取れる状態になった。

* 記述完了とOKF完了は別の基準であること。
* Plan Loop Stepの終了条件はP010のレビュー合格のみを要件とし、P007・P008・P009のOKF完了を含まないこと。
* **Plan Loop Step完了時点でOKF目次が `[ ]` のままであるのが正常**であること(V0.9では、この「正常である」という明示が無かったため、未完了に見える状態を異常と誤認する余地があった)。

差分検証では新規にPlan Loop Stepを通していないため、実行担当の挙動そのものは確認していない。ただし本件は誤読の防止が目的であり、文面上の曖昧さが解消されていることをもって確認とする。

### 1-3. #3(トポロジー決定主体)— 合格

新ルールに従いP003を実行したところ、`docs/P003-backend-spec.md` に §2.3「開発・テスト時のクロスオリジン方針」が追加され、次が記録された。

* CORSヘッダを緩めるだけでは解決しない理由(ワイルドカードのACAOと `Access-Control-Allow-Credentials: true` は併用不可)。
* 決定(Vite開発サーバのproxyで同一オリジン化、CORSミドルウェア不採用、相対パスfetch)。
* 理由(SameSite=Laxを維持できる / 本番配布トポロジーと接続前提が一致する)。
* 検討した代替案2件(CORSミドルウェア導入、トークン認証への変更)とその却下理由。

続いてP021が **ADR-006** を起票した。`TEMPLATE-ADR.md` の節構成(タイトル/状態/日付/関連要求/背景/決定内容/理由/検討した代替案/残存リスク/影響範囲/関連成果物/備考)に沿っており、残存リスクには★ACCEPTED★が付された。

`docs/P009-acceptance-direction.md` には「テスト実行環境(全テスト共通)」節が追加され、ADR-006を参照する形になった。**各A0NNファイルに同じ記述を複製せず、共通の目次側に1回だけ置いた**のは、`SKILL.md` の「共通ルールは1箇所に置き、各所からは参照する」という方針に沿った判断である。

## 2. 新設した一般ルール(停止時の対処案提示)の検証結果

### 検証方法

`docs/P003-backend-spec.md` を一時的に退避し、`docs/.inprogress` を `P021` に設定してOverview Stepを実行させた。これによりOverview Stepの停止条件「必要な成果物が不足していた場合、処理を停止して人間に報告する」に該当させた。

### 検証結果: 合格(ただし規定に不備を1件発見)

`docs/.stop-report.md` が生成され、次が記録された。

* 停止した時点(フェーズ・Step・`.inprogress` の値)と、該当した停止条件。
* 問題の内容 — 単に「P003が無い」ではなく、**既存のADR-003〜006がいずれもP003を根拠にしていること**を具体的に列挙し、なぜこのまま進めないかを説明している。
* **対処案3案**(復元 / 再作成 / 欠いたまま続行)。それぞれに利点・欠点・判断材料を付し、推奨案を明示した。「欠いたまま続行」案には推奨しない理由(誤りが下流に伝播する)を書いている。
* 「対処案の提示のみを行い、実施はしていない。`docs/ADR.md` は変更していない」という明記。

V1.0で追加した「**提示であって実施ではない**」の規定が実際に効いており、停止したフェーズが勝手に復旧作業を始めることはなかった。

### 2-1. 発見した不備(低重大度) — 本検証で自動修正済み

V1.0のルール文は記録先を次のように定めていた。

> 報告内容を、**そのフェーズの成果物文書に記録する**。そのフェーズの成果物文書がまだ存在しない場合は `docs/.stop-report.md` に記録する。

この規定は**差分実行・再実行の場面で破綻する**。今回のP021の成果物は `docs/ADR.md` であり、これは前回のビルドで既に存在していた。規定を文字どおり適用すると、停止報告を `docs/ADR.md` の中に書き込むことになるが、同ファイルは `TEMPLATE-ADR.md` が定める構造(ADR一覧 + ADR-NNN の並び)を持つ**納品対象の成果物**であり、そこに「停止しました。対処案は…」という節を挿入するのはテンプレート違反であり、かつ成果物を汚染する。

一方 `docs/P302-deliver.md` のように「10. 未整備事項」という自然な受け皿を持つ成果物もあるため、「常に成果物へ書く」も「常に `.stop-report.md` へ書く」も単純には決められない。

**自動修正した内容**(`V1.0/SKILL.md`): 記録先の規定を次のとおり改めた。

* 原則として `docs/.stop-report.md` に記録する(成果物の有無によらず、常にここに残る)。
* そのうえで、成果物文書側に停止事由を記載する所定の欄がある場合(例: `docs/P302-deliver.md` の「10. 未整備事項」)は、そちらにも記載する。
* 成果物文書の定められた構造(テンプレート)を崩してまで書き込まない。

この修正により、報告の所在が常に1箇所に定まり、かつ既存の受け皿がある場合の二重記載も許容される。**軽微であり人間の判断を要しないため、本検証内で修正した。**

## 3. 新たに見つかった問題

### 3-1. 生成されたテストスイートが再実行可能でない(中重大度) — **人間の判断を受けて解決済み**

> **本項の経緯**: 発見時点では「対処方針の決定に設計判断を要する」として未修正のまま報告した。その後、人間から「テストデータの投入時にリセットすれば防げないか。データ投入を伴わないテストの冪等性が失われる点は許容する」との方針が示され、これを受けて**V1.0本体にルールを追加し、テストベッドで是正・確認まで実施した**。以下、発見時の記述に続けて、決定した方針と確認結果を記載する。

#### 事象

結合テスト(Playwright、9件)は、テストDBを削除した直後に実行すると**9件全PASS**するが、**同じDBのまま続けてもう一度実行すると2件がFAILする**。

```
1回目(DB削除直後):  9 passed
2回目(同一DB):      7 passed / 2 failed
```

失敗内容:

```
T003: strict mode violation: getByText('一般花子 / テスト会議T003') resolved to 2 elements
T005: strict mode violation: getByText('T005未来の予約') resolved to 3 elements
```

原因は、`client/playwright.config.ts` がテストDBを固定パス(`server/data/e2e-test.db`)で指定しており、**テスト実行のたびに作成された予約データが同じDBに累積する**ことである。各テストは実行前にDBを初期化する処理も、作成したデータを後片付けする処理も持たない。

#### なぜこれが重要か

**P205(結合テスト再実施)は、まさに同じテストを再実行するフェーズである。** Reviewer Loopは「P201でFAIL → P202〜P204で修正 → P205で再実施」という流れを持ち、通常運用のなかで同じテストが2回目・3回目と実行される。この性質があると、P205は**修正とは無関係な理由でFAILを検出する**ことになり、次のいずれかを招く。

* P202が存在しないバグの修正計画を立てる(実際にはテストデータの累積が原因)。
* Reviewer Loopが収束せず、3回の差し戻し上限に達して停止する。

`V0.9_testbed` でこれが顕在化しなかったのは、各ラウンドが独立したセッションで実行され、そのつどDBが作り直されていたためと考えられる。差分検証で同一環境の連続実行を行ったことで初めて表面化した。

#### Skill側の欠落として何が言えるか

本Skillは、**マイグレーションの冪等性**については明確な規定を持っている(P003で方式を明記、P006でテスト観点に含める、P903で「実際に2回連続実行して確認する」、P302の実行前チェック項目8)。これはV0.6で追加され、以後複数版で機能している仕組みである。

しかし、**テストスイート自体が再実行可能であること**については、同等の規定が無い。`SKILL.md` の共通指示にある「テスト実行コマンドは記載前に一度実際に実行し、意図したテストが実行されることを確認する」(V0.8の2-15)は**1回の実行**しか要求しておらず、2回目を要求していない。

つまり、マイグレーションに対して既に確立している「2回連続で実行して確認する」という考え方が、テストスイートには適用されていない。

#### 発見時に想定した対処の方向性

1. `SKILL.md` の共通指示、または `SKILL-P006-test-plan.md` に「テストは繰り返し実行可能であること(独立したデータストアを使う、または各テストが自身の作成データを後片付けする)」を要求する規定を追加する。
2. `SKILL-P302-deliver.md` の実行前チェック項目8(再起動の冪等性)に倣い、**テストスイートを2回連続実行して同じ結果になること**を確認する項目を追加する。
3. 上記1・2の双方を行う。

いずれも新しいルールの追加であり、どのフェーズに置くか・どこまで厳密に要求するか(全テストに一律で課すのか、E2E/永続ストアを使うテストに限るのか)は設計判断を伴うため、人間の判断を仰いだ。

#### 決定した方針(人間の判断)

**「テストデータの投入時にリセットする。データ投入を伴わないテストの冪等性が厳密には失われるが、そこは許容する」**

この方針を実装するにあたり、次の2点を整理した。

* **「リセット」の定義**: 全行削除ではなく**マイグレーション適用直後の状態への復元**を指す。本テストベッドでは `server/migrations/002_seed_initial_users.sql` が `admin001`/`user001` を投入しているため、全行削除するとログインすらできなくなる。この定義により、本Skillが既に持つ「マイグレーションは冪等であること」という保証をそのまま流用できる。
* **リセットの単位**: 「テスト1件ごと」ではなく「**スイートの実行ごとに1回**」とした。テストごとにリセットすると、先行するテストが用意したデータまで消してしまい、投入を伴わないテストは「冪等性を失う」のではなく**動かなくなる**。スイート単位であれば、実行のたびに必ず同じベースラインから始まるため、**スイート全体としては何度実行しても同じ結果**になる。得られる性質は「個々のテストの独立性」ではなく「**スイート単位の再実行可能性**」であり、人間が示した割り切り(投入を伴わないテストは単独では成立しない)はこの整理のもとでそのまま受け入れられる。

#### V1.0本体への反映

| ファイル | 追加した規定 |
| --- | --- |
| `SKILL-P006-test-plan.md` | テストデータのライフサイクル方針(復元の単位・ベースラインの定義)を決めて記載することを必須化。既定は「スイートの実行ごと」 |
| `SKILL-P008-test-direction.md` | 各テストの「事前準備」は上記方針に従うこと。復元は**アプリケーション起動より前**に、スイート全体で1回だけ実行されるようにすること |
| `SKILL-P009-acceptance-direction.md` | 同上。あわせて、データの永続自体を検証するテスト(再起動耐性)は復元処理と衝突しないよう別のデータストアを用いること |
| `SKILL.md` 共通指示 | **テストスイートは続けて2回実行しても同じ結果になることを確認する**。マイグレーション冪等性の「実際に2回連続実行して確認する」と同じ考え方。確認の単位はスイート全体であり、個々のテストの単独実行可能性ではない |

#### テストベッドでの是正と確認結果

`client/scripts/reset-e2e-db.mjs` を新規作成し、`client/playwright.config.ts` の `webServer` 起動コマンドから実行するようにした。

| スイート | 1回目 | 2回目 | 3回目 |
| --- | --- | --- | --- |
| 結合テスト(Playwright、9件) | ✅ 9 passed | ✅ 9 passed | ✅ 9 passed |
| 受け入れ結合テスト(Playwright、5件) | ✅ 5 passed | ✅ 5 passed | — |

**是正前は2回目で2件失敗していたが、是正後は連続実行でも全件PASSする。** 詳細は `docs/test-records/20260820-test-rerunnability-record.md` 参照。

#### 実装過程で判明した2つの事実

**(a) Playwrightの `globalSetup` はこの用途に使えない。** 当初 `globalSetup` に復元処理を置いたが、実行ログから **`webServer` が `globalSetup` より先に起動する**ことが判明した。この順序では起動済みバックエンドが開いているDBファイルを削除することになり、実行が不安定になった(ネイティブクラッシュを再現)。**復元はテスト対象アプリケーションの起動より前でなければならない**という一般則として、`SKILL-P008-test-direction.md` に「テストフレームワークの初期化フックはアプリケーション起動より後に実行される場合があるため、フックの実行順序を必ず確認すること」を明記した。これは実際に動かさなければ気づけなかった点である。

**(b) 本実行環境のNode.jsで `fs.rmSync` がネイティブクラッシュする。** 復元スクリプトの実装中、`fs.rmSync()` が Node.js v24.12.0(Windows)で対象の有無によらず必ずクラッシュすること(`STATUS_STACK_BUFFER_OVERRUN`)を最小再現で特定した。`fs.unlinkSync()` + `try/catch` は正常に動作するため、そちらを用いている。

> **この不具合は、`V0.9_testbed` で「原因不明・ソース内容によらず発生」と記録されていた `npm run build`(`vite build`)のネイティブクラッシュを説明する可能性が高い。** `vite build` は出力先ディレクトリの掃除に `fs.rmSync(outDir, { recursive: true, force: true })` を用いるためである。アプリケーションの欠陥でもSkillの欠陥でもなく、実行環境の問題である。

##### この2点をどこに記録したか

同じ試行錯誤を次回以降くり返さないよう、**知見の性質に応じて置き場所を分けた**。

| 知見 | 置き場所 | 理由 |
| --- | --- | --- |
| (a) 初期化フックの実行順序 | `SKILL-P008-test-direction.md`(Skill本体) | 特定の製品に依存しない一般則として書ける(Playwrightは例示にとどめた)。復元手順を書くのはP008/P009であり、その担当が読む場所に置くのが適切 |
| (b) `fs.rmSync` の不具合(事実) | `docs/ArchitectureHandbook.md` 第9章「既知の制約・技術的負債」(プロジェクト側) | Skillに書くと陳腐化する。Nodeのパッチで偽になり、他OSでは無関係であり、Skillは任意のマシンにコピーされる。`SKILL-P007-impl-direction.md` が技術スタック名のハードコードを禁じているのと同じ理由。第9章はP101のインプットであるため、記録すればExecutorに自動的に引き継がれる |
| (b') 上記から一般化した**切り分け手順** | `SKILL.md` 共通指示(Skill本体) | 「結果を出力せず異常終了したら、最小再現で環境要因かを切り分けてから判断する」は再利用可能な一般則である。`V0.9_testbed` が `vite build` のクラッシュを原因不明のまま持ち越したのは、この規定が無かったためであり、あれば同じ切り分けに到達できたはずである |

この分け方自体が、本Skillの既存方針(特定の技術解を決め打ちせず、判断の手順と記録先を規定する)に沿っている。

## 5. 総評

V1.0の変更5件+新設ルール1件は、実地で確認できた範囲すべてで意図どおり機能した。特筆すべきは次の2点である。

1. **レビュー段階で予測した副作用が、予測より危険な形で実在した**(#1のスキャフォールド問題。終了コード0で無言の失敗)。方針レビューの段階でこの副作用を捕捉し、実装前に対策を組み込めたことは、今回の進め方(実装前に方針をレビューする)の有効性を示している。
