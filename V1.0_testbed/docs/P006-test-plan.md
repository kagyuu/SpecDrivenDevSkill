# テスト計画書 — 会議室予約システム

> 本書は `spec-driven-dev` Skill フェーズP006の成果物。`docs/P002-frontend-spec.md`・`docs/P003-backend-spec.md`・`docs/P005-impl-plan.md` にもとづき、テストレベル・観点を確定する。個々のテストケースの実装・具体的パラメータは、この計画をもとに `docs/P007-impl-direction.md`(単体テスト)、`docs/P008-test-direction.md`(スプリント内結合テスト)、`docs/P009-acceptance-direction.md`(スプリント横断・システム・受入テスト)で別途作成する。

## 1. テストレベルと目的

| テストレベル | 目的 | 主な実装先 |
| --- | --- | --- |
| 単体テスト | `docs/P002-frontend-spec.md`・`docs/P003-backend-spec.md` で定義した、画面・APIの構成要素(バリデーション関数・Repository・Service・APIハンドラ・UIコンポーネント)が単体で仕様どおりに動くか | `docs/P007-impl-direction/U00N-*.md` |
| 結合テスト | 同一スプリント内で、画面とAPI、Service層とRepository層などが連携して仕様どおりに動くか | `docs/P008-test-direction/T0NN-*.md` |

## 2. 機能観点

各画面・各APIエンドポイントについて、正常系に加え、少なくとも以下の異常系を対象とする。

* バリデーションエラー(必須未入力、文字数超過、形式不正、終了時刻≦開始時刻)
* Not Found(存在しないID指定)
* 認可エラー(未ログイン、他ユーザーのリソースへの操作、一般ユーザーによる管理者専用操作)
* 業務ルール違反(予約重複、収容人数超過、社員ID重複、無効化された会議室への予約、自己アカウント無効化)

重複判定の境界値(`docs/P003-backend-spec.md` §5.9 の半開区間ルール、背中合わせの予約が重複にならないケース)は、単体テスト(Service層の重複判定関数)と、スプリントをまたぐ業務フロー確認の両方でカバーする。前者は `docs/P007-impl-direction.md`(U002該当タスク)、後者は `docs/P009-acceptance-direction.md` の対象とする。

**閲覧範囲のマスキング(※CR-001により追加)**: 「備考(社内向けメモ)」のように、同一リソースの一部フィールドだけを閲覧者に応じてマスキングする(レスポンス全体は返すがフィールド値のみ`null`にする)観点は、通常の認可エラー(403)の確認だけでは検出できない(リクエスト自体は200で成功するため)。この観点は明示的にテスト対象へ含める: (1) 所有者が取得した場合に実際の値が返ること、(2) 管理者が取得した場合に実際の値が返ること、(3) 所有者でも管理者でもない一般ユーザーが取得した場合に`null`が返ること、の3パターンを最低限確認する。スプリント内結合テスト(`docs/P008-test-direction.md`)の対象とする。

## 3. 非機能観点

| 観点 | 内容 | 実施レベル |
| --- | --- | --- |
| 性能 | カレンダー表示(`GET /api/reservations` を含む初期表示)が実行可能な範囲で許容時間内に完了すること。本番相当の負荷試験は `docs/P302-deliver.md` に委譲(`docs/P003-backend-spec.md` §7参照) | システムテスト(実行可能な範囲) |
| セキュリティ | 未認証・認可エラー時のステータスコード/エラーコードが仕様どおりであること、パスワードが平文でDB・レスポンスに含まれないこと | 結合テスト・システムテスト |
| 運用(ログ監視) | 標準出力への構造化ログ出力が行われること(実際のログ集約基盤への転送確認は対象外、`docs/P003-backend-spec.md` §7参照) | システムテスト(実行可能な範囲) |

## 4. 運用観点(再起動耐性)— 担当フェーズの明記

* `docs/P003-backend-spec.md` §4 に定めるとおり、データストア(SQLite)を持つ本アプリケーションでは、**アプリケーションを停止・再起動しても正常に起動すること**を確認する観点を必ずテスト計画に含める。
* マイグレーションが冪等でない実装になっていた場合、2回目以降の起動(＝2回目以降のマイグレーション実行)で `duplicate column name` 等のエラーが発生し、アプリが起動しなくなる不具合が典型例である。
* この観点は、テストごとに新しい一時データストア(一時SQLiteファイルまたはインメモリDB)を作成する単体テスト・スプリント内結合テストでは検出できない(常に「初回起動」と同じ状態からテストが始まるため、2回目の起動が発生しない)。
* したがって、この観点は**永続化された同一のデータストアファイルに対して実際にプロセスを2回以上起動する**ことで初めて検証できる。この検証は本テスト計画において**単体テスト(`docs/P007-impl-direction.md`)にもスプリント内結合テスト(`docs/P008-test-direction.md`)にも含めない**。両フェーズのインプット文書(`SKILL-P007-impl-direction.md`・`SKILL-P008-test-direction.md`)がテストごとに新しい一時DBを使う前提であることと矛盾しないようにするためである。
* この観点は**受け入れ結合テスト(`docs/P009-acceptance-direction.md`)が担当する**。P009側で、永続DBファイルに対する起動→データ作成→プロセス停止→再起動→データ確認、という一連のシナリオとして具体化する(詳細は同文書の該当テストケース参照)。

## 5. テスト遂行上の技術的決め事

* **外部APIのモック方針**: 本アプリケーションは外部APIサービス連携を持たない(要件定義のとおりGoogleカレンダー/Outlookカレンダー連携は対象外)。そのためモック対象の外部APIは無い。
* **テストデータの準備方法**:
  * 単体テスト: テストごとに一時SQLite DB(`:memory:` またはテスト用一時ファイル)にマイグレーションを適用してから実行する。
  * スプリント内結合テスト(P008): スプリント専用の一時DBファイルを使い、テストケースの前提となる最小限のシードデータ(ユーザー・会議室)をテストコード内で作成する。
  * 受け入れ結合テスト(P009): 永続DBファイル(実運用相当のパス)を用いる。再起動耐性テストではこのファイルを複数のテストケース間で意図的に共有する(§4参照)。それ以外のP009テストケースでは、原則としてテストケースごとにDBファイルを初期化する。
* **認証情報のテストデータ**: 管理者ユーザー(`employee_id=admin001`)・一般ユーザー(`employee_id=user001`, `user002`)をシード投入する(`docs/P007-impl-direction/U001-foundation-and-auth.md` のマイグレーションタスクで作成)。パスワードは全テスト共通で `TestPassw0rd!` とする。
