## 問題の内容

P021のインプット文書として規定されている `docs/P001-requirement.md` 〜 `docs/P009-acceptance-direction.md` のうち、**`docs/P003-backend-spec.md`(システム詳細設計書)が存在しない**。

このファイルは、ADRに記録すべき技術的決定の主要な供給元である。実際に、現行 `docs/ADR.md` の以下のADRは、その根拠をP003に置いている。

* ADR-003(データアクセスに標準ライブラリsqlite3を直接使用) — 根拠: P003 §5.9の重複判定クエリ
* ADR-004(パスワードハッシュにbcryptを採用) — 根拠: P003 §2.2
* ADR-005(セッション管理をSQLite永続化+Cookie方式) — 根拠: P003 §2.1
* ADR-006(クロスオリジンを開発サーバproxyで解決) — 根拠: P003 §2.3

したがって、この状態でP021を実行すると、既存ADRの妥当性を検証できず、また新規に追加すべき技術的決定を発見できない。P021の成果物である `docs/ADR.md` はP022(ArchitectureHandbook)のインプットでもあるため、不完全なADRのまま先へ進むと後続フェーズにも影響する。

## 対処案

### 案1: `docs/P003-backend-spec.md` を復元する(推奨)

* 内容: バックアップ・版管理(git等)から当該ファイルを復元し、`docs/.inprogress` が示すP021から再開する。
* 利点: 他の成果物との整合性が保たれる。P003を根拠とする既存ADR-003〜006の裏付けがそのまま維持される。
* 欠点: 復元元が存在することが前提。
* 判断材料: 直近の実行で `docs/P004-traceability-matrix.md` がP003の各節(§5.1、§2.2 など)を参照しており、P003が存在していた時点の成果物が残っている。したがって、何らかの事故で消失した可能性が高く、復元が最も自然である。

### 案2: P003を再作成してからP021へ進む

* 内容: Plan Loop Step の P003 まで戻り、`docs/P001-requirement.md`・`docs/P002-frontend-spec.md` からシステム詳細設計書を作り直す。その後 P004(トレーサビリティ)以降を再確認し、Overview Step へ進む。
* 利点: 復元元が無い場合でも前進できる。
* 欠点: 再作成した内容が、既存の実装(`server/` 配下)および既存ADR-003〜006と食い違う危険がある。特に §5.9(予約重複判定の半開区間ルール)は実装・テストが依存しており、再作成時に差異が生じると広範囲のテスト失敗を招く。再作成後は P004・P010 による整合性確認が必須になる。
* 判断材料: 実装が既に存在するため、再作成は「実装からの逆生成」に近い作業になる。案1が可能なら案1を優先すべきである。

### 案3: P003を欠いたままP021を実行する

* **推奨しない。** 既存ADR-003〜006の根拠が検証できず、ADRの正当性を担保できないまま `docs/ADR.md` を確定させることになる。P022(ArchitectureHandbook)がこれを入力として取り込むため、誤りが下流に伝播する。
* この案を採る場合でも、ADRの各項目に★FIXME★を付し、P003復元後に再検証が必要である旨を明記する必要がある。

## 推奨

**案1(復元)**を推奨する。案1が不可能な場合に限り案2を採り、その場合は再作成したP003に対してP004・P010を必ず再実行すること。
