## A004: 予約重複防止のシステム全体確認(境界値を含む)

- 実行日時: 2026-08-11 05:20
- 参照したテスト指示: docs/P009-acceptance-direction/A004-reservation-conflict-system-check.md
- 実行環境: Playwright(chromium)、APIRequestContext経由(UI操作なし)
- 実行コマンド: `cd client && npx playwright test tests/acceptance/a004_reservation_conflict_system_check.spec.ts`
- 結果: FAIL
- 期待結果: 手順2〜4すべてで409 `RESERVATION_CONFLICT`。
- 実際の結果: 手順2(重なる時間帯、10:30-11:30)は期待どおり409。**手順3(11:00-12:00、背中合わせ)は201(予約成立)** となり、テストの期待(409)と食い違った。手順4は未到達(手順3のassertで停止)。
- 失敗ログ抜粋: `Expected: 409 / Received: 201`(手順3、`backToBackAfter.status()`)
- 再現手順: `docs/P003-backend-spec.md` §5.9の重複判定ロジック(半開区間 `[start, end)`)どおりに実装されており、既存予約10:00-11:00に対して11:00-12:00の新規予約は「重複ではない」と判定され201になる。
- 影響がありそうなモジュール: `server/app/validation/reservation.py`(`overlaps`関数)、`server/app/repositories/reservations.py`(`find_conflicting`のSQL)。P202で、コードとテスト指示のどちらが誤りかを判定する。
- テスト指示との矛盾の疑い: **あり**。`docs/P003-backend-spec.md` §5.9は「この判定式の性質上、`new.start_time == existing.end_time` または `new.end_time == existing.start_time`(背中合わせの予約)は重複とみなさない。例: 会議室Xに10:00-11:00の予約が既にある場合、同じ会議室Xに11:00-12:00の予約を新規作成することは重複エラーにならず成立する」と明記しており、`docs/P009-acceptance-direction/A004-*.md` 手順3・4の期待結果(409になる)と正面から矛盾する。
- 次工程への申し送り: P202で「テスト指示側の誤り」として扱う候補。ただし、コード側が本当に仕様(P003)どおりに実装されているかも合わせて再確認したうえで最終判定する。
