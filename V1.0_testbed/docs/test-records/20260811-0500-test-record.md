## T006: 予約編集(自己除外重複)の結合確認

- 実行日時: 2026-08-11 04:47
- 実行者: Executor(P103)
- 対象ブランチ/コミット: 作業ツリー(未コミット)
- 参照したテスト指示: docs/P008-test-direction/T006-reservation-update-self-exclusion.md
- 実行環境: Playwright(chromium) + Vite dev server + uvicorn(実サーバー)
- 事前ビルド結果: 上記共通のとおり
- 実行コマンド: `cd client && npx playwright test tests/integration/t006_reservation_update_self_exclusion.spec.ts`
- 結果: FAIL
- 期待結果: 更新が409にならず成功し、件名が更新される。
- 実際の結果: S04での更新自体はUI上成功しS02へ遷移したが、更新後の内容を検証するためAPI経由で `GET /api/reservations/{id}` を呼んだところ、レスポンスがJSONとしてパースできない("Internal S..."で始まる非JSON本文)エラーになった。
- 失敗ログ抜粋: `SyntaxError: Unexpected token 'I', "Internal S"... is not valid JSON`
- 再現手順: 実サーバー(uvicorn、複数ワーカースレッド)に対してリクエストを送ると、バックエンドのログに `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread.` が断続的に出力される(T001実行時にも同様のエラーがログに出ていたが、その時はレスポンス自体は200で返っていた)。T006では、このエラーがハンドラ実行中に発生しレスポンスの生成自体に失敗したため、FastAPIの既定の500エラーページ(非JSON)が返り、テストのJSONパースが失敗した。
- 影響がありそうなモジュール: `server/app/api/deps.py`(`get_db` 依存関数、`sqlite3.Connection` をリクエストごとに生成・破棄している)。FastAPI/Starletteは同期の依存関数・エンドポイントをスレッドプールで実行するが、リクエストによって異なるワーカースレッドに割り当てられうるため、1リクエスト内で生成した`sqlite3.Connection`(既定で `check_same_thread=True`)を、生成時と異なるスレッドで使おうとすると例外になる。単体テスト・APIテスト(`fastapi.testclient.TestClient`)では同期的に同一スレッドで処理されるため、この問題はTestClient経由のテスト(P007・P008のT002・U001〜U004の全APIテスト)では一切再現しなかった。実サーバー(uvicorn)に対する結合テストで初めて顕在化した。
- テスト指示との矛盾の疑い: なし
- 次工程への申し送り: **重大度が高い実装不具合**。`server/app/db/connection.py`/`server/app/api/deps.py` の見直しが必要(例: `sqlite3.connect(..., check_same_thread=False)` への変更、またはリクエストの依存解決とハンドラ本体を確実に同一スレッドで実行する設計への変更)。この不具合は本番相当の実サーバー運用で断続的な500エラーを引き起こす可能性があり、P202(修正計画)で優先度「高」として扱うべきと考える。
