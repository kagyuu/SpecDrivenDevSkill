# 【テストID】A004

## 【目的】

* 複数ユーザーが同一会議室に対して連続して予約を試みる業務フローを通して、予約重複防止が一貫して機能することをシステム全体で確認する。単一APIの単体テスト(`docs/P007-impl-direction/U002-reservation-core.md`)・単一スプリントの結合テスト(`docs/P008-test-direction/T004-reservation-conflict-display.md`)は個別のAPI呼び出し単位での確認にとどまるため、本テストでは複数ユーザー・複数回の予約操作を1つの業務フローとして通しで確認する。

## 【参照テスト計画】

* `docs/P006-test-plan.md` §2(業務ルール違反観点、境界値)

## 【対象モジュール】

* `server/` 予約API全体、`client/` S02/S03

## 【前提条件】全モジュールビルドが成功していること

* `cd server && uv run python -m pytest tests/ -v` が全PASS
* `cd client && npm run build` が成功

## 【使用するテストデータ】

* 一般ユーザー `user001`・`user002`、会議室1件(`会議室A`、収容10名)

## 【事前準備】

* 永続DBファイルにマイグレーションを適用し、上記データをシードする。

## 【実行手順】

1. `user001` でログインし、`会議室A` に本日 `10:00-11:00` の予約を作成する。
2. `user002` でログインし、同じ `会議室A` に本日 `10:30-11:30` の予約を作成しようとする。
3. `user002` で、同じ `会議室A` に本日 `11:00-12:00`(手順1の予約の終了時刻ちょうどから始まる、連続した時間帯)の予約を作成しようとする。
4. `user002` で、同じ `会議室A` に本日 `09:00-10:00`(手順1の予約の開始時刻ちょうどに終わる、連続した時間帯)の予約を作成しようとする。

## 【実行コマンド】

* `cd client && npx playwright test tests/acceptance/a004_reservation_conflict_system_check.spec.ts`

## 【期待結果】

* 手順2: 時間帯が重なるため、409 `RESERVATION_CONFLICT` となり、画面に「選択した会議室・時間帯は既に予約されています」が表示される。
* 手順3: 手順1の予約とちょうど時刻が接している(背中合わせの)時間帯への予約となる。`docs/P003-backend-spec.md` §5.9は「背中合わせの予約(`new.start_time == existing.end_time` または `new.end_time == existing.start_time`)は重複とみなさない」と明記しており、この判定式は半開区間モデルの意図的な設計判断である。したがって本手順は**重複エラーにならず201(予約成立)** となる。※P202 F004にもとづき訂正(訂正前は誤って409を期待していた。矛盾の詳細・訂正の根拠は `docs/P202-fix-plan/fixed/F004-a004-back-to-back-expectation.md` を参照)。
* 手順4: 手順3と同様に時刻が接している(背中合わせの)ケースであり、同じ理由により**重複エラーにならず201(予約成立)** となる。※P202 F004にもとづき訂正。

## 【合否判定基準】

* 手順2で409エラーとなり予約が作成されないこと、かつ手順3・4で201(予約成立)となることを確認できればPASS。手順2が409にならなかった場合、または手順3・4が409になった場合(背中合わせの予約が誤って拒否された場合)はFAILとする。※P202 F004にもとづき訂正。
