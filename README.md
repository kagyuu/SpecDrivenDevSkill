# Spec-Driven Dev Skill

Claude Code に、日本のシステム開発で標準的な**ウォーターフォール/V字モデル**の手順を踏ませて開発を行わせるための Skill(指示書一式)。

あいまいな要求からいきなりコードを書かせるのではなく、要件を段階的に具体化し、設計レビュー・実装指示書・テスト指示書を経てから初めて実装・テストに進ませる。テストで見つかった不具合の修正も、いきなりコードを触らせず、まず修正計画を作らせてから着手させる。

## このリポジトリの構成(バージョン履歴)

このリポジトリは、Skill そのものを Claude Code とやり取りしながら育てていった履歴を兼ねているため、通常のプロジェクトとは違い、バージョンごとのフォルダをそのまま並べる変則的な構成にしている。

```
V0.1/           最初のドラフト(9フェーズ構成、各フェーズごとに人間レビュー)
V0.2/           整合性・実行可能性・記述一貫性の観点でレビューし、不備を修正した版
V0.2_testbed/   V0.2を会議室予約システムで実地検証した記録
V0.3/           V0.2_testbedの検証で見つかった不備を修正した版
V0.3_testbed/   V0.2→V0.3の差分(不備が実際に解消されたか)を再検証した記録
V0.4/           設計方針を変更: 要件定義後は人間レビューなしで一気通貫実行 + ADR/CR/ArchitectureHandbookを新設
V0.4_testbed/   V0.4をP002〜P302連続実行 + CRによるRefactorまでフルに実地検証した記録
V0.5/           V0.4_testbedの検証で見つかった不備26件を修正した版。人間向け利用マニュアル(USER_GUIDE.md)を新設
V0.5_testbed/   V0.4→V0.5の差分を、実際のCR処理(CR-002)を含めて再検証した記録
V0.6/           V0.5_testbedの検証で見つかった新規2件を修正した版。持ち越されていた3論点を「対処しない」と確定
V0.6_testbed/   V0.5→V0.6の差分を、データモデル変更を伴うCR-003とデプロイトポロジー破壊実験で検証した記録
```

* 各 `Vx.y/` フォルダは、その時点での Skill 一式(`SKILL.md` + `SKILL-P0NN-*.md`/`SKILL-0N-*.md` + `TEMPLATE-*.md`)をまるごと収めたスナップショット。
* 実際に使うときは、**最も新しいバージョンのフォルダ(`V0.5/`)を使うこと**。
* バージョンごとに何を直したかは、そのバージョンのフォルダにある `review-report.md`(存在する場合)に記載している。
* 各 `Vx.y_testbed/` フォルダは、そのバージョンのSkillを実際に(会議室予約システムを題材に)動かして検証した記録。`testbed.md`(確認観点と検証結果)と `e2e-validation-report.md`(詳細な検証レポート・見つかった不備一覧)を収めている。次バージョンは、この不備一覧をもとに改訂している。

## V0.4以降のSkillの中身(P番号フェーズ構成)

V0.4からは、フェーズを7つの「Step」にグループ化し、フェーズ番号を`P001`〜`P905`という3桁のP番号で管理している(`V0.1`〜`V0.3`はフェーズ1〜9の通し番号だった)。

| Step | 内容 | 主なフェーズ |
| --- | --- | --- |
| Require Development Step | 要件定義。ここだけは人間と対話しながら作る | P001 |
| Plan Loop Step | UI設計・詳細設計・トレーサビリティ確認・実装計画・テスト計画・実装/テスト/受け入れの各指示書作成・横断レビュー | P002〜P012 |
| Overview Step | ソースツリー索引・ADR・ArchitectureHandbook整備 | P020〜P022 |
| Executor | 実装コンテキスト構築・実装・結合テスト・索引更新(スプリント単位で反復) | P101〜P104 |
| Reviewer Loop | 受け入れテスト・修正計画・修正実行・影響分析・再テスト | P201〜P205 |
| Closing | 全体索引作成・納品物作成(リリース判定) | P301〜P302 |
| Refactor | 人間からの変更依頼(CR)を受けて、影響範囲を判断し差分更新する | P901〜P905 |

P001完了後は、Require Development Step以外は人間のレビューを挟まず連続実行する。実行結果(コード・テスト結果・各種ドキュメント)がまとまった後で、人間が内容を確認し、変更してほしい点があれば `docs/CR.md` に変更依頼(CR)を書くことで、Refactor(P901〜P905)が変更を取り込む。この一連の流れの実例(小さな変更・UI+バックエンド+DBにまたがる大きめの変更それぞれ)は `V0.5_testbed/docs/cr-records/CR-001.md` `CR-002.md` を参照。

このSkill自体はソースコードやテストの実行は行わない。各フェーズで生成される実装指示・テスト指示・修正指示という「Markdown」を、実装担当・テスト担当・修正担当として動くClaude Codeに実行させることで、初めてコードが書かれたりテストが実行されたりする。

## 使い方(Claude Codeへの導入方法)

詳しい手順・具体例は **`V0.5/USER_GUIDE.md`** を参照。要点だけ書くと:

1. `V0.6/` フォルダの中身(`SKILL.md` `SKILL-P0NN-*.md` `TEMPLATE-*.md`)を、開発対象プロジェクトの Skill 用フォルダ(例: `.claude/skills/spec-driven-dev/`)にそのままコピーする。
2. 対象プロジェクトで Claude Code を起動し、作りたいアプリケーションの概要を伝えてこのSkillでの開発を依頼する。まず人間と対話しながら `docs/P001-requirement.md`(要件定義)を作る。
3. 要件定義ができたら、そのまま続行を指示する。以降はP002〜P302まで人間のレビューを挟まず自動的に進み、実際のアプリケーションコード・テストが作られる。`docs/.inprogress` に現在のフェーズ番号が記録され、中断しても再開できる。
4. `docs/.inprogress` が削除され `docs/P302-deliver.md` が作られたら初回ビルド完了。人間は実際に動かして確認し、変更してほしい点があれば `docs/CR.md` に変更依頼(CR)を書く。
5. CRを書いたことをClaude Codeに伝えると、P901〜P905(Refactor)が影響範囲を判断したうえで差分更新を行い、テストを再実行して結果を記録する。

## 各バージョンの位置づけ(サマリ)

* `V0.1` → `V0.2`: 開発体系の整合性・実行可能性・記述の一貫性の3観点でレビューし、不備を修正(詳細: `V0.2/review-report.md`)。
* `V0.2` → `V0.3`: `V0.2_testbed` の実地検証で見つかった不備7件(中3・低4)を修正(詳細: `V0.3/review-report.md`)。
* `V0.3` → `V0.4`: 各フェーズごとの人間レビューを廃止し、要件定義後は完成まで連続実行する方式に設計変更。ADR・CR・ArchitectureHandbookを新設し、フェーズ番号をP番号体系に刷新(詳細: `V0.4/SKILL.md`)。
* `V0.4` → `V0.5`: `V0.4_testbed` の実地検証(P002〜P302連続実行+CRによるRefactor)で見つかった不備26件を修正し、人間向け利用マニュアル(`USER_GUIDE.md`)を新設(詳細: `V0.5/review-report.md`)。
* `V0.5` → `V0.6`: `V0.5_testbed` の実地検証(CR-002)で新たに見つかった2件を修正(詳細: `V0.6/review-report.md`)。
  * 完了したCRを `docs/CR.md` にどう反映するかを、「残す/削除する」の二値ではなく、既存の記法を現物で確認して複製する**手順ベースの指示**に変更した。あわせて、`TEMPLATE-CR.md`(削除と指示)と `SKILL-P904-cr-verify.md`(残すと指示)が正面から矛盾していた根本原因も解消した。
  * データモデルを持つ場合の**マイグレーション方式の明記と冪等性の担保**を、設計時(P003)・テスト計画時(P006)・CR適用時(P903)・納品時(P302)の4段階で求めるルールを追加した。
* `V0.5` まで持ち越されていた3論点(テストIDと実装命名の対応づけ・1根本原因に対する修正ファイルの粒度・CRのスコープ判断の仕組み化)は、**人間の判断により「対処しない」と確定**した(理由: 自動検証は複雑化し破綻しやすい / 形式化はAIが苦手で誤判定が増える / 影響分析エンジンは破綻リスクが高い)。詳細は `V0.6/review-report.md`「人間の判断により対処しないと決定した論点」を参照。
