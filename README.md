# Spec-Driven Dev Skill

Claude Code に、日本のシステム開発で標準的な**ウォーターフォール/V字モデル**の手順を踏ませて開発を行わせるための Skill(指示書一式)。

あいまいな要求からいきなりコードを書かせるのではなく、要件を段階的に具体化し、設計レビュー・実装指示書・テスト指示書を経てから初めて実装・テストに進ませる。テストで見つかった不具合の修正も、いきなりコードを触らせず、まず修正計画を作らせてから着手させる。

## V0.4以降のSkillの中身(P番号フェーズ構成)

V0.4からは、フェーズを7つの「Step」にグループ化し、フェーズ番号を`P001`〜`P905`という3桁のP番号で管理している(`V0.1`〜`V0.3`はフェーズ1〜9の通し番号だった)。この番号体系はV0.4以降変わっていない。

| Step | 内容 | 主なフェーズ |
| --- | --- | --- |
| Require Development Step | 要件定義。ここだけは人間と対話しながら作る | P001 |
| Plan Loop Step | UI設計・詳細設計・トレーサビリティ確認・実装計画・テスト計画・実装/テスト/受け入れの各指示書作成・横断レビュー | P002〜P012 |
| Overview Step | ソースツリー索引・ADR・ArchitectureHandbook整備 | P020〜P022 |
| Executor | 実装コンテキスト構築・実装・結合テスト・索引更新(スプリント単位で反復) | P101〜P104 |
| Reviewer Loop | 受け入れテスト・修正計画・修正実行・影響分析・再テスト | P201〜P205 |
| Closing | 全体索引作成・納品物作成(リリース判定) | P301〜P302 |
| Refactor | 人間からの変更依頼(CR)を受けて、影響範囲を判断し差分更新する | P901〜P905 |

P001完了後は、Require Development Step以外は人間のレビューを挟まず連続実行する。実行結果(コード・テスト結果・各種ドキュメント)がまとまった後で、人間が内容を確認し、変更してほしい点をAIに伝えることで、Refactor(P901〜P905)が変更を取り込む。

V0.7では、CRに関わるファイルを役割ごとに3つに分けた。人間はファイルを自分で書く必要はなく、普通の言葉で依頼すればP901が起票する。

| ファイル | 役割 |
| --- | --- |
| `docs/CR.md` | 状態の台帳(一覧・状態・優先度のみ。本文は持たず、完了行も残す) |
| `docs/P901-cr-direction/CR-NNN.md` | 変更要求(何をなぜ変えてほしいか。P901が起票し、着手前なら人間が修正してよい) |
| `docs/P903-cr-records/CR-NNN.md` | 対処の記録(スコープ判断・変更内容・テスト結果。P903が起票しP904/P905が追記) |

実例は `V1.0_testbed/docs/P901-cr-direction/CR-001.md` と `V1.0_testbed/docs/P903-cr-records/CR-001.md` を参照。却下されたCRの例は `CR-003`(優先度 `N/A`)。

V0.8では、この3ファイル構成に加えて次の仕組みを導入した。

* **タスク単位のチェックボックス**: P007のスプリントファイルが、`U0NN-Txx`単位のOKFチェックボックスを内包する構成になり、スプリント途中の中断・再開を「どのタスクまで完了したか」で正確に扱えるようになった。
* **`.inprogress`の入れ子表記**: RefactorがPlan Loop〜Closingを内部で再実行している間、`docs/.inprogress`が`P903:P0NN`という表記を持ち、中断・再開時にCRの文脈を見失わないようにした。
* **「テスト指示側の誤り」という結果区分**: テストが失敗した原因がコードの欠陥ではなく、テスト指示自体が上位仕様と矛盾していた場合を、コード欠陥の修正とは別の一級の結果区分として扱えるようにした。

このSkill自体はソースコードやテストの実行は行わない。各フェーズで生成される実装指示・テスト指示・修正指示という「Markdown」を、実装担当・テスト担当・修正担当として動くClaude Codeに実行させることで、初めてコードが書かれたりテストが実行されたりする。

## 使い方(Claude Codeへの導入方法)

詳しい手順・具体例は **`V1.0/USER_GUIDE.md`** を参照。要点だけ書くと:

1. `V1.0/` フォルダの中身(`SKILL.md` `SKILL-P0NN-*.md` `TEMPLATE-*.md`)を、開発対象プロジェクトの Skill 用フォルダ(例: `.claude/skills/spec-driven-dev/`)にそのままコピーする。
2. 対象プロジェクトで Claude Code を起動し、作りたいアプリケーションの概要を伝えてこのSkillでの開発を依頼する。まず人間と対話しながら `docs/P001-requirement.md`(要件定義)を作る。
3. 要件定義ができたら、そのまま続行を指示する。以降はP002〜P302まで人間のレビューを挟まず自動的に進み、実際のアプリケーションコード・テストが作られる。`docs/.inprogress` に現在のフェーズ番号が記録され、中断しても再開できる。
4. `docs/.inprogress` が削除され `docs/P302-deliver.md` が作られたら初回ビルド完了。人間は実際に動かして確認する。
5. 変更してほしい点があれば、普通の言葉でClaude Codeに伝える。P901が変更要求として起票し、P902〜P905(Refactor)が影響範囲を判断したうえで差分更新を行い、テストを再実行して結果を記録する。
