# システム詳細設計

## 目的

* システム詳細設計書を作成して、バックエンドの仕様を確定する。

## インプット文書

* `docs/P001-requirement.md`
* `docs/P002-frontend-spec.md`
* `docs/ADR.md` (既存のADRがあれば)
* `docs/CR.md` (Refactorステップからの再入時。未対応の変更要求があれば)

## アウトプット文書

* `docs/P003-backend-spec.md`

### アウトプットの記載内容

* `docs/P001-requirement.md` のAPI一覧にある全エンドポイントの完全な内部仕様
  * `docs/P002-frontend-spec.md` で明らかにしたAPIとデータモデルを使ってどのように外部仕様を成り立たせるか
  * 状態を保持する場合は、そのスコープ (システム、アプリケーション、ユーザセッションなど)と実現方法 (メモリ、KVS、RDBなど)を明らかにすること
* ユーザインタフェースに現れないデータがある場合は、データモデルを追加する: ER図 + テーブル定義書(主要カラム・型・制約・リレーション)
* ユーザインタフェースから使うデータモデルを修正する場合は、その旨を `docs/P002-frontend-spec.md` に追記する。修正内容と理由を明記すること。
* 非機能要件のうちインフラ寄りの項目(可用性・TLS終端・スケーラビリティ・ログ集約基盤など)を担当するフェーズを明確化する。
  * これらは`docs/P001-requirement.md`に記載された非機能要件のうち、アプリケーションコードの範囲を超え、実行環境・インフラ構成に依存する項目である。
  * P003では、これらの項目についてアプリケーションコード側で前提とする内容(例: 「TLS終端はリバースプロキシ側で行われる前提とする」)のみを明記し、実際のインフラ構成そのものの決定は `docs/P005-impl-plan.md`(インフラ・ミドルウェアが必要な場合のスプリント化)および `docs/P302-deliver.md`(Closing、実際の配布トポロジー整備)に委譲する旨を、該当箇所に明記すること。
  * この委譲の明記により、P004(トレーサビリティマトリクス)・P010(設計書横断レビュー)は、これらの非機能要件の充足確認をP005/P302の記載箇所で行う。P003側で「委譲する」旨の記載自体が無い場合は、P004/P010はMISSING/PARTIALとして扱う。

`docs/P001-requirement.md` になかったAPI実装をここで新たに追加しない。詳細化の過程でスコープの抜け漏れに気づいた場合は、勝手に拡張せず明示的に指摘すること。

* フェーズP002とP003の役割分担が曖昧になりやすい記載(例: 認証方式)について
  * 内部実現方法(例: パスワードのハッシュ方式、セッションの保存先・有効期限)をここP003で確定する際は、対応する外部から見える契約(例: Cookie/トークンの別、レスポンス形式)が `docs/P002-frontend-spec.md` のどこで確定しているかを参照として明記すること。
  * この相互参照は、P002・P003どちらで決めるべきか判断に迷う項目についてのみ行えばよい。役割分担が明確な項目にまで機械的に付ける必要はない。
* CR(`docs/CR.md`)にもとづく再入時は、CRで指定された変更点のみを反映し、無関係な既存記述は変更しない。何をCRの何番にもとづいて変更したかを本文中に明記する。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* `docs/P004-traceability-matrix.md`
* `docs/P005-impl-plan.md`
* `docs/P006-test-plan.md`
