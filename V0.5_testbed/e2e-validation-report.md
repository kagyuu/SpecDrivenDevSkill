## これは何か

`spec-driven-dev` Skill(V0.5)が、V0.4で発見された23件(実際の列挙は26件、`testbed.md`「件数についての注記」参照)の不備・曖昧点を意図どおり解消しているかを、`V0.5_testbed/`(`V0.4_testbed/`を土台に`.claude/skills/spec-driven-dev/`だけをV0.5に差し替えたテストヘッド)上で確認した記録。

検証はコスト制御のため全パイプライン(P002〜P302)を再実行せず、次の2段構えで行った。

* **Tier A(動的検証)**: 新規のCR-002(S06会議室管理画面に説明文フィールドを追加)を実際にP901→P905のフルフローで処理し、コード・テストを実際に書き・実行し、意図的に仕込んだバグに対して実際の修正サイクル(P202〜P205相当)を回した。1-3, 1-4, 1-5, 2-1, 2-2, 2-5, 2-7, 2-8, 2-9, 3-10, 3-11の11件がこの過程で確認できた(2-9は当初Tier B想定だったが、CR-002処理で実際にバックアップファイル名の衝突回避を確認できたため昇格)。
* **Tier B(静的検証)**: 残る15件について、V0.4実行時の実際の問題箇所(原文引用)とV0.5の新しい記述(原文引用)を突き合わせ、新記述が有効だったかを判断した。1-6のみ、デプロイ資産(`docker-compose.yml`・`nginx.conf`)の軽量な動的スポットチェックも併用した。

**結果サマリ**: 26件中、24件は明確に解消(✅合格)、2件(1-6, 3-11)は「概ね合格だが確度の割引・留保あり」と判定した(3-8も既存記述の非遡及という留保付きだが、これはV0.5の欠陥ではなくSkillという仕組みの当然の限界であるため別枠で扱う。詳細は本文参照)。**致命的にV0.5でも未解決の重大な不備は無い**。CR-002の実処理を通じて、V0.5が新たに導入した仕組み(CRスコープ決定表、複数テスト1根本原因の修正、優先度ルーブリック、ADR確認記録など)がいずれも実際に機能することを確認できた。

一方、本検証を通じてV0.5にも新たに1件の実質的なワーディング上のギャップ(3-11の完了行表記が実際の運用パターンを正確に言い当てていない)と、V0.5の対応範囲に含まれない1件の新規ギャップ(CRによるデータモデル変更(ALTER TABLE)時のマイグレーション冪等性についてSkillが指針を持たない)を発見した。詳細は「V0.5で新たに見つかった問題」を参照。

## 3. V0.5で新たに見つかった問題

V0.4→V0.5で対応した26件の不備とは別に、本検証の過程で以下を新たに発見した。V0.5(`/tmp/work/V0.5/`)のファイル自体は変更していない。

### 3.1 defect 3-11再訪: P904の完了行表記ルールが「二値」を前提にしており、実際に確立した記法(第三のパターン)を正確に言い当てていない — 新規指摘、重大度: 低

* **事象**: `SKILL-P904-cr-verify.md`は「完了したCRを`docs/CR.md`から削除するか残すかは、プロジェクトの慣習に従う。慣習が無い場合のデフォルトは『残す(状態欄のみ完了に更新、一覧表からは除かない)』」と、"残す"か"削除する"の二値を前提に書かれている。
* しかし本testbedで実際にCR-001処理時(V0.4ルール下)に採られた記法は、そのどちらでもない。実物の`docs/CR.md`を確認すると、CR一覧の**表からは除かれ**(表は「現在、未対応・対応中のCRはありません」のプレースホルダのみ)、代わりに表の下に「対応完了済みのCRは`docs/cr-records/`を参照」という見出しと、`* [docs/cr-records/CR-001.md](...) — タイトル(完了、日付)`という**リンク一覧(箇条書き)**が追加される、という第三の形式だった。
* **影響**: 今回はCR-002処理の際に「既に確立した記法があれば従う」という上位の趣旨を汲み取り、この第三の形式(表からは除くがリンク一覧として残す)を正しく再現できた。しかし、`SKILL-P904-cr-verify.md`の字面が「残す/削除する」の二値評価を前提としているため、これを字面どおりに読んだ別のAgentが「これは"削除する"パターンだ」と誤認して(表だけでなくcr-recordsへの参照も含めて)CRへの言及を完全に消してしまう、あるいは逆に「これは"残す"パターンだ」と誤認して表に行を残したまま`完了`にするだけで済ませてしまう、という2方向のブレが起こりうる。
* **推奨対応(V0.6検討課題)**: `SKILL-P904-cr-verify.md`の記法バリエーションを二値ではなく「プロジェクトの`docs/CR.md`の直近の完了CRの実際の記載形式をそのまま複製する」という手順ベースの指示に書き換えるか、「表からは外し、`docs/cr-records/`へのリンク一覧を残す」という具体的な第三形式自体をデフォルトとして明記することを推奨する。

### 3.2 新規: CRによるデータモデル変更(ALTER TABLE系マイグレーション)時の冪等性について、Skillに指針が無い — 新規指摘、重大度: 中

* **事象**: 本testbedのマイグレーション基盤(`server/app/db/connection.py`の`init_db()`)は、アプリ起動のたびに`app/db/migrations/*.sql`を全件再実行する設計になっており、これは既存の`0001_initial.sql`が`CREATE TABLE IF NOT EXISTS`のみで構成されているために冪等に成功していた(V0.4実行時点では問題が顕在化しなかった)。
* CR-002でデータモデル変更(`ROOMS.description`カラム追加)を実装する際、新しいマイグレーション`0002_add_room_description.sql`(`ALTER TABLE ROOMS ADD COLUMN description TEXT`)を追加する必要が生じたが、SQLiteの`ALTER TABLE ADD COLUMN`には「未適用の場合のみ実行する」という条件付き構文が無いため、素朴に追加すると2回目以降の起動で`duplicate column name`エラーになり、アプリが起動しなくなるという問題が判明した(単体テストでは各テストが独立した一時DBを使うため気づきにくいが、実運用の再起動シナリオでは確実に踏む)。
* `SKILL-P903-refactor-execute.md`の「データモデル変更」カテゴリの対応表(目安フェーズ: P002・P003・P004・P005〜P009)にも、`SKILL-P003-backend-spec.md`のデータモデル記述にも、この種の非冪等マイグレーションへの対処方針についての言及が無い。V0.5は「Docker CLIはあるがデーモンが無い」(defect 2-6)のような他の運用上のギャップは丁寧にケアしているが、CRによるスキーマ変更が今回のような非冪等な追記マイグレーションを要求するケースは想定されていない。
* **影響**: 今回は実行担当(私)が独自に「`init_db()`側で`duplicate column name`エラーを捕捉して無視する」という対処を判断し、★FIXME★付きでP003・P007に記録した。V0.4→V0.5で「実行担当が独自に発明した運用をSkillのルールとして正式に取り込む」という前例(1-5, 2-6, 3-1など)にならえば、これも将来のバージョンでSkill側のルールとして明文化する候補になりうる。
* **推奨対応(V0.6検討課題)**: `SKILL-P003-backend-spec.md`または`SKILL-P020-source-index.md`に、「データモデル変更を伴うCRでは、既存のマイグレーション実行方式(全件再実行/差分適用/バージョン管理テーブルの有無)を確認し、非冪等なDDL(`ALTER TABLE ADD COLUMN`等)を追加する場合は冪等化の方針(エラー捕捉、マイグレーション適用済みテーブルの導入など)を明記する」という指針を追加することを推奨する。

### 3.3 参考: defect 3-8の既存記述への非遡及(V0.5の不備ではなく、当然の限界として記録)

* `docs/P007-impl-direction.md`冒頭に、V0.4時点で作成された「クライアント・サーバ型のため`client/`(React+TS+Vite、npmビルド)・`server/`(Python+FastAPI、uvビルド)とする」というハードコードされた技術スタック名が今も残っている(実際にはサンドボックス制約により代替実装〈Starlette、プレーンJS〉が採用され、この記述は事実と異なる)。
* V0.5の新ルール(ADR参照での表現に統一)は今後の新規作成・改訂時に適用されるものであり、Skillのルール変更が既存の生成済みドキュメントを自動的に遡及修正するわけではない。これはV0.5の欠陥ではなく、Skillという仕組みの当然の限界(生成物の遡及修正は、そのドキュメントを実際に再生成するP020/P007等のフェーズを再実行しない限り起こらない)であるため、新規のdefectとしては扱わない。CR-002ではP007目次冒頭の当該行は更新対象に含めなかった(CR-002のスコープに関係しないため)。

`V0.5/review-report.md`末尾「今回あえて反映しなかった判断」に記載のとおり、1-3(P008テストIDとP102命名の対応の構造的保証)・2-5(1根本原因・多テスト波及時の修正ファイル粒度の形式的基準)・1-5(P903のCRスコープ判断の自動分類の仕組み化)の3件は、V0.5では部分的な緩和にとどめ、設計そのものの再検討はV0.6の検討課題として人間に委ねる方針だった。本検証(CR-002の実地処理)は、この3件についてV0.5の「部分的な緩和」が実務上は十分に機能することを示した(1-3: 命名の厳密一致を実際に達成、2-5: 複数テスト1ファイルの運用を実際に達成、1-5: 複合カテゴリのCRでも対象/対象外の判断と記録を実際に達成)一方、3.2節で新たに指摘したマイグレーション冪等性のような、CRのデータモデル変更カテゴリに特有の別の課題があることも明らかになった。V0.6の設計検討時にはあわせて考慮することを推奨する。
