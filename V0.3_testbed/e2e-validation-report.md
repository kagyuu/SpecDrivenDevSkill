# spec-driven-dev Skill V0.3 差分検証レポート(V0.3_testbed)

作成日: 2026-07-30

## 概要

本レポートは、`V0.2_testbed`(会議室予約システムを題材にした Skill V0.2 のフルパイプライン実地検証)で見つかった7件の不備を修正した `spec-driven-dev` Skill V0.3 が、**意図通りに機能するようになったか**を確認するための差分検証(第2回実地検証)の結果である。

`docs/01-requirement.md`(フェーズ1)は V0.2_testbed のものをそのまま再利用し、`docs/.inprogress` を `2` にリセットしたうえで、Skill V0.3 のルールに従いフェーズ2〜9を通しで無人・自己レビュー方式(1人のAgentがSkill実行者役・レビュー役・実装/テスト/修正担当役を兼務)で再実行した。V0.2との違いを検証するのが主目的であり、V0.2で発見済みの機能自体(会議室予約システムの業務要件)は変更していない。

検証観点は `testbed.md` の「V0.2 → V0.3 の変更点と確認観点」に列挙された6項目(以下、確認観点1〜6)である。特に確認観点4(フェーズ7全PASS時のフェーズ8自動完了)を主たる検証対象とするため、フェーズ6のコード実装は、V0.2で見つかった不具合(F001: 予約作成時に存在しない参加者IDを指定すると500エラーになる)の修正を**実装時点から**組み込んだ状態でスタートした(意図的にバグを再現していない)。この結果、当初のフェーズ7は全件PASSとなった。

このままでは確認観点2(`ALL_RESOLVED`)・確認観点3(OKF目次の`fixed/`付け替え)は、実際にフェーズ8の修正サイクルが回る場面がないと検証できない。そこで**補足ラウンド**として、検証目的で意図的に1件のバグ(F002: 会議室登録APIの`capacity`検証漏れによる500エラー)を仕込み、フェーズ7の該当テストを再実行して実際に1件のFAILを発生させたうえで、`SKILL-08-fix-plan.md`(V0.3)の規定に従ってフェーズ8の修正サイクル(修正指示ファイル作成→調査→修正→再テスト→`fixed/`への移動→解決記録の更新)を実際に最後まで回した。これにより確認観点2・3も実地検証済みである(詳細は後述)。

実装は V0.2 と同様、本検証環境がネットワーク分離されており `pip install fastapi` / `npm install react` 等が実行できない制約があるため、バックエンドは FastAPI の内部基盤である Starlette + Pydantic(事前インストール済み)、フロントエンドはビルド不要の素のHTML/CSS/JavaScriptで実装した。これは V0.2 と同一の環境制約であり、`testbed.md` の記載どおり V0.3 のSKILLルールにもこの点は反映されていない(実行環境起因でありSKILL自体の欠陥ではないため)。

## 新たに見つかった問題

V0.3で修正済みの7件とは別に、今回の再検証で以下を確認した。

1. **(軽微・V0.2の残骸、V0.3ルールとは無関係)** `docs/08-fix-plan/fixed/F001-invalid-participant-id-500.md`(V0.2実行時に作成された過去の修正記録ファイル)の1箇所に、旧テンプレートの `FIX001` という表記が残っていた(`【修正タスクID】FIX001`。同じファイル内の他の箇所は既に`F001`表記に統一されていた)。これはV0.2実行時点でAgentの自己判断による表記統一が不完全だったことを示す実例であり、V0.3で `TEMPLATE-08-fix-direction.md` のプレースホルダ自体を修正した効果(確認観点6)を裏付ける材料でもある。本検証中に発見し、`F001`に修正した。SKILL側の欠陥ではなくV0.2実行時の記録内容の問題であり、SKILL修正は不要と判断する。
2. **(SKILLルールの軽微な gap、要検討)** `SKILL-08-fix-plan.md`の「直近のテスト記録に失敗が1件もない場合」の規定は、`docs/08-fix-plan.md`と`docs/08-fix-plan/08-fix-unresolved.md`の作成のみを明記しており、`docs/08-fix-plan/08-fix-resolved.md`の扱いには言及していない。フェーズ7当初全PASSだった時点(16:00)で、V0.2から引き継いだ`08-fix-resolved.md`(F001の記述)をそのまま残すと実行実態(修正サイクルなし)と矛盾するため、実態に合わせて0件の内容に上書きしたが、この判断はSKILLの明示的指示によるものではなくAgentの自己判断だった(その後の補足ラウンドでF002の実修正サイクルが発生したため、最終的な`08-fix-resolved.md`はF002を1件記録する内容になっている)。V0.4を検討する際は、「テスト全PASSの場合、`08-fix-resolved.md`をどう扱うか(作成しない/0件で作成する/前回内容を保持する等)」を明記することを推奨する。
3. **(実装上の逸脱、V0.2から継続、SKILL欠陥ではない)** バックエンドはFastAPI代替のStarlette+Pydantic、フロントエンドは素のHTML/JS、単体テストは`unittest`(pytestではなく)、結合・システムテストはPython標準ライブラリによるHTTPスクリプトで代替した。理由はV0.2と同一(本検証環境がネットワーク分離されており`pip install fastapi`/`npm install react`等が実行できないため)。`testbed.md`記載のとおりV0.3のSKILLルールにはこの点は反映されておらず、今回もSKILLの欠陥としては扱っていない。

上記以外に、V0.3の新ルール自体の記述に矛盾・欠落は見つからなかった。
