# ユーザインタフェース設計

## 目的

* ユーザインタフェース設計書を作成して、フロントエンドの仕様を確定する。

## インプット文書

* `docs/01-requirement.md`

## アウトプット文書

* `docs/02-frontend-spec.md`

### アウトプットの記載内容

* `docs/01-requirement.md` の画面一覧にある全入力項目のバリデーションルール(必須・形式・文字数・範囲など)
* `docs/01-requirement.md` のAPI一覧にある全エンドポイントの完全な外部仕様(メソッド、パス、リクエストボディ/パラメータ、レスポンス形式、ステータスコード、エラーケース)
* ユーザインタフェースを成立させるためのデータモデル: ER図 + テーブル定義書(主要カラム・型・制約・リレーション)
* 複雑な処理フロー(複数のユーザインタフェースをまたぐ処理など)があれば、シーケンス図で流れを明確化する

`docs/01-requirement.md` になかった画面やAPIをここで新たに追加しない。詳細化の過程でスコープの抜け漏れに気づいた場合は、勝手に拡張せず明示的に指摘すること。

* フェーズ2とフェーズ3の役割分担が曖昧になりやすい記載(例: 認証方式)について
  * 外部から見える契約(例: ログインでCookieを使うのかトークンを返すのか、レスポンス形式、クライアントが認識できるエラーコード)はこのフェーズ2で確定する。
  * その内部実現方法(例: パスワードのハッシュ方式、セッションの保存先・有効期限)はフェーズ3(`docs/03-backend-spec.md`)で確定する旨を、該当箇所に明記すること。
  * この相互参照は、フェーズ2・3どちらで決めるべきか判断に迷う項目についてのみ行えばよい。役割分担が明確な項目(例: 単純なCRUD API)にまで機械的に付ける必要はない。

### アウトプットを参照する文書

アウトプットの記載内容は、次の文書を作成できる程度に具体的であること

* `docs/03-backend-spec.md`
* `docs/04-impl-plan.md`
* `docs/05-test-plan.md`
