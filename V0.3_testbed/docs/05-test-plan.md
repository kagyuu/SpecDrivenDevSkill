# テスト計画書 — 会議室予約システム

> 本書は `spec-driven-dev` Skill フェーズ5の成果物です(V0.3ルールで再生成。内容自体はV0.2から変更なし — V0.3の変更点はフェーズ2/3・6・7・8のルールのみのため)。
> インプット: `docs/01-requirement.md`, `docs/02-frontend-spec.md`, `docs/03-backend-spec.md`, `docs/04-impl-plan.md`

## 1. テストレベルと目的

| テストレベル | 目的 | 本プロジェクトでの実施範囲 |
| --- | --- | --- |
| 単体テスト | 画面・APIが単体で仕様どおり動くか | 各スプリント(`docs/06-impl-direction/U000-*.md`)内で、バリデーション関数・重複チェックロジック・Repository/Service層を対象に実施 |
| 結合テスト | 画面・APIが連携して仕様通りか | スプリント内結合はフェーズ6で、スプリントをまたぐ結合(認証→予約作成→一覧反映等)はフェーズ7(`docs/07-test-direction.md`)で実施 |
| システムテスト(総合テスト) | システム要件・非機能要件を満たすか | フェーズ7で、性能・権限制御・主要業務シナリオを対象に実施 |
| 受入テスト | 本番相当環境での利用可否 | 本プロジェクトは社内ツールのモックデプロイであり、本番相当環境を用意しないため、フェーズ7では実施せず「10.未整備事項」相当としてフェーズ9で記録する |

## 2. 機能観点のテストケース(API単位)

各APIについて、正常系1件以上・主要異常系(バリデーションエラー/Not Found/認可エラー等)を最低限カバーする。

| API | 正常系 | 主要異常系 |
| --- | --- | --- |
| POST /api/auth/login | 正しいID/PWでCookie発行 | ID不存在、PW不一致、無効化ユーザー(いずれも401) |
| POST /api/auth/logout | セッション破棄(204) | 未ログイン(401) |
| GET /api/me | ログインユーザー情報取得 | 未ログイン(401) |
| GET /api/rooms | 有効な会議室一覧取得 | 未ログイン(401) |
| POST /api/rooms | 会議室作成(201) | 名称重複(400)、一般ユーザー(403) |
| PUT /api/rooms/{id} | 更新(200) | 不存在(404)、一般ユーザー(403) |
| DELETE /api/rooms/{id} | 論理削除(204) | 不存在(404)、一般ユーザー(403) |
| GET /api/reservations | 期間内予約一覧取得 | 日付パラメータ不正(400) |
| GET /api/reservations/mine | 自分の予約一覧取得(future/past) | 未ログイン(401) |
| GET /api/reservations/{id} | 詳細取得 | 不存在(404) |
| POST /api/reservations | 予約作成(201) | 時刻矛盾(400)、会議室不存在/無効(404)、重複(409) |
| PUT /api/reservations/{id} | 更新(200) | 他人の予約を一般ユーザーが編集(403)、重複(409) |
| DELETE /api/reservations/{id} | 取消(204) | 他人の予約を一般ユーザーが取消(403) |
| GET /api/users | ユーザー一覧取得 | 一般ユーザー(403) |
| POST /api/users | ユーザー作成(201) | 社員ID重複(400)、一般ユーザー(403) |
| PUT /api/users/{id} | 更新(200) | 不存在(404)、一般ユーザー(403) |
| DELETE /api/users/{id} | 論理削除(204) | 一般ユーザー(403) |

## 3. 機能観点のテストケース(画面単位)

| 画面 | 主要シナリオ |
| --- | --- |
| S01 | ログイン成功→S02遷移、ログイン失敗→エラー表示 |
| S02 | カレンダー表示、会議室フィルタ、空きセルクリックでS03へ |
| S03 | 予約作成成功→S02へ戻る、重複時エラー表示のまま画面に留まる |
| S04 | 本人予約の編集・取消成功、他人予約は編集不可(一般ユーザー) |
| S05 | 自分の予約のみ表示、期間フィルタ切替 |
| S06 | 会議室のCRUD、一般ユーザーは画面遷移不可 |
| S07 | ユーザーのCRUD、一般ユーザーは画面遷移不可 |

## 4. 非機能観点

| 観点 | テスト内容 | テストレベル |
| --- | --- | --- |
| 性能 | カレンダー表示APIのレスポンスが実用的な時間で返ること(参考値として計測し記録する。本番相当のロードテスト環境がないため目標値3秒はローカル計測での目安とする) | システムテスト(フェーズ7) |
| セキュリティ | 未ログイン状態での保護APIアクセス拒否、一般ユーザーでの管理者API/画面アクセス拒否、パスワードが平文で保存/レスポンスされないこと | 結合テスト/システムテスト(フェーズ7) |
| 運用(ログ監視) | アプリケーションログが標準出力に出力されること | システムテスト(フェーズ7、簡易確認) |
| 同時実行時の排他制御 | 同一会議室・同一時間帯への同時予約リクエストで二重予約が発生しないこと | システムテスト(フェーズ7) |

## 5. テスト遂行上の技術的な決め事

* 外部APIは存在しないため、モックは不要。
* テストデータは各テスト実行時にテスト専用のSQLiteファイル(一時ファイルまたは`:memory:`)を用いてクリーンな状態から準備する。本番用データファイル(`server/data/app.db`)を直接使ったテストは行わない。
* 単体テストは Python 標準の `unittest` を使用する(`docs/09-deliver.md` 未整備事項に後述する理由により、`pytest` は本検証環境では利用不可のため)。
* 結合・システムテスト(フェーズ7)は、実行中のアプリケーションサーバーに対して Python の `urllib`/`http.client` 等を用いたHTTPリクエストで検証する簡易スクリプトで実施する。ブラウザ自動化によるUI操作テストは、本検証環境にブラウザ自動化ツールが利用できないため対象外とし、画面の主要操作はその画面が呼び出すAPI呼び出し順序を模したシナリオスクリプトで代替する。この制約は `e2e-validation-report.md` に明記する。
