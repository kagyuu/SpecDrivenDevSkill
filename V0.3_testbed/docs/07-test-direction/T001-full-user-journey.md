# T001: フルユーザージャーニー(スプリント横断)

> V0.3ルールで再生成。IDは本ファイル名・目次と一致する T001 表記を最初から使用している。

あなたはテスト担当です。以下の1テストタスクだけを実施してください。

【テストID】T001
【目的】U001〜U004の全スプリントをまたいで、管理者による会議室登録から一般ユーザーの予約作成・カレンダー反映・編集・取消までの一連の業務フローがAPIレベルで仕様通りに動作することを確認する。
【参照テスト計画】`docs/05-test-plan.md` 3章(画面単位テストケース: S02,S03,S04,S05,S06)
【対象モジュール】`server/app/routers/auth.py`, `rooms.py`, `reservations.py`(スプリント1〜3の統合)
【前提条件】ビルド成功(本書冒頭参照)。サーバーが起動できること。
【使用するテストデータ】seedデータ(admin/admin12345, u001/password01)+ テスト内で新規作成する会議室・予約
【事前準備】一時DBファイルでサーバーをサブプロセス起動する。
【実行手順】
1. adminでログインし、会議室を1件新規登録する。
2. 一般ユーザー(u001)でログインし、`GET /api/rooms`で新規会議室が見えることを確認する。
3. u001で予約を1件作成する(`POST /api/reservations`)。
4. `GET /api/reservations`(カレンダー相当)で作成した予約が期間内に含まれることを確認する。
5. `GET /api/reservations/mine`で自分の予約に含まれることを確認する。
6. 予約の件名を変更して更新する(`PUT`)。
7. 予約を取消する(`DELETE`)。
8. 取消後、`GET /api/reservations/{id}`が404になることを確認する。
【実行コマンド】`cd server && python3 -m unittest tests.system.test_t001_full_user_journey -v`
【期待結果】各手順のHTTPステータスが仕様通り(200/201/204/404)であること。
【合否判定基準】全アサーションが成功すること。
【失敗時に記録する内容】失敗したステップ番号、期待したステータスコード、実際のレスポンス。
【修正禁止事項】アプリケーションコードを修正しない。テストコードをその場で都合よく変更しない。失敗したテストをスキップしない。期待値を変更して成功扱いにしない。同じ失敗に対して場当たり的な再テストを繰り返さない。
【次タスクへ進む条件】結果(PASS/FAIL/BLOCKED)がテスト記録`docs/test-records/`に記載された時点で次タスクへ進む。
